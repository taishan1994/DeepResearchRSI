# ADR-0001：首版采用模块化单体，而非微服务

- **状态**：已接受
- **日期**：2026-10-27
- **决策者**：架构

## 背景

DeepResearchRSI 需要同时处理检索、解析、证据抽取、综合、核验与进化。直觉方案是把每个 Agent 拆成独立服务，用消息队列连接。但这会立刻引入：分布式事务、跨服务追踪、版本兼容、部署编排等成本——而这些成本与研究质量无关。

## 选项

1. **微服务**：每个角色一个服务，消息队列通信。
2. **模块化单体**：单进程部署，代码层面保持模块边界与明确接口。
3. **单体 + 后台任务队列**：单进程承载 API 与逻辑，重活丢给 worker 进程（同一代码库）。

## 决策

选择 **选项 3**。

理由：
- 研究任务的瓶颈是**外部 API 限速与解析耗时**，不是内部调用开销。把重活放进队列 worker 就够。
- 模块边界通过目录（`services/*`）与接口（`packages/schemas/*`）强制，而不是通过网络边界强制。后者更贵且更容易腐化。
- 只有在**来源抓取、解析、并发任务**出现独立扩展需求时，才把对应模块拆出去。

## 后果

**正面**
- 本地一条命令启动，调试简单。
- 重构接口不需要协调多个部署。
- 数据一致性由数据库事务保证，不需要分布式协调。

**负面**
- 模块边界靠纪律维持，容易在赶工时被绕过。缓解：`packages/schemas` 作为唯一契约源，跨模块调用必须经过它。
- 单进程故障会同时影响 API 与 worker。缓解：worker 独立进程，崩溃不拖垮 API。
- 未来拆服务时需要做数据切分。缓解：模块内不跨表写别人的数据。

## 复查触发条件

出现以下任一情况时重新评估：
- 检索/解析成为独立扩展瓶颈（CPU 或网络配额）；
- 单机任务并发超过 worker 进程能承载的量；
- 进化模块需要与生产隔离运行（此时它应最先拆出）。
