# ADR-0003：冲突不强裁决，并列呈现

- **状态**：已接受
- **日期**：2026-10-27

## 背景

研究过程中频繁遇到来源冲突。例如 RTX PRO 6000 的 Blender 成绩：Blender Open Data 众测给 Server 版 15,821 分，Drop & Render 自测给 9,382 分——相差 69%。

直觉做法是"选更可信的那个"。但这会隐藏重要信息：**冲突本身往往是最有价值的发现**（说明结果对测试条件高度敏感，采购时必须自己实测）。

## 选项

1. **加权裁决**：按来源可信度打分，选高分者。
2. **并列呈现**：同时展示双方，标注 `confidence=disputed`，说明可能原因。
3. **不采集冲突数据**：只保留一致的部分。

## 决策

选择 **选项 2**。

规则：
- `Claim.confidence = "disputed"` 时，报告**必须**展示双方数字与来源。
- **不得**仅凭来源权威性高低抹掉另一方。
- 允许给出"可能原因"（测试条件、版本、散热），但必须标明这是**推断**而非事实。
- 只有在能证明一方**测量方法有误**时，才可降级或剔除——且需记录理由。

## 后果

**正面**
- 读者能看到真实的不确定性，而不是被喂一个虚假的确定答案。
- 冲突驱动的"需要自行实测"建议，比单一数字更有行动价值。
- 防止系统用"权威来源"掩盖证据不足。

**负面**
- 报告更冗长，读者需要自己判断。
- 部分用户会觉得"没给结论"。
- 需要额外的工作量去解释冲突成因。

**缓解**：对每个冲突给出**可执行的下一步**（如"以 Blender 为主要渲染器时必须自测"），把不确定性转化为行动项。

## 实例

`research/rtx-pro-6000` 中的 `c-blender-conflict` 即按本 ADR 处理：两个分数并列，标注 disputed，列出三种可能原因，并给出采购建议。
