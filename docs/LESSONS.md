# 上篇：做项目可复用的经验

## 一、证据与来源

### 1.1 「写了」/「配置了」/「跑了」是三件事

读到代码里有实现，不等于它在执行路径上；读到 `add_test(NAME ...)`
不等于测试在跑——要看它是否被调用。读到配置文件里有这个键，
不等于运行时这个键生效。

**怎么发现的**：某仓库有四个 CUDA 算子，代码写得完整，但从未被编译进
任何构建目标。基于「有这个算子」写的性能结论全部作废。
另一次：`--gguf-sha256` 参数标记为必填，但代码只是把它原样转发，从不计算。

**怎么用**：任何「系统具备某能力」的判断，都要能指出**执行路径**上的
具体位置。指不出就降级为「代码里存在该实现」。

### 1.2 分母要单独证明

比例类结论里，分母错了比分子错更致命，因为它不被怀疑。

**怎么发现的**：「覆盖审计：3069 个 blob 只覆盖 198 个」——3069 是错的
（那是把目录下所有对象数算了一遍）。分母一换，结论从「严重不足」
变成「基本覆盖」。

**怎么用**：报任何百分比之前，单独写一句「分母是 X，来自 Y」。

### 1.3 优先相信恒等式，其次才是描述

若 `A` 恒等于 `B`，这个事实强于任何文档对 `A` 的解释。
文档会过期、会措辞含糊，恒等式不会。

**怎么发现的**：追了八轮「那 11 MB 是什么」，最后发现是
「GGUF 元数据 + 对齐」的固定开销；另一处用一次减法锁定
`projected` 字段就是 `output` 字段。

**怎么用**：看到两个字段名不同但值总是一样，先假设它们是同一个东西，
再去找反例。

### 1.4 引用要存原文子串，不是「大意」

存摘要、存改写、存翻译，都会在回查时失效。字面子串能。

**代价**：跨语言材料上很难受（英文原文 vs 中文报告），
且渲染差异会造成假失败（见 1.5）。

**怎么用**：`quote` 字段存原文，允许截断。判定时做**空白与转义归一化**，
但不做同义改写。

### 1.5 同一段原文可能有多种渲染形态

从 HTML 提的文本与从 API 取的摘要，**不是同一串字符**：
LaTeXML 会把 `26%` 渲染成 `$26\%$`，非断行空格 `\xa0` 混在词之间。

**怎么发现的**：切换全文快照后，14 条原本正确的引文全被判「找不到」。
差点据此去改正确的证据。

**怎么用**：子串判定前做归一化（去 `$`、去 `\%`→`%`、`\xa0`→空格、
空白折叠）。归一化规则要写进文档，因为它决定了「什么算同一段原文」。

### 1.6 「没查」不能显示为「通过」

这是本文最重要的一条。

一个归档有 3002 条证据、0 份原文快照。E1 检查（引文是否原文子串）
无从比对，于是**退化为「无法校验」**。第一版把这种情况记为通过，
界面上显示 `[OK]`——而它一条都没验过。

**怎么用**：三态而不是两态。`通过` / `失败` / `未校验`，
且「未校验」要显式计数、醒目打印。任何把第三态折叠进第一态的代码，
都是在生产虚假的安全感。

### 1.7 只检索论文会漏掉整层工程实践

术语按发明者的人群分布。学术术语在论文里，工程术语在文档与博客里，
两者可能**完全不重叠**。

**怎么发现的**：一篇关于 PD 分离的综述，前三轮检索了 12 组主题式
查询、203 篇候选、46 篇纳入，`TBO` 在 46 篇全文里命中 47 篇。
但用户问的 `LPLB`、`Waterfill`、`DSpark` **一次都没出现**——
它们是 2026 年的框架实现，还没有对应论文，机制与实测数字只存在于
SGLang / vLLM 的官方文档与工程博客。

**代价**：论文因此缺了整整一层（优化技巧），而这一层恰是实践者
最需要的。补录花了整整一轮，新增 22 条证据、4 个来源。

**怎么用**：检索计划里**单独列一类来源**——框架官方文档、设计文档、
工程博客、release notes。判定标准不是「有没有论文」，而是
「这个系统在生产里怎么配」。凡是「本领域从业者会怎么称呼它」
的词汇，都要拿去做一轮检索。

### 1.8 分类的完备性不能用分类内部的例子来验证

拿几个例子套出一个分类，若这些例子都能归类，分类就「看起来完备」。
但这是循环论证——**例子是被用来构造分类的，当然落得进去**。

**怎么发现的**：一篇综述把优化技巧按「作用于成本链的哪个环节」分成
四类（省量/隐藏/均衡/少步），四个代表技巧各归一类，包括用户点名问的
那几个，看起来完整。直到被追问「还有其它的吗」，换一个维度
（按实现平面：数据面/执行面/控制面）重切，才发现至少五个维度
掉在四类之外，且**其中三个的幅度比四类里任何一个都大**——
2.65 倍的并行策略、93% 的调度上限、13% 的算子融合。

**为什么危险**：这类欠缺不会触发任何检查。E1 覆盖率 100%、
数值回溯全通过、审计全绿——因为语料里本来就没有那一层。
检查器只在已有语料上工作。

**怎么用**：给出一个分类后，**必须换至少一个正交维度重切一次**，
并明确回答「什么东西会掉在新切法里而旧切法里没有」。
答不出，就说明旧分类的完备性没有被验证过。
另一条更省力的检测：问「本领域从业者在生产里还会调什么」，
凡是答不出对应类别的项，都是缺口。

## 二、数字与产物

### 2.1 数字由脚本算，绝不手写

手写数字必然漂移：改了一处忘另一处，最后出现「表里 7 篇、正文 6 篇」。

**怎么发现的**：论文里 29 条主张，实际已是 36 条；另一处表格显示
`19 → 0`，因为数据文件缺列，审计静默计成 0。

**怎么用**：所有计数由一个 `analysis.json` 生成，正文、图、表都读它。
再加一道 P2 检查：图里的每个数必须能在其引用的主张里找到。

### 2.2 未登记 = 不被检查 = 出错没人报

用「手写清单」决定哪些图表进审计，清单本身就成了盲区。

**怎么发现的**：两次。`fig4`/`tab3` 未登记，导致数值回溯只覆盖一部分；
后来 `tab1` 又是一次，说明当时只修了那两张表，没修流程。

**怎么用**：清单应由扫描产物自动生成，而不是手工维护。
若暂时做不到，至少让「正文提到的图不在清单里」直接报错。

### 2.3 不要用「看起来合理的默认值」兜异常

```python
try:
    stats = read_actual_counts()
except Exception:
    stats = {"sources": 35, "evidence": 39}   # 恰好是对的
```

数字对不代表代码对。下次换个归档，默认值就写出错数据，
而警告只有一行，很容易被过滤掉。

**怎么用**：读不到就失败退出。宁可跑不动，不要产出错数字。

### 2.4 检查器是代码，不是真理

检查器会假警报，而**假警报比不检查更容易让人放弃检查**：
一个报错三次全是误报的检查器，第四次真报错时没人会看。

**怎么发现的**：`check_references.py` 连续三次假警报（拉平换行导致
URL 粘连、URL 与中文括号同行、页脚页码粘进最后一条 URL）。

**怎么用**：
- 给检查器写反例测试（故意弄错，必须报出来）
- 检查器的期望值必须算出来，不能写死

### 2.5 期望值写死，检查就变成了自我验证

```python
print(f"编号数：{len([n for n in nums if n <= 20])} 个")   # 20 是硬编码
```

35 条文献只报出 20 个编号，看起来像少了 15 条。
**把期望值写进检查，检查的就成了「PDF 是否等于我以为的样子」，
而不是「PDF 是否等于数据源」。**

**怎么用**：期望值一律从数据源长度算。

### 2.6 读错单位会让「文件被截断」成为幻觉

字节数与字符数在非 ASCII 文本上差 2–3 倍。把字节当字符，
会得出「文件被截断了」的错误结论，然后去修一个不存在的问题。

**怎么发现的**：某次插入后用 `len(s)` 与 `stat().st_size` 对比，
看到 13,363 → 8,634，据此判断「内容被我的切片截断」，
差点回滚重写。实际是前者为字节、后者为字符（中文占 3 字节），
文件完好无损。同一个错误在本项目里出现过**两次**。

**怎么用**：报文件大小时永远带单位（`8,634 字符 / 16,588 字节`）。
判「是否被截断」不要看总长度，要看**结构标记**——
小节数、标题数、关键锚点是否存在。长度是间接指标，结构是直接指标。

## 三、流程与交付

### 3.1 没接进构建的检查等于没有

写在 README 里的「请运行 X」，在第三次赶时间时就会被跳过。

**怎么发现的**：档案层校验只跑论文层三道，档案层从没跑过；
补进构建后立刻发现一个归档的 E1 覆盖率是 0。

**怎么用**：检查要么进 CI，要么进 `make`/单条命令，要么进 git hook。
「文档里写了」不算。

### 3.2 报告里的数字要与数据一起校验

报告写「447 条来源」、CSV 里其实是 20 条，这类漂移没有任何机制会发现。

**怎么发现的**：一次同步脚本带 `--slug` 过滤，把某归档的 447 条
改写成 20 条并写回了 README。

**怎么用**：报告头部的计数由脚本写入，再加一个测试核对它与 CSV 行数一致。

### 3.3 提交信息是有价值的资产

`fix(research): 那个数我数错了 - 22 不是 40` 这样的标题，
比任何事后总结都真实。它会告诉你系统真正在哪儿出错。

**怎么用**：把失败写进提交标题（而不是埋进 body）。
事后要写「经验文档」时，`git log` 就是最好的素材来源。

### 3.4 大文件放进 git 前先想清楚

一个 2.8 MB 的 Markdown 报告在网页上渲染会很慢甚至截断；
十几个 PDF 会让 clone 变重。

**怎么用**：产物分两类——**可重建的**（PDF、图、中间 JSON）考虑
不入库或放 release；**不可重建的**（原始抓取快照、人工判定记录）必须入库。

## 四、与 AI 协作

### 4.1 让 AI 做「可验证的错」，而不是「不可验证的对」

AI 能高效产出的东西，是**能被机器或人快速判错的**：
代码、表格、校验器、可复算的统计。

它不擅长的，是**无法判错**的东西：判断某篇论文是否重要、
某个方向是否值得投入。这类判断即使错了，也没有信号。

**怎么用**：把任务设计成「产出 + 判据」。没有判据的任务，
先花时间造判据。

### 4.2 明确禁止「差不多」

证据抽取若允许「意思对了就行」，就会得到一批看起来像证据、
实际零贡献的句子。

**怎么发现的**：18 条证据里 5 条是论文题名与作者行。它们**确实是
原文子串**，E1 全通过，但对论证毫无贡献——是抓取时正则命中了标题。

**怎么用**：抽取规则里加「实质性判据」（必须含实义动词/指标词），
并排除题名、作者、致谢区。

### 4.3 让 AI 记录「为什么没做成」

失败记录比成功记录更有信息量。要求它在放弃时写清楚
「试了什么、为什么不行」，这些是下一次的起点。

# 下篇：让系统自我改进的经验

这里说的「自我改进」是**流程层面**的：人根据踩坑改脚本与校验，
不是模型自己搜索策略。这是当前真实状态，见 EVOLUTION.md 第 6 节。

## 五、把坑变成机制

### 5.1 自我纠正的比例是一个健康指标

本仓库 320 个提交里 64 个（20.0%）是在推翻自己上一轮的结论。

**这个比例长期接近 0，更可能的解释不是严谨，而是没有检查。**

**怎么用**：给项目定一个「自我纠正比例」并观察它。太低要怀疑检查不足；
太高的同时产出停滞，要怀疑方向选错。

### 5.2 同一类错误出现两次，就该写规则

第一次是意外，第二次是流程缺陷，第三次还靠「下次注意」是自我欺骗。

### 5.3 规则要能自动判错，否则只是愿望

「写报告时要注意分母」不是规则，是愿望。
「比例类结论必须附一行『分母=X，来自 Y』，否则审计报错」才是规则。

**怎么用**：写规则时问一句「这条规则由哪行代码执行」。答不上来，
它就不是规则。

### 5.4 先做三态，再做通过率

在能自动判错之前，先保证「未校验」不被算成通过（见 1.6）。
顺序反了，会得到一条漂亮的、无意义的通过率曲线。

## 六、进化的节奏

### 6.1 密度最高的阶段是「读原始材料」

从二手描述转向一手材料时，之前基于摘要的结论会成批失效。
这是痛苦但最高产的阶段——本仓库密度最高的一天，
提交主题几乎全是 `fix(research): 那个……`。

**怎么用**：把「读一手材料」单独排期，不要指望顺带完成。
它一定会推翻你已有的东西。

### 6.2 一个错误假设可以让几十轮白做

提交主题里有「那条悬了十八轮的账，是方向错了」「一个持续 33 轮的
缺口其实是措辞过宽」。

**怎么用**：长任务要设「证伪检查点」——每隔若干轮，专门问一次
「如果这个前提是错的，会有什么现象」。而不是一路往前推。

### 6.3 机制化之后要回头验收覆盖率

加了 E1 规则，不等于它在每个归档上都执行了。
四个归档的实际覆盖率是 0% / 95% / 100% / 100%，
而 `[OK]` 这个结论在四个上是一样的。

**怎么用**：机制上线后，报**覆盖率**而不是报「已启用」。

## 七、三次没起作用的改进

只记成功会失真。这三次都加了机制，但没解决问题。

### 7.1 注册表式检查被绕过

清单手写 → 未登记的图表不进审计 → 两次踩同一个坑。
**根因没修**：应该让「正文提到但未登记」直接报错。

### 7.2 自动筛选在最后一公里无效

词频筛选能分清「讲 GPU」与「不讲 GPU」，分不清
「用 CUDA 加速这个计算」与「生成 CUDA kernel」——**主语不同，词频无解**。
最后一层只能人判，但判据要固化成可复查的数据。

### 7.3 静默回退

异常兜底用了「看起来合理的默认值」。数字对、代码错，
警告被过滤掉就完全看不出来。

**共同点**：三次都是**加了检查但没加「检查是否真的在检查」的检查**。

## 八、一页速查

若只记十条：

1. 「写了」/「配置了」/「跑了」是三件事
2. 分母要单独证明
3. 「没查」不能显示为「通过」
4. 数字由脚本算，不手写
5. 未登记 = 不被检查 = 出错没人报
6. 检查器是代码，要有反例测试，期望值要算出来
7. 没接进构建的检查等于没有
8. 引用存原文子串，判定前做渲染归一化
9. 同一类错误出现两次就该写规则，且规则要能自动判错
10. 不要用「看起来合理的默认值」兜异常
