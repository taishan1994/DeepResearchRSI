# RSI 自我进化记录

- **状态**：持续更新
- **记录区间**：2026-10-27 ～ 2026-11-04
- **数据来源**：`git log`（314 个提交）与 `docs/evolution-stats.json`
- **复现**：`python scripts/evolution_stats.py`

本文记录 DeepResearchRSI **实际发生了什么**，不是设计蓝图。凡属设想、
尚未实现的，一律标注「未实现」，见第 6 节。

---

## 0. 一句话概括

这个系统的「进化」不是模型权重更新，也不是策略搜索，
而是**把每一次踩到的坑变成一条机器可查的规则**：
在 5 天、314 个提交里，20.4% 的提交是在推翻自己上一轮的结论；
每推翻一次，就多一道校验或一条不变量，使同类错误无法再静默通过。

它进化的方向不是「更聪明」，而是**更容易被证明是错的**。

## 1. 先看数

| 指标 | 值 |
|---|---|
| 提交总数 | 314 |
| 活跃天数 | 5（10-27 ～ 11-04） |
| feat / fix | 173 / 98 |
| 自我纠正类提交 | 64（**20.4%**） |
| `research` 域提交 | 283（90%） |
| 真实代码量 | 6353 行（非空行；scripts 3977 + packages 1039 + tests 1337） |

「自我纠正类」的判定口径：提交主题含「撤回 / 推翻 / 错了 / 其实 /
更正 / 数错了 / 假象」等词。这是主题级统计，不等于实际出错次数
（一次错误可能只提交一次修复，也可能改三次才提交）。

**20.4% 这个比例是本仓库最值得看的一个数。** 它说明这套流程的主要
工作量不是「产出结论」，而是「发现结论不对」。若这个比例长期接近 0，
更可能的解释不是严谨，而是**没有检查**。

真实样例（原文照抄提交主题）：

```
fix(research): 撤回 8391269600 - 那个数不存在于任何文件
fix(research): 那个数我数错了 - 22 不是 40
fix(research): block_size 是 7 而不是 128 - 上一轮绝对量除以 18.29
fix(research): 撤回一条预言 - 捡到一个只给 Hopper 的开关
fix(research): 那条悬了十八轮的账，是方向错了
fix(research): 一个持续 33 轮的缺口其实是措辞过宽
```

注意「悬了十八轮」「持续 33 轮」——这类记录比数字更能说明问题：
**一个错误的假设可以让后续几十轮全部白做**，而它被发现时往往只值
一个提交。

## 2. 五个阶段

阶段划分依据是「当时在解决什么问题」，不是按时间硬切。
每个阶段写：触发了什么、加了什么机制、代价是什么。

### 阶段一：能产出，但不可审计（10-27 ～ 10-28 上午）

**起点**：`Initial commit` 之后，先做了目录结构、数据契约，
再拿一个真实问题（RTX PRO 6000 性能分析）跑通。

**做法**：检索 → 抽证据 → 写主张 → 出报告。证据存 `quote` 字段。

**触发的第一个问题**：ADR-0002 写于 10-27，明确要求
「`quote` 必须是原文子串」（不变量 E1）。但实现只有：

```python
if not quote:       报错（信息里写「不变量 E1」）
if not fetched_at:  报错（信息里写「不变量 S1」）
```

「非空」既不能证明 quote 是原文子串，也不能证明时间戳带时区。
错误信息里挂着不变量编号，**读起来像是验过了**。

**这一阶段的教训**：契约写了不等于实现了。错误信息里挂编号会
制造已校验的假象——这比不校验更危险，因为它会让人停止怀疑。

### 阶段二：读原始材料，发现结论站不住（10-28）

这一天是密度最高的一天，提交主题几乎全是
`fix(research): 那个……` 的句式。

**触发**：从「看摘要与文档」转向「读内核源码、读 CI 配置、读测试」。
一旦读到原始材料，之前基于二手描述得出的结论成批失效。

**反复出现的模式**：

| 原来的判断 | 实际 | 教训 |
|---|---|---|
| CUDA 有四个算子 | 代码从未被编译过 | 「写了」不等于「跑了」 |
| 覆盖 3069 个 blob | 实际只覆盖 198 个 | 分母错了，比例全错 |
| token 计数很复杂 | 就是一个除法 | 复杂感常来自没读完 |
| 某处是静默降级 | 十四处 `return false` 且零日志 | 个案要变成分母 |
| 某字段是独立值 | 一次减法锁定它就是 `output` 字段 | 恒等式比描述可信 |
| 某缺口存在 | 它是一个错误假设 | 缺口报告前先证伪假设 |

**这一阶段的教训**（后来固化成了规则）：

1. **「写了」/「配置了」/「跑了」是三件事。** 读到 `add_test` 不代表
   测试在跑；要找到调用点。这一条在 cuda-kernel-rl 里又验证过一次：
   Dr. Kernel 报告了 hacking check 的对照组，但那是图里的对比，
   不是消融实验。
2. **比例的分母要单独证明。** 「3069 个 blob 只覆盖 198 个」——3069
   是错的。分母错了，再精确的分子也没意义。
3. **恒等式优先于描述。** 若 `projected` 恒等于 `output`，这个事实
   比任何文档里对 `projected` 的描述都强。

**代价**：这一天几乎全部提交都是 fix。产出速度慢，
但每一条 fix 都让后续某一类错误变得可检。

### 阶段三：把教训变成不变量（10-28 ～ 10-29）

**触发**：fix 太多，靠人记不住。若「读源码发现结论错」只靠认真，
下一轮换个主题还会犯同样的错。

**做法**：把反复出现的错误类型抽象成机器可查的判定。

| 机制 | 触发它的具体错误 |
|---|---|
| E1 引文可回溯 | 报告里的数字找不到原文出处 |
| S1 时间戳带时区 | `fetched_at` 写 `2026-10-28`，无法判断时区 |
| D1 一 document_id 一 content_hash | 来源改版后旧结论被静默覆盖 |
| `sku` 列 | 「没说 SKU」只能写在散文里，机器看不见 |
| 五级证据阶梯 | 「读到文档」与「读到内核」被当成同级证据 |

**关键设计：不可校验必须与校验失败区分开。**

E1 需要文档快照才能比对。没有快照时，检查退化为「无法校验」。
第一版把这种情况记为通过，于是 `rtx-pro-6000`（3002 条证据、
零快照）安静地显示 `[OK]`——而它一条 E1 都没验过。

改为输出 `e1_unverifiable=3002` 并打印醒目警告。**「没查」不得显示为「通过」**。

这个区分后来在 cuda-kernel-rl 里救了一次：切换全文快照后，
14 条原本正确的引文全被判错，因为 LaTeXML 把 `26%` 渲染成 `$26\%$`。
若当时把「校验失败」直接当结论，会去改正确的证据。

**这一阶段的教训**：
- **一条规则只有能自动判错才有价值。** 写在文档里的「注意事项」不算。
- **不可校验 ≠ 通过。** 两者混同，检查就成了装饰。

### 阶段四：把检查器本身当成代码来测（10-29 ～ 11-01）

**触发**：检查器自己开始出错。

**典型**：`check_references.py` 连续三次假警报——
(1) 拉平换行导致 URL 与下一条编号粘连；(2) URL 与中文括号同行时
`startswith("http")` 漏掉 7 条；(3) 页脚页码 `7` 粘到最后一条 URL 上
变成 `abs/2502.105177`。

**为什么这件事很重要**：假警报比不检查更容易让人放弃检查。
一个报错三次全是误报的检查器，第四次真报错时没人会看。

**做法**：
1. **给检查器写反例测试。** 从 `sources.csv` 临时删一条，
   检查必须报出来；恢复后必须通过。
2. **检查器的期望值必须是算出来的，不能写死。**
   `check_references.py` 曾硬编码「应有 20 个编号」（继承自只有 20 条
   来源的归档），于是 35 条文献只报出 20 个，看起来像少了 15 条。
   把期望值写进检查，检查的就成了「PDF 是否等于我以为的样子」，
   而不是「PDF 是否等于 sources.csv」。
3. **把文字转换器当核心代码测。** `md_to_tex.py` 的 `inline()` 是整篇
   PDF 的唯一文字入口，写 11 个固定输入→输出用例（`tests_inline.py`）。

**这一阶段的教训**：**检查器是代码，不是真理。** 它需要有测试、
需要有反例验证，否则它会安静地给出错误的安全感。

### 阶段五：把流程本身接进构建（11-01 ～ 11-04）

**触发**：机制都有了，但要不要跑靠人记得。

**做法**：
- `scripts/audit_paper.py`：P1 引用闭合、P2 数值可回溯、P3 无凭空图表
- `scripts/sync_report_counts.py`：报告里的数字与 CSV 行数对齐
- `scripts/write_validation_line.py`：把校验结果写进 REPORT.md，
  且 `tests/test_schemas.py` 会核对它与实际 CSV 一致
- `scripts/commit_msg.py`：避免 PowerShell 写入 BOM 污染提交标题

**这一阶段的教训**：**没接进构建的检查等于没有。**
写在 README 里的「请运行 X」在第三次赶时间时就会被跳过。

## 3. 进化出来的七条判据

以下七条是这套系统真正学到的东西，每条都对应一次具体的翻车。
它们不是原则宣言，是**可操作的检查动作**。

### 判据一：「写了」/「配置了」/「跑了」是三件事

读到代码里有实现，不等于它在执行路径上；读到 `add_test`
不等于测试在跑。要找到调用点，或者找到它不在调用点上的证据。

### 判据二：分母要单独证明

任何比例先问分母从哪来。「3069 个 blob 覆盖 198 个」——3069 是错的。
分母错了，分子再准也没用。

### 判据三：不可校验 ≠ 通过

没有快照、没有原文、没有测试环境时，结论是「无法判定」，
必须显式记录并醒目提示。**把「没查」显示成「通过」是这套系统里
最危险的一种错误**，因为它会让人停止怀疑。

### 判据四：引用必须能回到原文子串

不是「大意相同」，是字面子串。允许截断，不允许改写、翻译后回填。
这条规则在跨语言材料上会疼，但疼是对的——它逼你保留原文。

### 判据五：数字由脚本算，不手写

论文里每一个数都从 `analysis.json` 读。手写数字必然漂移：
改了一处忘了另一处，最后出现「表里 7 篇、正文 6 篇」。
本仓库为此专门写了 P2 检查（数值可回溯到主张）。

### 判据六：检查器要有反例测试

一个从没报过错的检查器，可能只是没在查。要用「故意弄错」验证它真的会报。

### 判据七：同一类错误出现两次，就该写规则

第一次是意外，第二次是流程缺陷。第三次还靠人认真，是自我欺骗。

## 4. 三次「进化失败」

只记成功会失真。以下三次是加了机制但没起作用的。

### 失败一：注册表式的检查被绕过

`audit_paper.py` 的图表清单是 `paper.json` 里手写的 `FIGURES` /
`TABLES` 列表。未登记的图表不进审计。

后果：`fig4` 与 `tab3` 曾长期未登记，于是「数值回溯 19 条」实际只覆盖了
其中一部分。后来又发生一次（kernel-agent 的 `tab1`），说明当时只修了
那两张图表，**没修「新增图表必须登记」这个流程**。

**现状**：仍是手写清单。正确做法是让 `md_to_tex.py` 检测正文里出现的
图片文件名，若不在 `paper.json` 的 figures 里就直接报错。**未实现。**

### 失败二「自动筛选」在最后一公里无效

尝试用词频与正则从 180 篇候选里自动筛出相关论文。

- 一筛（关键词）：保留 44 篇，混进水下机器人巡检、控制理论、对话推理
- 二筛（要求 kernel 与「生成/优化」同句共现）：**一篇都没剔除**

原因不是词不够近，是**主语不同**：「我们用 CUDA 加速这个计算」与
「我们让智能体生成 CUDA kernel」在词汇上完全重叠，在语义上是两件事。

**教训**：自动筛选的价值在「把 180 缩到 44」，不在「把 44 缩到 26」。
承认这个边界比继续调正则有用。最后一层改人判，
判据固化成 `decide_agent.py` 里的 `(layer, 理由)` 表，可复查。

### 失败三：静默回退掩盖了错误

`write_validation_line.py` 从 `validate_research_dir()` 按属性取值，
抛 `AttributeError`，被 `except` 兜住后用**硬编码默认值**写入报告。
而默认值恰好是对的，于是数字正常、只有一行警告。

**教训**：异常兜底时不要用「看起来合理的默认值」。它在正确时掩盖错误，
在错误时生产错误数据——两头都坏。宁可直接失败。

## 5. 覆盖率作为进化指标

一个可量化的进化证据是 E1（引文可回溯）的实际覆盖率：

| 归档 | 证据数 | E1 已校验 | 覆盖率 |
|---|---|---|---|
| `rtx-pro-6000` | 3002 | 0 | **0%** |
| `cuda-kernel-gen` | 19 | 18 | 95% |
| `cuda-kernel-rl` | 37 | 37 | **100%** |
| `kernel-agent` | 39 | 39 | **100%** |

`rtx-pro-6000` 是第一个归档，做它时还没有快照机制，故 3002 条证据
一条都没验过。后三个归档逐步做到 100%。

**这张表比任何叙述都更能说明进化**：同一套契约，在四个归档上
的实际执行程度从 0 走到 100%。而 `[OK]` 这个结论在四个归档上是一样的——
这正是为什么要单独报覆盖率。

**未做**：给 `rtx-pro-6000` 补文档快照（属 `services/ingestion` 范围）。

## 6. 设计与实现的差距

写这份记录时核对了一件必须说清楚的事：

| 目录 | 状态 |
|---|---|
| `scripts/`（3873 行） | **真实运行** |
| `packages/`（1039 行） | **真实运行**（schema、不变量、provider） |
| `tests/`（1337 行） | **真实运行**（80 项） |
| `services/`（6 个子目录） | **只有 README**，无代码 |
| `apps/`（api、web） | **只有 README**，无代码 |

README 里描述的架构（orchestrator 状态机、evidence 冲突图、
evolution 灰度发布）是**设计意图**，当前由 `scripts/` 里的脚本
以简化方式承担。

**这不影响本文的事实陈述**（本文只描述 `scripts/` + `packages/`
实际做了什么），但它影响对整个仓库的判断，故必须写明。

`services/evolution/` 目录名里虽有 "evolution"，但它是空壳；
**本文记录的「自我进化」是流程层面的**——人根据踩坑经验改脚本与校验，
不是系统自动搜索策略。

## 7. 下一步

按「同一类错误出现两次就该写规则」的判据，目前有两条该做未做：

1. **图表登记由脚本强制**（失败一的收尾）。让 `md_to_tex.py`
   检测未登记的图片/表格并报错。
2. **给 `rtx-pro-6000` 补快照**，把 E1 覆盖率从 0 拉起来。

另有一件更根本的：

3. **「自我进化」目前靠人的记忆驱动。** 踩坑 → 写规则 → 接进构建，
   这个链条的第一步依赖人还记得那个坑。若要让它真正自动，
   需要从失败轨迹里自动提取模式。这是 `services/evolution/README.md`
   描述的东西，**尚未实现**。
