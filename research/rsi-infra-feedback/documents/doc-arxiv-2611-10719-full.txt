No Second Run: Does RSI Stop at Frontier Pre-training?
SII & Xinxu AI
Abstract
Pre-training is where every foundation model begins; bringing recursive
self-improvement (RSI) there would let AI improve the process that
creates AI, and could change how the entire industry builds foundation models.
Yet public RSI work has so far targeted only post-training, which starts from
an existing base model, runs trials costing GPU-hours, and returns verifiable
scores. RSI for pre-training breaks all three conditions at orders-of-magnitude higher
cost: a run consumes hundreds of thousands of GPU-hours over months and cannot
be repeated; its objective, post-training headroom, cannot be read off any
single score; and what must improve is not a model but the whole production & organization
system, from data pipelines and training infrastructure to the teams that run
them. To our knowledge, we are the first in the world to apply RSI to
an entire frontier pre-training run from scratch , and to report it in detail.
RSI does not stop at frontier pre-training, but it changes form: since no
end-to-end loop can close over a single unrepeatable run, we decompose the
pre-training loop into smaller loops that can, each repairing a step
the full run breaks.
The result is 801-30B-A3B-Base, † †
We present 801 (pronounced eight-oh-one), named after the classroom where it was built.
a 30B-A3B MoE model trained from scratch on 11.8T tokens in three months by a
newly formed team. We release it as a base model : full
post-training is left to a subsequent release, and the lightweight SFT
reported here (6B tokens, no RL) only probes post-training headroom. As a

1 Introduction
Recursive self-improvement (RSI), in which a system turns its own experience
and feedback into persistent changes that improve its capability, has moved
quickly from idea to practice. Agents now run the loop
propose → run → measure → update \textit{propose}\rightarrow\textit{run}\rightarrow\textit{measure}\rightarrow\textit{update}
on neural architectures ( Xu et al., 2026b ) , GPU kernels ( Yu et al., 2026 ; Fu et al., 2026a ) ,
agent harnesses ( Xia et al., 2026 ) , and, closest to model building, on
post-training itself ( NeoHorse Team et al., 2026 ; Rank et al., 2026 ; Huang et al., 2026 ) .
Where these loops touch pre-training, they do so through small-scale proxies:
data-curation and data-selection strategies validated on small models ( Mi et al., 2026 ; Xu et al., 2026c ; Meng et al., 2026 ) ,
or single-GPU training runs measured in minutes ( Karpathy, 2026 ; Guo et al., 2026 ) .
These settings share three conditions: they start from an existing base
model or a toy-scale one, each trial costs GPU-hours or less, and each
returns a verifiable score. Pre-training is where every foundation model
begins, and it satisfies none of the three. Bringing RSI there would let AI
improve the very process that creates AI; yet, to our knowledge, no public
work has attempted it on a full frontier pre-training run.
RSI for pre-training is not a harder instance of RSI for post-training but
a different regime (Table 1 ). First , it breaks
run . A single run consumes hundreds of thousands of GPU-hours over
months, and most projects can afford only one at full length. An ablation
that isolates a single cause costs GPU-weeks, so most hypotheses are never
tested end to end. Second , it breaks measure . The goal of
pre-training is not the highest score today but headroom for post-training.
A run that chases the metric can quietly borrow against post-training, for
example by annealing in supervised fine-tuning (SFT) data too early, or by
collapsing output diversity at the expense of the headroom that
reinforcement learning (RL) later relies on ( Yue et al., 2025 ) . Such an
objective cannot be read off any single score, and if even a crisply
defined benchmark gets overfit by self-improvement loops ( Xia et al., 2026 ) ,
a target this diffuse offers far more ways to be hacked than to be met.
Third , what must improve is not a model but a production system
and the organization that runs it. Before a single token is trained, the
data must be built: in our run, six pipelines with more than 30 processing
stages turned raw web pages, documents, and code into 1,053 data subsets.
The training stack evolved through more than 130 infrastructure code
versions and 106 hyperparameter fields. Behind these artifacts stands an
organization: data, infrastructure, training, and evaluation teams, each
holding a different part of the evidence, with the hardest problems falling
between them. A load-balance anomaly, for instance, surfaced in training
metrics but traced to an infrastructure change interacting with optimizer
settings (Section 3 ); no single team could have closed
that loop alone. Improving pre-training therefore means improving how the
organization divides work, shares evidence, and remembers what it has
learned. Post-training RSI starts where this
system ends: it presupposes a strong base model, which is exactly what the
system must produce.

Small-scale proxies and scaling laws seem to offer a fast loop, but a cheap
loop cannot answer every expensive question. Seemingly minor fitting choices
shift the fitted exponent ( Besiroglu et al., 2024 ; Weng, 2026 ) ,
small differences at fitting scale grow large at trillion-token scale, and a
ladder of proxy runs assumes that scale is the only thing
changing ( Weng, 2026 ) . Once a question couples architecture,
recipe, infrastructure, and multi-source data mixtures, the proxy study
needed to settle it becomes as expensive as the run it was meant to de-risk.
We therefore use our two pilot runs to surface and eliminate problems, not
to extrapolate scores.
If the end-to-end loop cannot be rerun, where do agents earn their place?
The run leaves behind a vast context: internal metrics, hyperparameter
changes, data-mixture edits, infrastructure diffs, and dozens of
evaluations on every intermediate checkpoint, far more than any team can
read, let alone remember. The characteristic waste in this regime is not a
bad experiment but re-investigating a question settled weeks earlier,
because no one linked the symptom to its class of cause. The bottleneck
thus shifts from compute to institutional memory: what was tried, what
failed and why, and which signals co-occurred. Agents earn their place by
recalling and attributing across evidence no human will finish reading,
and, wherever a fast signal can be built, by doing the work itself:
building data-pipeline components, crawling the web, and generating
agentic training data at a breadth no team could manage by hand.
Our answer to the question in the title is that RSI does not stop at
frontier pre-training, but it changes form. Since no end-to-end loop can
close over a single unrepeatable run, we decompose pre-training into smaller
loops that can close, each repairing a step the full run breaks.
Debugging loops relocate run onto the infrastructure and
data stacks, which can be rerun cheaply; the headroom loop repairs
measure for the run as a whole; and experience-to-metric
loops build a measure where none existed. A shared context
infrastructure serves as the organization’s memory: it integrates evidence
across teams and preserves negative results and their reasons, which is where the update step persists
and the recursion lives (Figure 2 ).
Figure 2: The standard RSI loop ( propose → run → measure → update \textit{propose}\rightarrow\textit{run}\rightarrow\textit{measure}\rightarrow\textit{update} )
does not close in frontier pre-training: a run takes months and cannot be
repeated, and today’s score does not reflect the headroom a checkpoint
leaves for post-training. We propose three types of loops, instantiated as six
practical loops. Debugging loops comprise the infra debugging loop and
the data debugging loop, which trace internal-metric and output anomalies
to their causes. The headroom loop is instantiated as the
recipe loop, using headroom measurements to guide the whole pre-training process.
Experience-to-metric loops comprise the classifier development loop,
the site discovery loop, and the crawl-coverage loop, turning
experience-based judgment into measurable feedback. All six loops share
a context infrastructure that integrates evidence across teams at scale.
We built these loops while training 801-30B-A3B, a 30B-A3B
Mixture-of-Experts (MoE) ( Shazeer et al., 2017 ) model trained from scratch
on 11.8T tokens in three months by a newly formed team. To our knowledge,
this is the first public account of RSI applied to an entire frontier
pre-training run. Our contributions are:
•
(a) Debugging loops (Section 3 ).
An infra debugging loop and a data debugging loop , driven by
internal-metric and output anomalies, respectively. Across two pilots
(stopped at 1T and 3T tokens) and the main run, agents localized causes
spanning infrastructure, data, and recipe, from a load-balance penalty
interacting with optimizer state to low-diversity synthetic data, and
resolved five cross-stack diagnoses in about one month. Together with data
and recipe revisions, these fixes raised the mean score over 22 benchmarks
(Appendix B ) at a matched 1T-token budget
from 47.78 (initial pilot) to 51.96 (revised pilot) to 56.83 (main run).
•
(b) A headroom loop (Section 4 ). Because base
scores do not preserve post-training rankings, we judge checkpoints by what
they are worth after adaptation, using tiny-SFT, a learning aptitude
curve, and a max-over-protocols estimate of the capability ceiling. These
measurements separate apparent stagnation in base evaluation from
continued gains after adaptation.
•
(c) Experience-to-metric loops (Section 5 ).
Classifier development, site discovery, and crawl coverage, in which agents
turn judgment once made by feel into recorded, quantitatively evaluated
workflows. We built six data pipelines from scratch this way.
•
(d) Agentic data at pre-training scale (Section 6 ).
Agents cross from consuming training to producing it: 220K executable pull
requests rolled out across nine harnesses yielded more than 100B tokens of
verified agentic trajectories (134B agentic tokens in total), used in the
long-context stage of pre-training.
What we release and how to compare it.
We release 801-30B-A3B-Base as a base model. Full post-training is
left to a subsequent release; the lightweight SFT reported here (6B tokens,
no RL) serves only to probe post-training headroom. We therefore compare at
three levels, from the fairest to the least favorable to us
(Section 8 ). (1) Base against base : 801-30B-A3B
outperforms Qwen3-30B-A3B ( Yang et al., 2025a ) and
Nemotron-3.5-Lightning-30B-A3B ( NVIDIA et al., 2026 ) ,
trailing only the larger Qwen3.5-35B-A3B ( Qwen Team, 2026a ) .
(2) Identical SFT : when every base model is fine-tuned on the same
SFT data, it keeps this position. (3) Lightweight SFT against full
post-training : even so, it achieves the highest average across four
agentic benchmarks among the fully post-trained models we compare,
including Qwen3.6-35B-A3B ( Qwen Team, 2026b ) . The third comparison pits
a few billion SFT tokens against complete vendor post-training pipelines;
we report it as a reference point for headroom, not as a like-for-like
comparison. We will open-source 801-30B-A3B-Base and the lightweight SFT
data, a ready-made resource for evaluating the post-training headroom of
base models, at https://github.com/GAIR-NLP/801-30B .
2 Adapting RSI to Frontier Pre-Training
Recursive self-improvement (RSI) is the idea that a system turns its own
experience and feedback into persistent changes that improve its capability
and, in the strongest form, the process of improvement itself.
The engine behind it is a closed loop, exemplified by
AlphaEvolve ( Novikov et al., 2025 ) and
ASI-Evolve ( Xu et al., 2026c ) . We write that loop as propose → run → measure → update \textit{propose}\rightarrow\textit{run}\rightarrow\textit{measure}\rightarrow\textit{update} and use it as the operational definition of RSI throughout this report. In this report, the improving system is the pre-training project itself, comprising its agents, researchers, and infrastructure, rather than the model being trained.
The four steps are worth defining precisely. Propose
forms a candidate change or hypothesis, the role played by the generator in
generate-critique-revise schemes ( Madaan et al., 2023 ) and by the proposer in proposer-solver
self-play ( Zhao et al., 2025 ) . Run realizes that candidate to produce evidence, by training,
rolling out, or executing it. Measure scores the evidence against a
signal that stands in for human judgment or the desired target. Chen et al. (2026) arrange
candidate signals into a verification hierarchy, from formal verifiers at the
strong end to a model’s intrinsic self-assessment at the weak end.
Update folds the outcome back into a persistent change, keeping what
scored higher and discarding the rest, and in the recursive case it also
revises the loop machinery that produced the change. This persistence is what makes the loop recursive rather than a one-off search.
Two preconditions decide whether this loop improves anything. The first is
cheap, repeatable iteration: gains compound only when a trial is cheap enough
that run and update can cycle many times. The second is a
reliable signal at measure , aligned with the true goal. Without an
external signal there is no reliable improvement
;
with a weak or misaligned one, the loop degenerates through self-confirming
errors, model and diversity collapse ( Shumailov et al., 2024 ) , or frame
lock-in on a well-posed but wrong objective ( Chen et al., 2026 ) .
As argued in Section 1 , frontier pre-training breaks both
preconditions: a full-length run cannot be repeated, and its true objective,
post-training headroom, is too diffuse to serve as a trustworthy
measure . The system that must improve is, moreover, an organization
rather than a model. The standard end-to-end loop therefore does not transfer
to this regime. We keep the loop, but change where it closes.

Three types of loops.
Rather than casting pre-training as one score-driven loop, we close three
types of smaller loops around it, with six concrete instances
(Figure 2 ). Table 2 shows how each
type instantiates the four steps.
•
Debugging loops relocate run onto the infrastructure and data-pipeline stacks, where a diagnosis can be rerun cheaply. They are driven by anomalies rather than by a score to maximize: measure asks whether the anomaly disappears, and each ruled-out cause is recorded as a negative result. The infra debugging loop traces unusual internal metrics to infrastructure code or training-recipe settings, and the data debugging loop traces unusual output patterns to a specific data source or processing stage (Section 3 ).
•
The headroom loop repairs measure for the run as a whole. Its signal is post-training headroom, estimated through tiny-SFT, learning aptitude, and max-over-protocols evaluation rather than read off a base-model score. It is instantiated as the recipe loop , which uses these measurements to revise the recipe from the two pilots, stopped at 1T and 3T tokens, to main pre-training, and to monitor progress within the main run (Section 4 ). Because its run is the costly run itself, it closes only a few times per project.
•
Experience-to-metric loops build a measure where none existed. Steps such as building data-pipeline components and acquiring web data were historically tuned by hand; we give each an explicit evaluation, such as a task-specific evaluation set or an SEO page-count estimate, so that revisions can be compared. This type is instantiated as the classifier development loop , the site discovery loop , and the crawl-coverage loop (Section 5 ).
Context infrastructure.
These loops operate on different parts of pre-training, but all require
evidence that spans teams: an anomaly may connect a model’s output to a
data-processing decision made weeks earlier, headroom measurements must be
read alongside recipes and checkpoint histories, and data workflows must
retain the evaluations behind each revision. We built a context
infrastructure to integrate this evidence (internal metrics such as per-layer
loss, per-module gradient norms, and expert load-balance statistics, together
with hyperparameter changes, data-mixture edits, infrastructure diffs, and
checkpoint evaluations), produced by agents and by researchers who separately
own the data, infrastructure, training, and evaluation stacks, at a scale no
team can read unaided (Table 1 ). It records not only what
was tried but what failed and why, so that negative results become persistent
knowledge. This is where the update step persists and where the
recursion in our loops lives: each new proposal starts from what earlier
iterations have ruled out, and agents direct their effort to the next
unresolved bottleneck instead of rediscovering old ones.
From pilots to main pre-training.
Together, these loops supported revisions of the data and training recipe across two pilots and main pre-training (Figure 4 ). The initial pilot stopped at 1T tokens, the revised pilot at 3T, and the main run used approximately 11.8T tokens; the figure shows main pre-training through Stage1-1 at 7T. These revisions brought together debugging, headroom assessment, and quantitatively evaluated data workflows.
At 1T tokens the mean score over the 22 common benchmarks rises from
47.78 to 51.96 to 56.83, and at 3T tokens main pre-training reaches 59.94
against the revised pilot’s 56.48. Because data and recipe changed together, these gains
reflect the combined iterations supported by the three types of loops rather
than any single fix.
The following sections describe how each type contributed to this process.

3 Debugging Loops
This section shows the two debugging loops operating on the context
infrastructure as we introduced in Section 2 .
(1) The infra debugging loop traces unusual internal metrics to
infrastructure code or training-recipe settings.
(2) The data debugging loop traces unusual output patterns to a
specific data source or processing stage
(Figure 5 ; Table 2 maps both loops
to the four RSI steps).
Unlike conventional RSI approaches, which improve performance by
repeatedly training and comparing candidate models, these loops operate
within a single pre-training run. Rather than restarting training to
evaluate new candidate models, they continuously identify, attribute,
and eliminate problems as training progresses, improving the ongoing
run itself.
We conclude with the five cross-stack diagnoses produced by these
loops (Table 3 ).

3.1 Infra Debugging Loop
The infra debugging loop uses internal training metrics as the
starting point for identifying and resolving anomalies during
pre-training. By linking these signals to infrastructure code
and training-recipe configurations through the context
infrastructure, agents can trace unexpected model behavior
to its underlying causes, propose targeted fixes, and verify
their effects within the ongoing training run. We illustrate
this process through the anomalies observed in the two pilot
runs, following four steps: detect, attribute, fix, and verify.
Detect.
During the two pilot runs, agents scanning internal metrics through the context infrastructure identified two contrasting patterns in MoE load-balancing indicators (Figure 6 ).
In the initial pilot, both aggregate and layer-wise MaxVio ( Wang et al., 2024a ) declined to low levels under a strong balancing penalty, raising concerns about potential over-balancing. The revised pilot revealed a different pattern: layers 15 and 18 developed large, persistent MaxVio violations, while the aggregate remained within a typical range. This discrepancy showed that aggregate monitoring alone could obscure severe layer-specific imbalance. Layer 48, the final layer, was also elevated, but we do not treat this alone as evidence of failure, since its function is closely tied to the output space. Together, these two patterns illustrate why monitoring MoE load balancing requires examining both aggregate trends and layer-specific deviations.
Attribute.
To identify the source of these anomalies, agents used the context infrastructure to correlate metric trajectories with infrastructure code commits and optimizer configurations. By searching across more than 130 infrastructure code versions and 106 hyperparameter fields, they narrowed the cause to a change in the load-balance penalty implementation and its interaction with optimizer state updates for certain parameter groups.
This process established an attribution chain from training stagnation to internal-metric anomalies, and from those anomalies to specific infrastructure and configuration changes. Rather than treating unusual metrics as isolated symptoms, agents traced them across the training stack to identify their underlying causes.
Fix.
Based on this diagnosis, we first revised the pilot configuration by lowering the load-balancing ( Fedus et al., 2022 ) coefficient from 10 − 2 10^{-2} to 10 − 4 10^{-4} , reducing the learning rate from 2.7 × 10 − 3 2.7\times 10^{-3} to 5 × 10 − 4 5\times 10^{-4} , and switching the optimizer for router parameters from Muon ( Jordan et al., 2024 ; Liu et al., 2025 ) to AdamW ( Loshchilov and Hutter, 2019 ) . These settings were carried into main pre-training, with two further adjustments: computing the load-balance loss over the global batch rather than per micro-batch ( Qiu et al., 2025 ) , and excluding normalization and bias parameters from weight decay.
Because several factors changed together, the comparison does not isolate the contribution of any single adjustment. Together, these changes constituted the revised training configuration used in main pre-training.

Verify.
Subsequent training shows that the revised configuration mitigates layer-wise load imbalance and suggests that internal metrics may reveal potential training problems earlier than downstream evaluation alone. (1) First, the revised configuration substantially mitigated the layer-specific imbalance observed in the pilot. At a matched training budget of 3T tokens, layer-15 MaxVio had already exceeded 14 in the revised pilot, whereas it was around 5 in main pre-training, with pronounced escalation occurring only at a later stage (Figure 7 ). This indicates that the revised configuration substantially alleviated the earlier anomaly, although it did not eliminate it entirely.
(2) Second, the internal metrics provided a more granular view of training dynamics than downstream evaluation alone. During main pre-training, layer-15 MaxVio rose sharply over approximately 2.2–6T tokens (the shaded interval in Figure 7 ). Over the same interval, downstream evaluation gains gradually diminished. After approximately 6T tokens, layer-15 MaxVio remained at a high plateau, while downstream evaluation gains within Stage1-1 had largely flattened.
This temporal correspondence suggests a possible association between layer-wise load imbalance and training saturation. Layer-wise MaxVio rises well before downstream performance plateaus, indicating that internal metrics can flag potential training problems while evaluation scores are still improving. Monitoring these metrics alongside downstream evaluations may therefore enable earlier investigation and intervention.
Finally, the context infrastructure allows these diagnostic experiences to persist across iterations. Because the previous diagnosis and its supporting evidence were preserved, the recurrence of similar anomalies could be anticipated rather than rediscovered from scratch. This allowed us to use the early MaxVio signal as a basis for further investigation, rather than waiting until downstream evaluation gains had flattened.
3.2 Data Debugging Loop
Figure 8: Diagnosing bad patterns in model outputs. Top : three representative output patterns, a credential leak with a verbatim-repeated config block, a jump into a fixed “Does this sentence make sense?” QA template, and a self-spawning chain of near-identical word problems. Bottom : the eight-step
loop that traces each pattern back to a data-pipeline defect. Agents handle detection, tracing, and inspection at scale, humans set triage priority and approve the fix.
During the two pilots, we continuously monitored the output behavior
of the trained model. Agents identified recurring patterns in the
model’s responses to greetings and common questions, which are
indicative of repetitive, low-diversity, or insufficiently cleaned
training data. They extracted these anomalous patterns and searched
the data pipeline for matching signatures at scale.
Anomalous patterns.
Figure 8 illustrates three representative
patterns observed in model outputs.
(1) First, credential leakage and repetition : given the prompt
deepseek , the model emits a secret resembling an API key,
followed by repeated copies of an identical proxy-configuration
block, continuing until the generation length limit is reached.
(2) Second, jumping to a fixed QA template : when given a natural
request for a dinner recommendation, the model fails to answer the
question and instead switches to a fixed “Does this sentence make
sense?” multiple-choice template, proceeding to solve this
invented task.
(3) Third, self-spawning repetitions : given only the marker
**New Example:** , the model generates an unbounded sequence
of nearly identical division word problems, each following the same
four-step solution scaffold.
Automated diagnosis process.
The bottom of Figure 8 illustrates how agents
trace these anomalous patterns back to specific data-pipeline
defects. The eight-step process can be organized into three stages.
(1) The first stage is detection and pattern extraction .
Agents identify anomalies in model-generated samples or evaluation
results and classify the corresponding cases. Based on the
identified patterns, agents write detectors and perform large-scale
matching across all 1,053 data subsets to identify those potentially
containing the corresponding anomalies.
(2) The second stage is attribution and localization .
After candidate data subsets have been identified, humans determine
the priority of investigation. Agents then trace these subsets to
their data pipelines (six in total) and inspect the
intermediate data produced at more than 30 processing stages across
these pipelines, ultimately locating the specific data sources and
processing stages responsible for the anomalies.
(3) The final stage is resolution and verification .
Once the source of an anomaly has been identified, agents propose fixes to the data or pipeline. Humans decide whether
to approve their execution. Approved fixes are applied to the
relevant processing stages, followed by model re-evaluation to
verify their effectiveness; rejected proposals are returned for
revision.
Throughout this process, agents handle large-scale anomaly
detection, data tracing, and stage-by-stage inspection, while
humans retain control over two key decision points: investigation
prioritization and fix approval. This division of labor makes
large-scale investigations systematic and practical, beyond what
could reasonably be accomplished through manual inspection alone.
Root cause attribution and fixes.
Through this process, the three anomalous patterns were traced to
three distinct data-pipeline defects.
(1) First, the credential-leakage and repetition case was traced to
insufficiently cleaned configuration files in the code corpus.
These files contained sensitive information and repetitive
configuration content that had entered the training data and
subsequently surfaced in model generations. We addressed this
issue by fixing the corresponding data-processing stage to remove
such inadequately cleaned content.
(2) Second, the fixed-QA-template case was traced to insufficient
filtering of synthetic data in a subset of an open-source QA corpus.
This subset contained a large volume of
“Does this sentence make sense?” questions. We strengthened
synthetic-data filtering at the corresponding stage to reduce the
presence of such fixed-template examples in the training data.
(3) Finally, the self-spawning case was traced to a synthetic-data
pipeline whose prompt design lacked sufficient diversity, resulting
in highly similar generated examples. We revised the corresponding
prompt design to improve the diversity of the synthetic data.
For all three cases, we modified the corresponding data-pipeline
stages and re-evaluated the model after applying the fixes to
verify their effectiveness.
3.3 Accumulated Diagnoses
The two debugging loops described above illustrate how agents
identify anomalies in model behavior and trace them back to
underlying issues in the infrastructure, training recipe, and
data pipeline. However, these are only representative examples
of a broader effort to diagnose and resolve problems throughout
the training process.
Across the two pilots and main pre-training, we applied the
same approach to systematically investigate issues across
different parts of the training system. Many of these issues
could not be attributed to a single component. Diagnosing them

4 Headroom Loop
The goal of pre-training is not to maximize today’s score but to leave the
greatest headroom for post-training. Measuring this headroom can supply the signal
for the headroom loop. We first describe three complementary measurements
(Section 4.1 ), then show what they revealed that base
evaluation did not (Section 4.1 ), and finally how the
recipe loop used them (Section 4.2 ).
4.1 Measuring Post-Training Headroom
We use three measures to assess post-training
headroom: Tiny-SFT, learning aptitude, and max-over-protocols
evaluation. Together, they capture three aspects of a model’s
potential: its performance after limited post-training, its
efficiency in learning from additional data, and the capabilities
it can demonstrate under evaluation protocols.

Tiny-SFT.
Base-model evaluation alone does not fully capture a model’s
potential after post-training. We therefore apply a small SFT
budget to each evaluated pre-training checkpoint and directly
measure its performance on benchmarks designed for post-trained
models. The resulting scores approximate how the checkpoint
would perform after a representative post-training phase,
providing a more realistic measure of its downstream potential.
The SFT corpus spans multiple task categories to approximate
the diversity of actual post-training workflows
(Figure 9 ).
We note that SFT was not repeated with multiple random seeds,
so small differences between adjacent checkpoints should
be interpreted with caution.
In our experiments, Tiny-SFT helped us identify two
interesting patterns that are not readily apparent from
base-model evaluation alone:

therefore compare their trends within each evaluation

on base-model evaluation could lead to premature
decisions to stop training or unnecessary changes
to the training recipe.
(2) Ranking disagreement.
We also found that the relative ranking of checkpoints

These results show that base-model scores alone cannot

across checkpoints.

Learning aptitude.
A model’s initial performance does not necessarily reflect how
effectively it can learn from additional post-training data.
We therefore measure its learning aptitude , which captures
how efficiently a model improves as the post-training data
budget increases.
To measure learning aptitude, we select a specific domain or
task family and fine-tune different base models using the same
domain-specific SFT data. We evaluate a sequence of intermediate
checkpoints throughout training to track how each model’s
performance changes as it sees more data. This allows us to fit
a learning curve and measure how efficiently the model learns
from additional data. For most models, scores grow approximately linearly with the
logarithm of the post-training data budget. We therefore fit
a log-linear learning curve for each base model m m
(Figure 12 ):

(1)
where s m ​ ( N ) s_{m}(N) is the downstream score after N N units of
post-training data (in practice, SFT steps at a fixed batch
size), and N 0 N_{0} is the data budget of the first evaluated
SFT checkpoint. The intercept b m b_{m} is the score at this
first checkpoint, representing the model’s initial performance
in the domain. The slope k m k_{m} measures the score gain for
every tenfold increase in post-training data, capturing how
efficiently the model learns from additional data. We estimate
both parameters by ordinary least squares over all SFT
checkpoints, excluding the untuned base model.
Neither parameter alone captures a model’s learning
aptitude. A model with a high initial score but a shallow
learning curve starts strong but gains little from
additional data. In contrast, a model with a lower initial
score but a steeper learning curve may eventually surpass it
as the data budget increases. We therefore consider both
parameters together and estimate the amount of post-training
data required for model m m to reach a target score s ∗ s^{*} :
N m ∗ ​ ( s ∗ ) = N 0 ⋅ 10 ( s ∗ − b m ) / k m , N_{m}^{*}(s^{*})=N_{0}\cdot 10^{(s^{*}-b_{m})/k_{m}},
(2)
We then compare this data requirement with that of a baseline model, using the ratio N base ∗ / N m ∗ N^{*}_{\text{base}}/N^{*}_{m} to measure data savings. A larger ratio means that the model requires less post-training data to reach the same target performance.
In this work, we use learning aptitude to compare different
models rather than different checkpoints within a single
training run. As shown in Section 8 ,
a model with a lower initial score but higher learning
aptitude can eventually surpass a model with a higher initial
score after sufficient fine-tuning. Applying this measure
to checkpoint selection within a single training run is
a natural direction for future work.
Max-over-protocols evaluation.
A model’s evaluation score does not always fully reflect its
acquired capabilities, as the extent to which these capabilities
are demonstrated can depend on the evaluation protocol. The same
benchmark may yield very different scores under perplexity
scoring, few-shot prompting, and zero-shot prompting
(Figure 13(a) ; protocol definitions in
Appendix C ). Moreover, the relative
performance of these protocols can change across pre-training
checkpoints, as illustrated by HumanEval in
Figure 13(b) .
A single evaluation protocol may therefore underestimate model’s capability. To obtain a more complete picture, we
evaluate each checkpoint under all available protocols and
take the highest score for each benchmark. Our goal is to
measure the capabilities a model can demonstrate, rather
than how well it adapts to a particular evaluation format.
Taking the maximum across protocols provides a more complete
estimate of the model’s capability ceiling. For cross-model
comparisons in Section 8 , we follow the
evaluation protocols specified in that section.

4.2 The Recipe Loop
The recipe loop brings post-training headroom
measurements into the pre-training process, using them as
feedback to assess training progress, guide recipe
adjustments, and inform subsequent iterations. The two
pilots, stopped at 1T and 3T tokens, and the subsequent
main pre-training run form the sequence of iterations
in this loop (Figure 4 ).
Throughout this process, we use headroom measurements to
track how the model’s post-training potential evolves
across training stages and feed the results back into
the pre-training recipe. Rather than focusing solely
on current base-model scores, we consider post-training
performance, learning efficiency, and the capabilities
the model can demonstrate under different evaluation
protocols. This helps us judge whether pre-training is
still accumulating useful capabilities and whether
the current recipe needs further adjustment.
Based on the issues identified through earlier debugging,
we continue to refine the infrastructure and training
configurations while developing the training data.
In particular, main pre-training introduced new QA data
and revised the proportions and sampling weights of web,
code, mathematics, books, and papers.
The central idea is that pre-training progress should
not be judged solely by current base-model scores, but
also by whether the model continues to accumulate
capabilities that can be further developed through
post-training. Even when base-model evaluation appears
to plateau, pre-training may still be making meaningful
progress if post-training headroom continues to grow.
5 Experience-to-Metric Loops
Many data-processing decisions in pre-training have
traditionally relied on expert experience, such as how
to clean and filter data, and how to judge whether a
processing strategy works well. We turn these
experience-driven tasks into standardized workflows
with explicit evaluation metrics. This allows agents
to analyze errors, revise their approaches, compare
alternatives, and improve their performance through
repeated iterations.
We call this the Experience-to-Metric Loop , and
apply it to three tasks: classifier development,
site discovery, and crawl-coverage optimization.
All three follow the same principle: turn human
experience into measurable tasks, let agents carry
out and improve the work, and use evaluation results
to guide the next iteration.
5.1 Classifier Development Loop

Left : a human defines the classification task (1); a strong model samples data and annotates an evaluation set (2); an agent analyzes cases and tunes the labeling prompt (3); the strong model uses that prompt to label training data (4); a compact classifier is distilled from these labels (5) and evaluated (6). Earlier work on Data Darwinism provides a
framework for the first question. It introduces a
ten-level taxonomy (L0–L9) that organizes data
processing operations, from data acquisition and
format normalization to filtering, model-driven
refinement, and synthesis ( Qin et al., 2026a ) .
Following its use in daVinci-LLM ( Qin et al., 2026b ) ,
we use this framework to guide pipeline design.
For example, OCR belongs to format normalization
(L1), rule-based and model-based filtering correspond
to L2–L3, and refinement for cleaning or
repairing content falls under L4. This taxonomy
helps us define what each component should do before
choosing its model, prompt, or implementation.
DataEvolve explores a complementary question: how data-curation strategies
can improve through repeated evaluation and diagnostic
feedback ( Mi et al., 2026 ) . Inspired by this approach, we develop
classifiers, filters, OCR models, and rewriters through a shared evaluation
workflow.Data Darwinism
guides the choice of processing operations, while
the evaluation loop helps determine whether a
particular implementation performs its intended
task well. Figure 14 illustrates this process for
classifiers, with three stages (six steps in the figure).
Step 1: Define the task and construct an
evaluation set.
A researcher specifies what the classifier
should do. A strong model then annotates
representative samples to create a reference
evaluation set. This establishes quality
criteria and provides a common basis for comparing prompts, models, and processing rules.
Since the reference labels come from a strong model,
the evaluation measures agreement with that model
rather than with human judgment.
Step 2: Analyze errors and improve the component.
Agents analyze hundreds to thousands of examples
in parallel, identify recurring error patterns,
and use these findings to revise prompts, compare
models, or adjust processing rules. Each revision
is evaluated against the same task definition and
evaluation set, allowing us to determine whether
the changes actually improve performance.
Step 3: Validate and deploy.
The revised component is evaluated before deployment. For a classifier, the
result can be used as a tuned labeling prompt or distilled into a
smaller model using training data labeled by the strong model. The distilled
classifier is evaluated and the loop continues revisions improve
its performance. The evaluation catches regressions: in
Figure 14 , all three classifiers lost accuracy at
v2 before improving at v3.
In under three months, we built six data pipelines, with
agents contributing 36 model-selection decisions as well as prompt
optimization and classifier construction.
5.2 Web Acquisition: Site Discovery and Crawl-Coverage Loops
Figure 15: Structure-aware web data acquisition. A human requirement seeds an
agent-driven pipeline with two loops. Loop 1 (site discovery) expands and verifies related
sites through the web’s link structure. Loop 2 (crawl coverage) crawls each confirmed site to
a coverage target informed by its SEO page estimate. Links, search indexes, and
robots directives are treated as structured signals rather than discarded.
The public web is a major source of pre-training data, but
systematically finding high-quality sources and collecting
their content as completely as possible remain challenging.
A common approach starts from seed documents, uses a
classifier to retrieve relevant pages, and identifies the
domains where these pages are concentrated ( Shao et al., 2024 ) .
However, two questions remain: how can we continuously discover
more valuable sites, and how can we tell whether we have
collected enough data from each site?
We address these questions with two connected agent-driven
loops: the site discovery loop , which finds high-quality data sources, and the crawl-coverage loop ,
which aims to collect their content as completely as possible.
Both use information from search-engine-optimization (SEO)
tools, which provide related-site information and estimates
of indexed page counts, as signals to guide discovery and
measure crawl coverage. Figure 15 shows the pipeline.
Loop1: Site Discovery Loop.
The goal of site discovery is to expand a small set of high-quality seed sites into a broader collection
of relevant data sources. We use SEO tools to identify
candidate sites related to the seeds through the web’s
link structure. An agent then visits each candidate to
check its relevance and quality, adding verified sites
to the seed set for the next round of discovery.
We measure the effectiveness of each round by its
verified yield , the number of discovered
sites that pass verification. Each round’s verified
sites become seeds for the next round, allowing discovery
to expand iteratively. The process stops when a round
produces no new qualified sites. This turns the
experience-based decision of where to look next into
a measurable and repeatable discovery process.
Loop2: Crawl-Coverage Loop.
Once valuable sites have been identified, the next
task is to collect their content as completely as
possible. For each confirmed site, an agent writes
and runs a crawler, then compares the number of
retrieved pages with the page-count estimate provided
by SEO tools.
We use the coverage ratio as the evaluation
metric, defined as the number of retrieved pages
divided by the estimated total number of pages:
Coverage Ratio = Retrieved Pages Estimated Pages \text{Coverage Ratio}=\frac{\text{Retrieved Pages}}{\text{Estimated Pages}}
Although SEO page counts are estimates, they provide
a quantitative reference for assessing crawl coverage.
The agent compares the retrieved count with this
estimate, investigates potential gaps, revises the
crawler, and runs it again to measure the resulting
coverage. In this way, crawling becomes an iterative
process driven by measurable coverage rather than
an informal judgment of when a site is sufficiently
crawled.
Closing the loops.
The site discovery and crawl-coverage loops address
two complementary challenges in web data acquisition:
where to find more valuable data sources and how to
collect their content as completely as possible.
Together with the classifier development loop, they
follow the same principle: turn experience-driven
tasks into workflows with explicit evaluation metrics,
so that agents can execute the work, assess the results,
and improve their approaches through repeated
iterations. Specifically, classifier development
uses task-specific evaluation scores, site discovery
uses the verified yield of each round, and web crawling
uses the coverage ratio.
The key is to give tasks that once relied on expert
judgment explicit objectives and evaluation procedures.
Agents can then use feedback to determine how well
a task has been completed and what to improve next.
This turns experience-based decisions into systematic
and repeatable processes, making pre-training more
scientific one component at a time.
6 Scaling Agentic Data into Pre-Training
Agentic data, consisting of trajectories generated by agents
solving real-world tasks with verifiable outcomes, has proven
effective in post-training ( Pan et al., 2025 ; Yang et al., 2025b ) .
Real-world software development provides a rich source of
such tasks and offers a new opportunity for pre-training.
Our goal is to scale this data source to hundreds of billions
of tokens while preserving task diversity and data quality.
However, achieving this scale requires more than conventional
data-processing pipelines. Real-world software tasks are diverse and involve complex task construction, execution environments, testing, and integration across agent harnesses. We argue that extensive
use of agents is a necessary condition for scaling agentic
data into pre-training . The main bottleneck is not
generating a handful of high-quality examples, but
systematically transforming diverse real-world software
development activities into executable, verifiable, and
scalable training data.

6.1 Why Agentic Data Requires Agents
Complex task construction and validation.
Real software development offers a rich source of tasks
for agentic data. Recent work has explored several
directions: making development tasks executable through
automated environment and evaluation-script construction
( Fu et al., 2026b ) , preserving development context
and execution feedback in mid-training trajectories
( Zeng et al., 2026 ) , and connecting related PRs into longer task chains
( Jiang et al., 2026 ) .
Scaling this data source to pre-training requires handling
the full diversity of real-world development activity.
This includes both PRs with clear task definitions and
well-maintained tests ( Jimenez et al., 2024 ; Pan et al., 2025 ; Badertdinov et al., 2025 ) , and those with incomplete descriptions,
implicit requirements, or multiple work items bundled
together.
For each PR, the pipeline must construct three mutually
consistent components: a reproducible execution
environment, an instruction specifying what the agent
is expected to do, and tests and evaluation scripts
that verify whether the task requirements are met.
These components must be developed together. For example,
a repository’s CI may inject environment variables that
were omitted from the constructed environment, causing
the evaluation to fail for reasons unrelated to the code
change. In another case, a test may require a function
with a specific name, while the instruction describes
only the desired behavior, causing a valid implementation
to be rejected. A single PR may also bundle multiple
work items, leaving the instruction, environment, and
tests with inconsistent task boundaries.
Task construction therefore involves more than simply
extracting a task description from a PR. The environment,
instruction, and evaluation must agree on what the task
requires. Agents need to inspect repository context,
identify inconsistencies across these components, and
revise them accordingly. At scale, this process must
handle the long tail of repository-specific conventions
and development practices.

Multi-harness integration and maintenance.
Even after constructing a task, generating diverse
trajectories at scale requires supporting multiple
harnesses during execution. We integrated nine harnesses

Each harness has its own interfaces, dependencies, and
failure modes. Even the same model can behave differently
across harnesses. In addition, harness updates and new
plugins introduce further configuration changes.
As a result, the combinations of models, harnesses, and
versions require ongoing integration and maintenance.
We use a unified adapter to launch rollouts across
different harnesses, with agents helping diagnose
execution failures, revise integrations, and validate
updated configurations. As these combinations grow
and change, manual maintenance becomes unsustainable.
Agents are therefore necessary for sustaining
large-scale trajectory generation.

Trajectory quality control and anti-hacking.
Anti-hacking is critical to producing high-quality
agentic data. Models can exploit evaluation shortcuts
in many ways ( Zhong et al., 2025 ; jacobkahn, 2025 ) , and agents are essential for
detecting such behavior at scale.
In a data synthesis pipeline, agents must distinguish
between two types of problems: hacks , where a
model bypasses the task rather than genuinely solving
it, and synthesis defects , where the execution
environment, tests, or task instructions themselves
are flawed. This distinction is particularly difficult
because a model’s cheating behavior can mask defects
in the task, making an invalid task appear solvable.
To address this, agents scan execution trajectories
for anomalous behaviors, such as accessing Git
repositories and logs, downloading related packages,
searching for code commits, or using shell commands
that bypass the actual task logic. Suspicious cases
are flagged for human review or re-synthesis
(Table 4 ).
Thus, producing agentic data at scale requires not
only making tasks executable, but also verifying
that models genuinely solve them and that the
resulting trajectories are trustworthy.
6.2 Scaling Agentic Data for Pre-Training
Through the task-construction, multi-harness execution,
and quality-control processes described above, we
established a pipeline for producing agentic data at scale.
Figure 18: Funnel chart of agentic data pipeline. 260K raw PRs are filtered into 220K executable tasks. Rolling each task out under 9 harnesses gives about 2M trajectories. After verification, 1.1M trajectories remain, totaling more than 100B training tokens (about 91K tokens per trajectory on average). Tasks and trajectories are drawn on separate scales.
More than 84% of the raw pull requests we collected
were successfully converted into executable tasks.
For these PRs, we constructed execution environments,
extracted task requirements, and synthesized
corresponding tests (Figure 18 ).
We then rolled out the resulting 220K executable PRs
across nine harnesses. The trajectories were generated
using small and medium-sized open-weight models,
including DeepSeek-Flash and GPT-OSS.
After layered filtering, we obtained 1.1M agent
trajectories that met our pre-training quality
standards, totaling more than 100B tokens, with
approximately 91K tokens per trajectory on average.
Together with trajectories from other diverse sources,
the total volume of agentic data available for
pre-training reached 134B tokens. Importantly, these trajectories are not merely an
auxiliary ingredient for post-training, but a
first-class data source for pre-training .
Agent-driven data pipelines represent a shift in how
training data is produced. As models become more capable,
they can solve harder tasks and generate richer training
signals. At the same time, as harnesses and tools evolve,
agents can adapt the underlying integration layer.
Beyond adding more harnesses, the plugin ecosystems
within each harness are also growing rapidly, further
expanding the space of configurations that must be
supported.
We expect agent-driven data pipelines to become an
increasingly important source of high-quality, diverse,
and verifiable training data for future frontier
pre-training runs.

We adopt the Qwen3-30B-A3B ( Yang et al., 2025a ) Mixture-of-Experts architecture, with approximately
30 billion total parameters and 3 billion active parameters per token.
Figure 21(a) summarizes the selected training recipe:
three pre-training sub-stages followed by two context-extension stages.
All stages use a global batch of 33,554,432 tokens and Muon ( Jordan et al., 2024 ; Liu et al., 2025 ) , with AdamW ( Loshchilov and Hutter, 2019 ) for
the excluded parameter groups, including embeddings, the output head,
normalization parameters, biases, and routers.
Stage1 maintains a sequence length of 4,096 tokens. Stage1-1 trains from
scratch through step 210,000 (approximately 7T tokens); Stage1-2 continues
to step 240,000 (approximately 8T), and Stage1-3 supplies the checkpoint at
step 345,000 (approximately 11.5T
). At these transitions, the data mixture
is updated and the RoPE ( Su et al., 2024 ) base increases from 10 4 10^{4} to 5 × 10 5 5\times 10^{5} and 5 × 10 6 5\times 10^{6} , following the base-frequency adjustment for longer contexts ( Xiong et al., 2024 ) . The learning rate remains 5 × 10 − 4 5\times 10^{-4} after an 2,000-step warmup; Stage1-2 and Stage1-3 resume the optimizer and
training state without a warmup. Stage1 uses global-batch load balancing ( Fedus et al., 2022 ; Qiu et al., 2025 ) with coefficient
10 − 4 10^{-4} and router z-loss ( Zoph et al., 2022 ) with coefficient 10 − 3 10^{-3} .
Stage2 extends the sequence length to 32,768 tokens and is configured for
3,000 steps (approximately 100B tokens). Stage3 further extends it to 262,144 tokens
and is configured for 6,000 steps (approximately 200B tokens). Both retain the RoPE base
of 5 × 10 6 5\times 10^{6} , initialize from the preceding stage’s weights with fresh
optimizer state, use a 1,000-step warmup, and disable both load-balancing
and router z-loss penalties. Stage2 keeps the learning rate at
5 × 10 − 4 5\times 10^{-4} after warmup, whereas Stage3 applies cosine decay to
5 × 10 − 5 5\times 10^{-5} . Stage3 also enables length-aware packing. The three stages together correspond
to approximately 11.8T tokens.
The training corpus draws from multiple data types (shown in Figure 20 ): web text, PDF documents,
question-answer pairs, code repositories, and agentic trajectories. Beyond the
agentic data pipeline detailed in Section 6 , each major
category branches into sub-pipelines (shown in Figure 19 ). Web data is
cross-classified by advertisement presence, content type tags, domain category,
and language, creating a Cartesian product of fine-grained cells that serve as
the atomic units for review and mixture tuning. Math data undergoes
model-driven rewriting to increase diversity and refine equation and symbols. PDF data
passes through OCR extraction, vision-language model (VLM) refinement to
correct OCR errors, and multi-stage quality filters. QA data pipelines
classify whether the problem’s context is complete or not and rollout the CoT with monitoring pass rate to probe their
difficulty. Code data includes static code files and pull-request records.
Figure 21(b) shows how the configured sampling mixture
changes across training stages. These proportions describe sampling weights,
whereas Figure 20 reports unique corpus tokens.
Stage1-1 assigns 48% to web text and 20% to code. In Stage1-2 and
Stage1-3, the web share falls to 23%, while papers, books, and QA increase
to 20%, 17%, and 10%, respectively. These two sub-stages share the same
category-level proportions, although their underlying data sources differ.
Stage2 removes the dedicated web component, raises QA to 32%, and assigns
10% to capability-targeted data. Stage3 introduces a 15% agentic component
and assigns 11% to capability-targeted data, including instruction-following
and long-context examples. The capability-targeted category also includes
retrieved web, book, and paper material, so the absence of a dedicated web
component does not imply the absence of all web-derived content.
7.1 Attention-Balanced Data Sampling
Mixing long sequences into training data can cause throughput degradation far beyond what their proportion would suggest. In theory, the expected training time should be the proportion-weighted sum of the time spent on long and short samples. In practice, adding only 10% long samples can halve the training speed.
Using the context infrastructure, the agent traces this unexpected slowdown to computation bubbles caused by imbalanced attention workloads across data-parallel (DP) ranks.
In synchronous data-parallel training, ranks with heavier attention workloads become stragglers, leaving other ranks idle at synchronization points. This imbalance is particularly severe for packed sequences, where attention cost depends on individual document lengths rather than total token count. To mitigate this imbalance, the dataloader sort packs by estimated attention cost within a bounded window and group similarly costly packs into global microbatches. When each DP rank receives multiple packs, we further assign packs in descending cost order to the least-loaded rank with remaining capacity (Figure 22 a).
The sorting window limits sample reordering. Larger windows improve load

training. We used a limited sorting window with a buffer of roughly twice the
distributed world size to balance computational efficiency and sample diversity.

8 Evaluation
We evaluate 801-30B-A3B through complementary comparisons of base-model
performance, general capabilities after supervised fine-tuning (SFT),
and agentic capabilities against post-trained models. The base-model
comparison assesses the pre-trained checkpoint directly, while the
Base+SFT comparison examines general capabilities after adaptation. The agentic comparison further evaluates performance on SWE-bench
Verified, SWE-bench Pro, CyberGym, and KernelBench. These settings are presented
separately to distinguish direct base-model evaluation from downstream
performance after adaptation.
Given current resource and time constraints, we have focused our initial
evaluation and optimization on the settings reported in this section, with
particular emphasis on agentic tasks. We plan to broaden task coverage and
provide more comprehensive evaluation support in future work.

zero credit on every rubric.

KernelBench ( Ouyang et al., 2025 ) .

harness ( Yang et al., 2024 ) , with a sampling temperature of 0.7,
a repetition penalty of 1.1, and a maximum of 300 interaction steps.
For SWE-bench Verified, we additionally apply anti-hacking safeguards
against the shortcut behaviors summarized in Table 4 .
For KernelBench, we use a sampling temperature of 0.6, top- p p of
0.95, and a repetition penalty of 1.1. Each model turn allows up to
65,536 output tokens, with a maximum of 20 interaction rounds.
Context compression is triggered when the context reaches 150K tokens.
For CyberGym, we use the Claude Code harness
( Anthropic, 2025 ) , with a sampling temperature of 1.0
and top- p p of 0.95. The context window is 262,144 tokens, with
automatic compression triggered at 90% utilization. Each task
attempt has a two-hour time limit.

801-30B-A3B achieves an AVG5 of 28.70, leading Qwen3.5
(20.54) by 8.16 points and ranking first on four of the
five evaluations. Its strongest results are on long-context
reasoning and factual knowledge, particularly AA-LCR v1.1
(61.00%), AA-OmniScience (31.30%), and SimpleQA-verified
(34.50%). The pre-training corpus was decontaminated against
SimpleQA using 8-gram overlap matching, making test-set
leakage an unlikely explanation for this result. The exception
is CL-bench Life, where 801-30B-A3B trails Qwen3.5 and
Nemotron-3-Nano.
Performance on classic general benchmarks.
801-30B-A3B achieves an AVG13 of 81.34, ranking second
behind Qwen3.5-35B-A3B (83.76), consistent with its
ranking in base-model evaluation (Table 7 ).
It performs particularly well on mathematics and code,
matching the highest Math500 score (98.40%) and reaching
95.75% on GSM8K and 95.12% on HumanEval. Its main
weaknesses are in competitive programming and instruction
following, as reflected by its results on LiveCodeBench
v5 and IFEval Strict.

8.4 Learning aptitude
Figure 25: Learning aptitude of 801-30B-A3B and Qwen3-30B-A3B on SWE-bench Pro
(left) and BFCL Full (right). Hollow markers are scores at successive SFT
checkpoints; the pale line is the least-squares fit of

in points per tenfold increase in SFT steps.
Lower start, faster learning on BFCL
At the first checkpoint (step 55), 801-30B-A3B scores 31.32 on BFCL Full,
below the 40.04 of Qwen3-30B-A3B. Its slope, however, is 8.62 points per
tenfold increase in SFT steps against 3.33, about 2.6 × 2.6\times steeper. From
step 697 onward it leads at every shared checkpoint and ends at 48.65
against 46.26 at step 3,485. This is the case that motivates
learning aptitude: a checkpoint that starts lower but learns faster overtakes
one that starts higher once fine-tuning runs long enough.
Higher start and faster learning on SWE-bench Pro
On SWE-bench Pro, 801-30B-A3B leads from the first checkpoint, 26.95
against 0 at step 30, and learns faster, with a slope of 9.15 against
5.03. Qwen3-30B-A3B stays at zero for the first three checkpoints (up to
step 120) and reaches 8.76 at step 1,922, where 801-30B-A3B reaches 43.37. Here the intercept and the slope point the same way, so the gap widens rather than closes as fine-tuning continues.
9 Conclusion
We attempted to answer a question that current RSI successes leave open: what
can agents do for frontier pre-training, where the
propose → run → measure → update \textit{propose}\rightarrow\textit{run}\rightarrow\textit{measure}\rightarrow\textit{update} loop cannot close because the run is not
repeatable and the objective is not a score? Our answer, drawn from building
801-30B-A3B in three months, is to organize improvement around three types
of loops. Debugging loops comprise
the infra debugging loop and the data debugging loop, which connect unusual
internal metrics and output patterns to their causes. Five cross-stack
diagnoses, resolved in about one month, came out of these investigations.
The headroom loop is instantiated as the recipe loop,
using tiny-SFT, learning aptitude, and max-over-protocols evaluation to guide
recipe revisions and monitor training progress. Experience-to-metric loops
comprise the classifier development loop, the site discovery loop, and the
crawl-coverage loop, turning experience-based judgment into feedback
that agents can use to improve data workflows. All of them share a context
infrastructure that integrates evidence across teams at scale and preserves
negative results and their reasons.
The resulting model is evidence that this regime works at scale. 801-30B-A3B
is state-of-the-art among open base models at the 30B MoE scale in both direct
base evaluation and matched-SFT comparison, and after a 6B-token SFT stage it
approaches a fully post-trained frontier of its size class on agentic tasks.
But we hold the model to be the byproduct and the account to be the
contribution. Our experience suggests that RSI need not stop at frontier pre-training.
It takes a different form: loops eliminate anomalies, headroom
measurements guide training, and quantitative feedback improves data
workflows. Shared context allows evidence and lessons to accumulate
across teams and iterations. There may be no second run, but the one
we have can still learn from its own progress.
