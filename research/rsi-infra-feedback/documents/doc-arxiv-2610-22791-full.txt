 Abstract

 
 Large language model (LLM) agents have shown promising potential in coding tasks, and their performance is jointly determined by the policy model and the harness that mediates their interaction with the environment.
Indeed, harness and policy are mutually reinforcing and evolving only one component is suboptimal—a harness tuned for one checkpoint may not target the failure modes of an updated policy, while policy learning remains limited to the trajectories elicited by a fixed harness.
In light of this, we propose Self-HPO , a recursive self-improving framework for coding agents that alternates harness and policy optimization, using the evolving policy as its own harness proposer.
Specifically, in each round, the current policy first analyzes its own failures and proposes new harness candidates (H-step).
The policy is then updated through reinforcement learning (RL) under the selected harness (P-step), and hard tasks identified during training form the next harness search set, keeping harness optimization targeted to the policy’s evolving failure modes.
Across three coding benchmarks, Self-HPO consistently outperforms harness-only and policy-only baselines, improving Qwen3.5-35B-A3B’s average resolve rate from 57.8% to 64.8%, with gains generalizing to out-of-distribution settings.
Further analysis shows that both optimized components retain gains even when paired with their base counterparts, while their joint gain exceeds the sum of their individual gains.
 Self-HPO also improves reliability (pass@1) and expands the capability frontier (pass@ k k ) over the base agent.
Additionally, we show that with a stronger external model ( e.g. , Opus 4.8) as the harness proposer, the same framework yields a further performance boost. 

 

 
 
 
 
 

 
 

 

 
 1 Introduction

 
 Large language model (LLM) agents have made rapid progress on complex, multi-step tasks such as software engineering  ( Jimenez et al., 2024 ; Yang et al., 2024 ) , web navigation  ( Zhou et al., 2024 ; He et al., 2024 ; Wei et al., 2025c ) , and computer use  ( Xie et al., 2024 ; Agashe et al., 2025 ) .
Such an agent consists of two components: the policy model and its harness, which is the external scaffold that decides what the model observes, how its actions are executed, what feedback it receives, and when an episode terminates  ( Yao et al., 2023 ; Shinn et al., 2023 ; Yang et al., 2024 ; He et al., 2024 ; Lee et al., 2026 ; Zhang et al., 2026a ) .
Typically, the policy model defines the agent’s capability boundary, while the harness determines how these capabilities are elicited, hence the same model may succeed or fail on one problem depending on its harness  ( Le et al., 2026 ; Zhang et al., 2026a ) .

 
 There have been two main lines of research on improving such agents.
Harness optimization holds the policy fixed and searches over prompts, workflows, or agent code  ( Hu et al., 2024 ; Lee et al., 2026 ; Zhang et al., 2026a ) , whereas policy optimization holds the harness fixed and updates the model from successful trajectories or verifiable rewards  ( Shao et al., 2024 ; Guo et al., 2025 ; Wei et al., 2025a ) .
However, harness-only optimization cannot improve the underlying model, while policy-only training can learn only from the trajectories that its fixed harness elicits.
Although recent works begin to optimize both components  ( Kim et al., 2026 ; Chen et al., 2026a ) , they rely on an external harness proposer and face the challenge of a moving optimization target as the policy and its failure modes evolve, leaving self-driven evolution for coding agents underexplored.

 
 In this work, we introduce Self-HPO , a framework for recursive self-improvement driven by the agent’s own policy.
As illustrated in Figure  1 , Self-HPO alternates harness optimization (H-step) with policy optimization under the optimized harness (P-step).
Harness optimization exposes and compensates for the weaknesses of the current policy, while policy optimization internalizes the elicited behaviors into the model and shifts the failures that the next harness should target.
Specifically, in the H-step, the current policy analyzes its failed trajectories and proposes harness revisions targeting its own failure modes, and selects the updated harness based on search-set performance (§ 2.2 ).
In the P-step, the policy is updated using reinforcement learning under the optimized harness (§ 2.3 ).
In the next H-step, the updated policy serves as the harness proposer, with hard tasks identified from the preceding P-step as the search set to keep harness search aligned with the policy’s evolving failure modes.

 We instantiate Self-HPO with Qwen3.5-35B-A3B  ( Qwen Team, 2026 ) as the base policy, and mini-SWE-agent  ( Yang et al., 2024 ) as the seed harness.
Across three coding benchmarks, Self-HPO consistently outperforms policy-only and harness-only optimization, with the average resolve rate improving at every optimization step, as demonstrated in Figure  1 .
On SWE-Bench Verified  ( Chowdhury et al., 2024 ) , it improves the base resolve rate from 61.0% to 69.5%, with transferable gains on the out-of-distribution SWE-Bench Multilingual  ( Yang et al., 2025 ) and SWE-Bench Pro  ( Deng et al., 2025 ) .
Ablations further show that evolving the harness search set with hard tasks identified during policy learning yields better performance than reusing a fixed set.
We also extend Self-HPO to the external-model setup where Opus 4.8 is used as an external harness proposer, which further raises the resolve rate on SWE-Bench Verified to 71.6%.
The main contributions of this work are as follows:

 
 • 
 
 We propose Self-HPO , a recursive self-improving framework for coding agents that alternates harness and policy optimization, where the agent uses its own policy as the harness proposer and adapts harness search to the policy’s evolving failure modes.

 • 
 
 We demonstrate that Self-HPO consistently outperforms policy-only and harness-only baselines across three coding benchmarks, improving the average resolve rate from 57.8% to 64.8%, with gains generalizing to out-of-distribution settings.

 • 
 
 Our study shows that both optimized components of Self-HPO retain gains even when paired with their base counterparts, while their joint gain exceeds the sum of their individual gains. We also find that Self-HPO not only improves reliability (pass@1) but also expands the capability frontier (pass@ k k ) of the agent.

 2.1 Problem Setup

 
 Given a software-engineering task x x , a coding agent combines a policy P P , parameterized by an LLM, with a harness H H , which controls context, tools, feedback, and termination.
The resulting trajectory τ ∼ π H , P ( ⋅ ∣ x ) \tau\sim\pi_{H,P}(\cdot\mid x) is scored by an executable verifier y ⁡ ( x , τ ) ∈ { 0 , 1 } y(x,\tau)\in\{0,1\} .
We measure a harness–policy pair by its expected resolve rate on the training data 𝒟 \mathcal{D} :

 

 
 
 J ( H , P ) = 𝔼 x ∼ 𝒟 𝔼 τ ∼ π H , P ( ⋅ ∣ x ) [ y ( x , τ ) ] . J(H,P)=\mathbb{E}_{x\sim\mathcal{D}}\,\mathbb{E}_{\tau\sim\pi_{H,P}(\cdot\mid x)}\big[y(x,\tau)\big]. 
 
 (1) 
 
 

 
 We study the problem of self-improving a coding agent’s own harness and policy. The harness changes which behaviors the current policy can reliably express, while a policy update changes the failures that the next harness should target.
As shown in Figure  2 , each H-step holds the policy fixed while using it to analyze failures and propose harness revisions, and
each P-step then freezes this harness and updates the policy through reinforcement learning.
The updated policy becomes the next harness proposer, with hard tasks identified from the training process forming the next search set.

 
 We call this alternating framework Harness-Policy Optimization (HPO) and implement it in two setups.
In the self-improving setup ( Self-HPO ), the evolving policy proposes its own harness candidates, so no separate proposer model is needed.
For reference, we also instantiate the same HPO loop with Opus 4.8 as a fixed external proposer.

 A formal description of Self-HPO is presented in Algorithm  1 .
Starting from a base policy P 0 P_{0} , a seed harness H 0 H_{0} , and a random search set 𝒮 0 ⊂ 𝒟 \mathcal{S}_{0}\subset\mathcal{D} , the method alternates two updates.
At round t t (starting from t = 0 t=0 ), the H-step keeps P t P_{t} fixed and uses it to propose K K harness candidates { H t k } k = 1 K \{H_{t}^{k}\}_{k=1}^{K} , retaining the best-scoring harness on 𝒮 t \mathcal{S}_{t} as H t + 1 H_{t+1} .
The P-step then freezes H t + 1 H_{t+1} and updates P t P_{t} to P t + 1 P_{t+1} on 𝒟 \mathcal{D} using reinforcement learning.
The resulting training rollouts identify the next hard-task set 𝒮 t + 1 \mathcal{S}_{t+1} and the loop stops when the hard-task set stabilizes between rounds.

 
 2.2 H-step: Failure-Conditioned Harness Search

 
 Self-proposer for harness optimization.

 
 The H-step uses the frozen P t P_{t} as both task solver and harness proposer.
The current pair ( H t , P t ) (H_{t},P_{t}) first generates trajectories on 𝒮 t \mathcal{S}_{t} , and the proposer inspects the current failures and produces targeted revisions to the prompt or executable runtime logic (see prompt in Appendix  D ).
Each of the K K search iterations revises the current best harness, starting from H t H_{t} , using the accumulated experience of all evaluated harnesses and their trajectories.
All candidates are evaluated on the same search set 𝒮 t \mathcal{S}_{t} .

 
 Evolving search set.

 
 The search set remains fixed within an H-step but evolves between rounds.
For initialization, we sample 𝒮 0 \mathcal{S}_{0} uniformly from 𝒟 \mathcal{D} . Subsequent search sets consist of hard tasks identified from the training trajectories generated during the preceding P-step, where a task is considered hard if it is never resolved in any of its rollouts in that P-step.
The next H-step regenerates trajectories on those hard tasks with the updated harness–policy pair, producing fresh failure evidence for proposal.
Harness search therefore follows the failures exposed by the preceding policy update instead of repeatedly optimizing against the initial tasks.

 
 2.3 P-step: Policy Optimization under the Optimized Harness

 
 The P-step improves the policy through reinforcement learning under the optimized harness H t + 1 H_{t+1} .
Starting from P t P_{t} , we collect on-policy trajectories over 𝒟 \mathcal{D} as the policy is updated.
An executable verifier assigns binary outcome rewards, and our default optimizer combines Group Relative Policy Optimization (GRPO)  ( Shao et al., 2024 ) with Balanced Adaptive Rollout (BAR) from Orchard  ( Peng et al., 2026 ) .
BAR adaptively draws additional trajectories to construct reward-balanced groups, reducing uninformative zero-variance groups under sparse outcome rewards, and GRPO then updates the policy using the resulting group-relative advantages.
The tasks that were never resolved during this P-step are identified as the hard-task set 𝒮 t + 1 \mathcal{S}_{t+1} , which will be passed together with the updated policy P t + 1 P_{t+1} to the next H-step.

 
 3 Experiments

 
 3.1 Experimental Setup

 
 Harness, model, and data.

 
 All experiments use Qwen3.5-35B-A3B  ( Qwen Team, 2026 ) as the base policy and mini-SWE-agent  ( Yao et al., 2023 ; Yang et al., 2024 ) as the seed harness.
Following Orchard  ( Peng et al., 2026 ) , we construct a training set of 2,484 tasks from SWE-rebench  ( Badertdinov et al., 2025 ) , SWE-rebench V2  ( Badertdinov et al., 2026 ) , and Scale-SWE  ( Zhao et al., 2026 ) , which is used for both harness search and policy optimization.
We perform two rounds of alternating harness and policy optimization based on the stopping criterion, with K = 6 K=6 harness candidates per H-step and 50 RL updates per P-step.
Appendix  A describes the implementation details.

 
 Benchmarks and evaluation metrics.

 
 SWE-Bench Verified (SWE-Verified) contains 500 human-validated GitHub issues and is our primary benchmark  ( Jimenez et al., 2024 ; Chowdhury et al., 2024 ) .
We further evaluate out-of-distribution performance on SWE-Bench Multilingual (SWE-Multi; 300 tasks)  ( Yang et al., 2025 ) and the public V2 set of SWE-Bench Pro (SWE-Pro; 642 tasks)  ( Deng et al., 2025 ) , covering other programming languages and more diverse repository-level tasks.
We report resolve rate, the percentage of tasks whose generated patches pass the benchmark verifier.
Main results are averaged over three evaluation runs (avg@3) with standard deviations.

 
 Baselines.

 
 We compare our method with policy-only and harness-only baselines under two setups, with the base agent as a reference.
In the self-improving setup , RLVR  ( Peng et al., 2026 ) updates the policy under the seed harness, whereas Self-Harness  ( Zhang et al., 2026a ) optimizes the harness using the base policy as proposer without updating its weights.
Self-HPO alternates both updates and uses the current policy to propose harness changes.
In the external-model setup , supervised fine-tuning (SFT) learns from resolved Opus 4.8 trajectories on the same training tasks, while Meta-Harness  ( Lee et al., 2026 ) uses Opus 4.8 to optimize the harness with the target policy fixed.
HPO combines external harness proposals with RL policy updates.

 3.2 Main Results

 
 Self-HPO consistently outperforms policy-only and harness-only optimization.

 
 As shown in Table  1 , jointly optimizing the harness and policy achieves the best performance on all three benchmarks within each setup.
Without an external proposer, Self-HPO reaches 69.5 % 69.5\% on SWE-Verified, outperforming RLVR and Self-Harness by 2.0 2.0 and 4.3 4.3 points, respectively.
Its average score improves from 57.8 % 57.8\% for Base to 64.8 % 64.8\% , exceeding the stronger single-component baseline, RLVR, by 2.9 2.9 points.
The same pattern holds with external supervision: HPO surpasses Meta-Harness by 2.5 2.5 points on SWE-Verified and 2.8 2.8 points on average.
These consistent gains support optimizing the harness and policy together.
Appendix  B further compares these results with frontier models on SWE-Verified.

 
 The gains generalize to out-of-distribution benchmarks.

 
 Although harness search and policy optimization use only tasks from Python projects, the gains transfer to SWE-Multi, which covers nine non-Python languages, and SWE-Pro, which spans a broader range of languages and engineering tasks.
Self-HPO achieves 59.7 % 59.7\% and 65.2 % 65.2\% , respectively, improving over Base by 5.5 5.5 and 6.9 6.9 points and over RLVR by 3.4 3.4 points on both benchmarks.
The benefit is particularly clear on SWE-Multi, where Self-Harness improves over Base by only 0.1 0.1 point, compared with 5.5 5.5 points for Self-HPO.
The same trend holds in the external-model setup, where HPO reaches 61.4 % 61.4\% and 66.0 % 66.0\% , outperforming both single-component baselines.
These results show that the benefits of joint harness–policy optimization extend beyond the Python training domain.

 
 Learning from Opus 4.8 through harness optimization is more effective than SFT distillation.

 
 SFT and Meta-Harness represent two different approaches for transferring knowledge from Opus 4.8: SFT distills generated trajectories into the model weights, whereas Meta-Harness uses external proposals to optimize the harness while keeping the model fixed.
Meta-Harness outperforms SFT by 4.1 4.1 points on SWE-Verified and 8.9 8.9 points on average.
The gap is largest out of domain: SFT falls below Base on both SWE-Multi and SWE-Pro, while Meta-Harness improves on both.
HPO further improves on Meta-Harness, indicating that policy optimization remains beneficial when coupled with an optimized harness.

 Alternating harness and policy optimization drives continued agent improvement.

 
 Figure  3 traces the optimization trajectories of Self-HPO and the two one-sided baselines.
Self-HPO and Self-Harness begin with the same first H-step, but their trajectories diverge once Self-HPO updates its policy.
Across all three benchmarks, the second H-step improves the updated Self-HPO policy, and the following P-step provides a further gain.
In contrast, another harness-only update does not consistently improve performance: Self-Harness drops from 55.0 % 55.0\% to 54.3 % 54.3\% on SWE-Multi.
The final Self-HPO pair surpasses both single-component baselines on every benchmark, supporting repeated adaptation of the harness to the evolving policy.

 We replace RL in the P-step with either SFT on trajectories distilled from Opus 4.8 or rejection-sampling fine-tuning (RFT) on the target policy’s own successful trajectories.
SFT reduces the final resolve rate from 71.6 % 71.6\% to 67.2 % 67.2\% , while RFT reaches 70.5 % 70.5\% , trailing RL by 1.1 1.1 points.
Even when fine-tuning uses the policy’s own successful trajectories, it still falls short of RL, supporting RL as the default P-step.

 
 Evolving the search set helps harness optimization keep pace with the policy.

 
 Reusing the initial search set lowers performance from 71.6 % 71.6\% to 70.1 % 70.1\% .
The evolving set instead directs the next H-step toward hard tasks from the preceding P-step rollouts.
The gain supports refreshing the search target as the agent improves: failures relevant to an earlier policy need not remain the most useful targets for its successor.

 
 Self-proposal retains strong performance without an external proposer.

 
 Replacing Opus 4.8 with the current target policy yields 69.5 % 69.5\% , a 2.1 2.1 -point decrease from HPO.
Although external proposals provide an advantage, Self-HPO still exceeds both self-improving single-component baselines in Table  1 .
Therefore, an external model is helpful but not required for our method.

 3.5 Case Studies

 
 Harness evolution adds targeted controls around the existing agent loop.

 
 Figure  5 contrasts the seed harness with the harness obtained after HPO’s second H-step.
The optimized harness retains the underlying model-query and command-execution loop, but intervenes before budget exhaustion and at submission.
First, it warns the model as the step or time limit approaches and prompts a best-effort submission before the episode ends with an empty result.
Second, a one-time empty-patch guard asks the model to include newly created files via git add -N .
Third, it delays the first submission that passes the empty-patch guard to prompt a check of API names and signatures against the repository and tests.
Finally, a fallback uses the sandbox’s Git diff when the submitted patch fails the apply check.
These changes target distinct ways in which useful repository edits can fail to become a valid submission.
They combine explicit runtime checks, such as detecting an empty patch, with behavioral guidance, such as requesting an interface check.
Harness optimization can therefore change execution and termination logic, in addition to prompts.
Appendix  D gives a detailed diff against the seed harness together with the injected messages, and Appendix  E walks through a task on which an evolved harness changes the outcome for the same policy.

 
 4 Related Work

 
 Harness optimization for LLM agents.

 
 Harnesses govern an agent’s interaction with tools and environments  ( Yao et al., 2023 ; Yang et al., 2024 ) .
Optimization spans prompts and programs  ( Pryzant et al., 2023 ; Khattab et al., 2023 ; Fernando et al., 2024 ; Yuksekgonul et al., 2025 ; Agrawal et al., 2026 ) , contexts  ( Zhang et al., 2026f ; Ye et al., 2026a ; Sun et al., 2026 ) , and workflows  ( Hu et al., 2024 ; Zhang et al., 2025 ; Wang et al., 2025a ; Gao et al., 2025 ) .
Agents reuse feedback through refinement and reflection  ( Madaan et al., 2023 ; Shinn et al., 2023 ) , skills  ( Wang et al., 2023 ) , and memory  ( Zhao et al., 2024 ; Wang et al., 2025c ) . Program evolution also improves solutions and agents  ( Novikov et al., 2025 ; Lange et al., 2026 ; Zelikman et al., 2024 ; Zhang et al., 2026b ; Zhang et al., 2026c ) .
Recent systems revise harnesses from execution evidence  ( Lee et al., 2026 ; Lin et al., 2026a ; Zhang et al., 2026a ; Park et al., 2026 ; Wei et al., 2026b ; Xu et al., 2026a ) , shared experience  ( Weng et al., 2026 ) , demonstrations  ( Che et al., 2026 ; Jiang et al., 2026 ) , or self-preferences  ( Pan et al., 2026 ) .
Other work studies continual adaptation  ( Liu et al., 2026 ; Xu et al., 2026b ) , task selection  ( Miyai et al., 2026 ) , generalization through search controls and modular edits  ( Zhang et al., 2026d ; Xia et al., 2026b ; Wu et al., 2026 ) , and fixed-budget evaluation  ( Ursekar et al., 2026 ) .
These methods adapt the agent around a fixed task-solving policy, whereas Self-HPO also updates the policy that the harness serves.

 
 Policy learning and self-improvement.

 
 Iterative training uses filtered reasoning  ( Zelikman et al., 2022 ; Singh et al., 2024 ; Yuan et al., 2023 ) , refreshed preferences  ( Chen et al., 2024 ; Yuan et al., 2024 ; Pang et al., 2024 ) , self-play curricula  ( Zhao et al., 2025 ; Huang et al., 2026c ; Huang et al., 2026a ) , negative teachers  ( Pei et al., 2026 ) , or evolving environments  ( Huang et al., 2026b ) .
Software engineering agents learn from executable environments  ( Pan et al., 2025 ; Jain et al., 2025 ; Yang et al., 2025 ) , software-evolution supervision  ( Wei et al., 2025a ) , and self-play code repair  ( Wei et al., 2025b ; Choi et al., 2026 ) .
Policy improvement also draws on verifiable-reward RL  ( Shao et al., 2024 ; Guo et al., 2025 ; Peng et al., 2026 ) , harness-guided distillation  ( Ye et al., 2026b ) , and test-time learning during solution search  ( Wang et al., 2025b ; Yuksekgonul et al., 2026 ) .
These methods train the policy under a fixed harness, whereas in Self-HPO the harness co-evolves with the policy being trained.

 
 Joint harness–policy evolution.

 
 Joint adaptation spans prompts and weights  ( Soylu et al., 2024 ; Tiwari et al., 2026 ; Zhang et al., 2026e ; Lu et al., 2026 ) , executable harnesses and policies  ( Hebbar et al., 2026 ; Karten et al., 2026 ; Chen et al., 2026c ; Kim et al., 2026 ; Luo et al., 2026 ; Chen et al., 2026b ; Chen et al., 2026a ) , and policies with evolving skills or external state  ( Xia et al., 2026a ; Fu et al., 2026 ; He et al., 2026 ; Ning et al., 2026 ) , including safety-oriented co-evolution  ( Mao et al., 2026 ) .
MetaRSI composes data generation, harness editing, and model training within a self-improvement loop  ( Tan et al., 2026 ) .
Concurrent work traces interventions  ( Fan and Huang, 2026 ) , studies transfer and multi-harness training  ( Le et al., 2026 ; Wei et al., 2026a ) , and separates the ability to edit a harness from the ability to benefit from one  ( Lin et al., 2026b ) .
Self-HPO differs from these methods along two axes.
First, the policy trained in the P-step becomes the harness proposer of the next H-step, whereas WHALE  ( Kim et al., 2026 ) keeps a frozen external proposer and Evo 2   ( Xu et al., 2026a ) trains a separate proposer for a frozen solver.
HASE  ( Luo et al., 2026 ) also trains a self-proposing policy, but places harness edits in the RL action space instead of alternating harness search with RL.
Second, Self-HPO selects the next harness search set from tasks that remain unsolved during RL, whereas WHALE, Evo 2 , and HASE search on a fixed task set.
Appendix  C gives a more detailed comparison with concurrent work.

 
 5 Conclusion

 
 We introduced Self-HPO, a recursive self-improving framework for coding agents that alternates harness and policy optimization.
The evolving policy proposes its own harness revisions, learns through RL under the selected harness, and supplies hard tasks for the next round of harness search.
Across three coding benchmarks, Self-HPO consistently outperforms policy-only and harness-only baselines, improving the average resolve rate from 57.8 % 57.8\% to 64.8 % 64.8\% .
Analyses further show that harness and policy improvements are complementary and that Self-HPO improves reliability (pass@1) and expands the capability frontier (pass@ k k ) over the base agent.

 Appendix A Implementation Details

 
 Agent implementation.

 
 We use Qwen3.5-35B-A3B  ( Qwen Team, 2026 ) as the backbone and SGLang  ( Zheng et al., 2024 ) for model serving. RL and SFT use the slime framework on one node with eight B200 GPUs.
The seed harness follows the mini-SWE-agent interface  ( Yang et al., 2024 ) , through which the model executes bash commands in a task-specific repository environment.

 
 Optimization data.

 
 The initial search set 𝒮 0 \mathcal{S}_{0} consists of 300 tasks randomly sampled from the training data 𝒟 \mathcal{D} .
For subsequent H-steps, the search set consists of hard tasks from 𝒟 \mathcal{D} , identified using the verified trajectories collected during the preceding P-step: a task is hard if it is never resolved in any of its rollouts in that P-step.
These task IDs are reused to generate fresh failure evidence with the updated policy at the next H-step.

 
 Harness optimization.

 
 Self-HPO uses the current policy checkpoint as both task solver and harness proposer.
The proposer examines the experience of evaluated harnesses and their trajectories, including failed trajectories, and revises the current best harness.
HPO instead uses Opus 4.8 to propose revisions, while retaining the same alternating H-step–P-step structure.
In both configurations, each H-step evaluates K = 6 K=6 candidates, each run once per search task, and the selected harness is held fixed during the next policy update.
The Self-Harness and Meta-Harness baselines use the same search budget.

 
 Policy optimization.

 
 Each P-step initializes from the policy produced by the preceding round and collects on-policy trajectories under the updated harness.
The executable verifier supplies outcome rewards, and the policy is optimized with GRPO and Balanced Adaptive Rollout (BAR)  ( Shao et al., 2024 ; Peng et al., 2026 ) .
Let 𝒜 ⁡ ( τ i ) \mathcal{A}(\tau_{i}) denote the assistant-generated token positions in trajectory τ i \tau_{i} , A ^ i \widehat{A}_{i} its group-relative advantage, and ρ i , u ​ ( θ ) \rho_{i,u}(\theta) the ratio of updated-policy to rollout-policy token probabilities.
The clipped objective is

 

 
 
 ℒ P ​ ( θ ) = − 𝔼 i ​ [ 1 | 𝒜 ⁡ ( τ i ) | ​ ∑ u ∈ 𝒜 ⁡ ( τ i ) min ⁡ ( ρ i , u ​ ( θ ) ​ A ^ i , clip ⁡ ( ρ i , u ​ ( θ ) , 1 − ε low , 1 + ε high ) ​ A ^ i ) ] , \mathcal{L}_{P}(\theta)=-\mathbb{E}_{i}\left[\frac{1}{|\mathcal{A}(\tau_{i})|}\sum_{u\in\mathcal{A}(\tau_{i})}\min\left(\rho_{i,u}(\theta)\widehat{A}_{i},\operatorname{clip}(\rho_{i,u}(\theta),1-\varepsilon_{\mathrm{low}},1+\varepsilon_{\mathrm{high}})\widehat{A}_{i}\right)\right],

 where ε low = 0.2 \varepsilon_{\mathrm{low}}=0.2 and ε high = 0.28 \varepsilon_{\mathrm{high}}=0.28 are the clipping thresholds.
BAR generates eight rollouts per task and selects four to form a reward-balanced group with a success fraction between 0.25 and 0.75.
Sampling continues until 32 groups pass filtering, yielding 128 training trajectories per batch.
Each batch is optimized for one epoch with a global batch size of 128, corresponding to one optimizer update.
We use Adam with a constant learning rate of 10 − 6 10^{-6} , weight decay 0.01, an entropy coefficient of 10 − 4 10^{-4} , and no KL penalty.
Rollouts use temperature 0.95 and top- p p 0.95.
RLVR uses the same configuration under the seed harness, with 50 updates per P-step.

 The trained solver becomes the next harness proposer.

 
 Self-Harness revises its harness with a fixed policy, WHALE uses a frozen external proposer alongside policy learning, and Evo 2 trains a separate proposer while the task-solving policy stays frozen.
Self-HPO instead reuses the updated task-solving policy as the proposer in the next round: the H-step holds policy weights fixed, and the P-step performs RL under the selected harness.
HASE also trains a self-proposing policy, but places task solving and harness editing in a joint RL action space, with persistent edits reviewed at phase boundaries.

 
 Policy training also determines the next harness-search tasks.

 
 The P-step supplies two inputs to the next H-step: the updated proposer P t + 1 P_{t+1} and a search set 𝒮 t + 1 \mathcal{S}_{t+1} drawn from hard tasks encountered during RL.
Thus, policy learning changes both who proposes and which tasks guide the search .
Task-CoEvolve also adapts task selection, but uses outcome variance across candidate harnesses within search rather than difficulty exposed during policy training.
Self-HPO updates task IDs between H-steps and keeps them fixed within each H-step.

 
 Appendix D Harness Details and Prompt Templates

 
 Seed harness.

 
 The seed harness H 0 H_{0} is the mini-SWE-agent ReAct loop  ( Yao et al., 2023 ; Yang et al., 2024 ) : the agent issues bash tool calls in a task-specific sandbox and ends the episode by printing the patch after a fixed submission command.
Its task prompt contains the issue description followed by fixed instructions, including the exact command used to submit the patch.

 
 Harness search space.

 
 A candidate harness is a Python class that subclasses the seed agent, together with its prompt templates.
It may override the agent’s step, for example to inspect the agent’s state, return feedback before accepting a submission, replace the submitted patch, or intervene at any step. All repository access goes through the sandbox.
The policy and sampling configuration (temperature and top- p p of 0.95) are fixed across candidates.

 
 Harness proposer.

 
 Figure  7 shows the system prompt of the harness proposer.
The proposer runs as a coding agent with shell access to the parent harness, its trajectories on the search set, reference fixes for search-set tasks, the outputs of earlier candidates, and notes that the proposer appends after each search round.

 
 
 Harness Proposer System Prompt 
 
 
 
 
 You are the harness optimizer for a fixed policy {P_t}. The search set contains {N} 
 
 
 
 hard training tasks that the policy never solved during the preceding P-step. The 
 
 
 
 parent harness is {H_best}, the current best harness. The starting harness of this search 
 
 
 
 solves {s}% of the search set under the frozen sampling configuration. Your goal is to design ONE new harness mechanism, of your own design, 
 
 
 
 that is added on top of the parent harness and solves more search-set tasks than the 
 
 
 
 parent. 
 
 
 
 
 CONSTRAINTS 
 
 
 
 - Keep every method of the parent harness verbatim and add exactly one new mechanism. 
 
 
 
 - The policy, sampling configuration (temperature 0.95, top-p 0.95), step limit, 
 
 
 
 maximum tokens, and verifier are frozen. 
 
 
 
 - Never inject reference patches or task-specific facts into the agent’s context; the 
 
 
 
 mechanism must compute its own signal at runtime. 
 
 
 
 
 EXPERIENCE (read it before designing; treat it as evidence, not a mandate) 
 
 
 
 - Candidates evaluated so far in this search: scores, code, and trajectories. 
 
 
 
 - Notes left by earlier proposals in this search. 
 
 
 
 Diagnostics computed from the starting harness’s runs on the search set: 
 
 
 
 - Coverage gap: the source files required by the reference fix versus the files the 
 
 
 
 agent touched. 
 
 
 
 - Precision gap: failures in which every required file was edited but the fix was 
 
 
 
 incorrect. 
 
 
 
 - Submission loss: failures in which a real source edit appears in the trajectory but 
 
 
 
 the final submitted patch is empty or malformed. 
 
 
 
 - Reference-fix archetypes (multi-file, signature change, new import, guard, error 
 
 
 
 handling, ...) versus what the agent produced. 
 
 
 
 Decide for yourself which failure is the largest and most reachable by a harness, or 
 
 
 
 find another one. 
 
 
 
 
 WORKFLOW 
 
 
 
 0. Review the experience: the earlier notes and every candidate evaluated so far. 
 
 
 
 For the most recent one, read the tasks it made worse and better than the starting 
 
 
 
 harness (trajectories and reference fixes), and work out why. 
 
 
 
 1. Read several failing trajectories and compare a few with the reference fix to form 
 
 
 
 your own hypothesis about the dominant failure cause. 
 
 
 
 2. Design a mechanism with a detectable trigger in the agent’s own state and a 
 
 
 
 concrete action: for example, intercept a submission and return feedback so that 
 
 
 
 the agent gets another turn to act on it, replace the submitted patch, or act at 
 
 
 
 any step. 
 
 
 
 3. Implement it in a copy of the parent harness. All repository access must go 
 
 
 
 through the sandbox environment. 
 
 
 
 4. Write a one-line purpose (diagnosed cause -> mechanism), append what you learned 
 
 
 
 this round to the notes, and stop. The search then checks that the candidate keeps 
 
 
 
 every parent method and fires on real sandbox tasks, and returns any failure to you 
 
 
 
 to fix.

 (1) Budget valve: RESCUE_TEXT 
 
 
 
 
 [BUDGET ALMOST EXHAUSTED -- STOP EXPLORING AND SUBMIT NOW] 
 
 
 
 
 You are nearly out of steps/time and have not submitted a patch. An empty result scores zero, but a focused best-effort edit can pass. Right now: 
 
 
 
 1. Decide the single most likely fix location from what you already know -- do NOT start new open-ended exploration. 
 
 
 
 2. Make that concrete edit to the source file (the smallest change that matches the PR’s literal request). 
 
 
 
 3. Immediately create and submit the patch, in SEPARATE commands: 
 
 
 
 git diff -- <the source files you modified> > patch.txt 
 
 
 
 echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT && cat patch.txt 
 
 
 
 Do this in your next one or two commands. 
 
 
 
 (2) Empty-patch guard: EMPTY_GUARD_TEXT 
 
 
 
 
 [YOUR SUBMISSION IS EMPTY -- it contains no source-code changes, so it cannot fix anything. Not finalized.] 
 
 
 
 
 You have not edited any source file yet (patch.txt is empty or has no diff hunks). Do NOT give up. Re-localize the bug: 
 
 
 
 1. Re-read the PR and grep for the exact symbol/message/flag it names. 
 
 
 
 2. Open the file where that symbol lives and make the concrete edit the PR requires. 
 
 
 
 3. IMPORTANT -- did your fix CREATE a NEW file (a brand-new module)? A plain `git diff` does NOT show untracked new files, so your patch looks empty even though the file exists. Stage new files first so they appear as additions: 
 
 
 
 cd /testbed && git add -N <the new file(s) you created> 
 
 
 
 4. Verify with `cd /testbed && git --no-pager diff` that a real change (or a `new file mode` hunk) now shows. 
 
 
 
 5. Then `cd /testbed && git diff -- <files> > patch.txt` and submit with: 
 
 
 
 echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT && cat patch.txt 
 
 
 
 (3) Contract grounding: GROUND_TEXT 
 
 
 
 
 [GROUND YOUR DIFF IN THE REPO’S EXISTING TESTS -- one-time check; your submission is NOT finalized yet] 
 
 
 
 
 The most common way this task is failed is submitting a patch that APPLIES cleanly but implements the WRONG contract -- a guessed function/option name, a signature the codebase never uses, a rename or new spelling that no caller expects, or an error/return shape different from what the code around it uses. Re-reading the PR will NOT catch this, because your reading of the PR is what produced the wrong contract. The codebase itself is the authority. The repo ships EXISTING tests that already exercise the code you touched and the API next to it -- they show the EXACT names, signatures, argument spellings, and error/return types the code is expected to have. Use them as ground truth now. 
 
 
 
 
 1. Print your changes and identify the concrete symbols you added or changed: 
 
 
 
 git --no-pager diff 
 
 
 
 List every NEW or RENAMED symbol/option/message string in your diff. 
 
 
 
 2. For each such symbol, search the repo’s tests and existing call sites for how that symbol -- and the nearest EXISTING sibling API -- is actually used: 
 
 
 
 grep -rn --include=’*.py’ -e ’<symbol>’ -e ’<sibling_api>’ . | head -40 
 
 
 
 Then OPEN and READ the specific test files that reference the area you changed (e.g. tests/ or test_*.py near your file) and note the exact spelling, call signature, and expected result/exception the codebase uses. 
 
 
 
 3. Confront your diff against what the tests/call sites actually expect. If you introduced a name, option spelling, signature, or error shape that NO existing test or caller uses -- while an existing convention does -- change your diff to MATCH the codebase’s convention. Do not invent a new API; conform to the one already there. Also confirm you did not MISS a behavior the tests imply is required. 
 
 
 
 4. If you changed anything, regenerate the patch: 
 
 
 
 git diff -- <the source files you modified> > patch.txt 
 
 
 
 and re-inspect patch.txt so it contains ONLY your intended source changes. 
 
 
 
 5. When your diff conforms to the codebase’s real contract, re-issue the EXACT submit command: 
 
 
 
 echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT && cat patch.txt 
 
 
 
 This check happens only once -- after you re-submit, it goes through.
