Operational notes

A defunct container can survive a single
docker rm -f
; the next
docker run
then fails on the name conflict while an orphaned engine process keeps the port and answers health checks — which silently mislabels the next experiment. Loop
docker rm -f
until the container is gone
and
nothing listens on the port.

A parse failure must never satisfy an "expected config" assertion, or a server that has not started yet gets recorded as "spec disabled".

Verify intended config from the server (
/get_server_info
) before timing anything; discard legs that fail the gate rather than recording them.

Update: 1M context is now what runs — measured cold, plus a measurement correction

Production was re-created with
CONTEXT_LENGTH=1048576
(same box: 4× RTX PRO 6000, TP4/EP4, DSPARK, fp8 KV; host exposes 7 GPUs, 4 in use). We measured it properly this time: cold prefill ladder, decode at short and at ~906K context, and stability. Write-up:
https://github.com/Lei-010/hermes-agent/blob/main/docs/DeepSeek-V4.1-Flash-SM120-1M-Context-Validation-2026-09-28.md

The one methodological change that matters: a unique marker at the head of every prompt.
sglang's radix cache keeps a completed request's pages, so a "level" that shares its prefix with the previous level skips prefill for everything shared and reports a throughput that contains almost no prefill work. Two numbers in circulation are exactly that artifact — including one of ours.

Stability:
two independent cold 1M passes, 5 sequential + 4 concurrent high-context decodes, no traceback / no OOM / no CUDA error in the log,
dmesg

RestartCount
0, GPU steady at 96.8 GB of 97.9 GB (98.9 %). Headroom is ~1 GB — worth knowing before running two long requests.

Correction to our own 2026-09-27 crash report in this thread:
a ~500K request SIGKILLed the entire TP group (
Exited 137
, no traceback, no OOM-killer, host RAM fine, last log line mid-prefill). We could not reproduce it today — cold 500K took 106 s, and cold 1M passed twice. Best current hypothesis (
⚠️
unproven): the first oversized request after a cold start triggers new Triton kernel-shape JIT compilation while a large prefill is in flight, stalling the scheduler past the 300 s watchdog, which kills the process group and therefore leaves no Python traceback. The timing fits — that container had become healthy ~90 s earlier, and its log carries both

Triton kernel '_hc_mix_reduce_sinkhorn_kernel' took 20.78 s to compile after serving started.
Health check failed. Server couldn't get a response from detokenizer for last 20 seconds.

while today's 40-minute window has no compile or watchdog line at all. The falsifiable test: restart, make a cold ≥500K request the very first request, and see whether the group dies again. Until then, the operational rule we're using is to send one warm-up request of a few hundred K tokens after a cold start and let it finish before trusting the service.

Since the vLLM blog notes that V4.1's shared KV latent is replicated on every rank under TP, each GPU would need to hold all 64 × 200K = 12.8M tokens. That works out to roughly
≤ 3.3 KB/token
. Your current figure is 5,931 B/token, while vLLM's H200 TP4 row (38.5 GiB KV ≈ 20M tokens) suggests about 2.07 KB/token at fp8. So it seems possible in principle, but I may well be missing something specific to SM120 or this build.

Things that might explain the gap (if you get a chance to check)

SWA bounded replay.
The vLLM blog mentions that without it, prefix caching stores uncompressed FP8 SWA KV at every hit boundary (more than 10× global KV). It's on by default in newer builds. I wondered whether
dev253
has it, and whether passing
--swa-bounded-replay
explicitly is accepted.

Engram placement.
The checkpoint includes 183.1 GiB of Engram tables, and the recipe's NVIDIA TP configs offload them with
--engram-config '{"cpu_offload":true}'
. I didn't see it in your launch command, and the recipe mentions some builds set the default through
VLLM_PLE_CPU_OFFLOAD
. Your 49.44 GiB/GPU sits between "fully resident" (~59.5) and "fully offloaded" (~36.6), so I wasn't sure what's actually on the GPU. Your earlier SGLang setup used
offload_mode=ram
, so the host may already have the ~183 GiB of RAM this needs.

KV groups.
If convenient, the resolved
kv_cache_config
lines at
VLLM_LOGGING_LEVEL=DEBUG
would show per-group page sizes, any padding-layer warning, and whether DSpark's KV shares the pool. That might also explain the 78,783 × 64 vs 2,983,601 difference.

Indexer dtype.
vLLM's Blackwell configs use
indexer_kv_dtype: mxfp4
. I'm curious whether SM120 accepts it, but completely fine to skip.

Graph sizing.
The recipe sizes capture as seqs × 6 (with DSpark), so 1024 corresponds to ~128 sequences. For 64,
--max-num-seqs 64 --max-cudagraph-capture-size 384
might return some of the ~7.5 GiB difference between estimated and actual graph memory.
