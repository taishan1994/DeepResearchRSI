# 用 DeepResearchRSI 做「kernel 生成智能体」综述：框架侧的改动

本轮新建归档 `research/kernel-agent`，产出 6 页论文。以下是框架与工具链上
实际问题与修法，按「症状 → 原因 → 修法」记录。

---

## 1. 检索式按「智能体的构成要件」拆，而不是按主题词

### 症状

第一版用 `all:"agent" AND all:"kernel"` 这类组合，11 组式子命中 180 篇，
粗筛后仍有 44 篇，其中混进了水下机器人巡检、控制理论、对话推理。

### 原因

`agent` 与 `kernel` 各自都是高频词。组合检索只能保证「两个词都出现」，
不能保证「讲的是同一件事」。

### 修法

从智能体的**构成要件**出发各设一组检索式：工具使用、环境反馈、多轮迭代、
多智能体、规划搜索、端到端系统。这样召回的工作天然含有要件描述，
为后续按维度抽取证据铺路。

代价是仍需人工判定（见 §2），但召回质量明显更高：180 → 178 篇
2025 年后 → 26 篇核心。

## 2. 自动筛选分不清「用 CUDA 加速」与「生成 CUDA kernel」

### 症状

三级筛选的前两级都失效：

1. **粗筛**（kernel 语境 + 智能体要件 + 生成词）：保留 44 篇，但混进
   水下多机器人巡检（`2610.26106`，有 GPU、有 pipeline）、控制理论
   （`2611.04096`，GPU 加速 HJ 可达性）、对话推理（`2506.11108`）。
2. **同句共现收紧**（要求 kernel 与生成/优化在同一句）：**一篇都没剔除**。

### 原因

不是词不够近，是**主语不同**：

- 「我们用 CUDA 加速这个计算」
- 「我们让智能体生成 CUDA kernel」

两句在词汇上完全重叠，在语义上是两件事。词频统计没有主语概念，
再怎么收紧共现窗口都分不开。

### 修法

最后一层改人判，但把判据固化成代码而不是写在脑子里：
`decide_agent.py` 里每个 arXiv ID 对应 `(layer, 理由)`，理由必须能指向
摘要里的具体表述，不能写「相关」。同时脚本检查两件事：

- 有候选没判定 → 报错（防止漏判被静默放过）
- 判定了但 ID 不在候选里 → 报错（防止手抖写错 ID）

结果 44 篇全部有判定：26 core / 9 adjacent / 9 exclude。

### 教训

**自动筛选的价值在「把 180 缩到 44」，不在「把 44 缩到 26」。**
承认这一点比继续调正则有用。原文已把这个过程写进论文第 1.3 节——
失败的方法论本身是结论的一部分，藏起来反而让读者无从判断可靠性。

## 3. 证据抽取会抓到题名和作者行——而 E1 检不出来

### 症状

第一版 18 条证据里有 5 条是题名与作者信息：

```
e-001  "Hardware Feedback for CUDA Kernel Optimization Thanks: Corresponding author."
e-004  "KernelOPT: Dispatch-Aware Agentic Search ... Aheli Poddar † † thanks:"
e-008  "SpecGen: Accelerating Agentic Kernel Optimization ... Jihu Guo Note:"
```

### 原因

正则找「关键词附近的一句话」，而题名里恰好含关键词；HTML 转文本后
题名与作者行黏成一句。

### 为什么危险

这些片段**确实是原文子串**，E1 校验完全通过。若不人工看一遍，
会得到「证据 18 条、E1 全绿」的假象，而其中 5 条对论证零贡献。

**E1 只能证明「这句话在原文里」，不能证明「这句话有意义」。**

### 修法

在 `grab()` 里加三道过滤，任一不满足就继续往后找：

1. 不含 `†` / `thanks:` / `Corresponding author` / `Affiliation` /
   `Equal contribution` / `@` / `arXiv:\d`
2. 不以论文题名开头（题名前 40 字不出现在片段前部）
3. 必须含实义动词或指标词（`is/are/we/propose/improv/...` 或
   `是/我们/本文/可以/因此`）

并把「取第一处命中」改成「取第一处**合格**命中」——`re.search` 换成
`re.finditer` 循环。

修后 18 条全部是正文实质句。

## 4. 26 篇 core 里有 12 篇一条证据都没有

### 症状

分析脚本统计「每篇工作被多少条证据引用」，发现 26 篇 core 中 12 篇为 0。

### 为什么是硬伤

不只是「材料少」。本文的核心判断是「跨维度工作为 0」——若这个统计
实际只基于 14 篇，样本就不是 26 篇，结论的稳健性完全不同。
**未被引用的来源等于不存在。**

### 修法

`cover_core.py`：对未覆盖的 core 逐篇扫全文，用通用 pattern 找一句
有实质内容的句子，并按句子内容**自动判定它属于哪个维度**
（出现 `ncu/profil/metric` → observe，出现 `turn/budget/prune` → budget，
以此类推；全不中记为 `general`，不计入维度统计——不能硬塞）。

补 11 条（CUDA Agent 无全文），覆盖 25/26 篇。

### 顺带发现的纪律问题

维度判定必须靠**句子内容**，不能靠「这篇论文被归为哪一类」——
否则就是自己给自己作证，循环论证。

## 5. 主张引用不全导致证据悬空

### 症状

第一版 9 条主张只引用 29 条证据，剩 10 条悬空。悬空意味着材料采了
却没进论证，读者无法判断它支持什么。

### 原因

`ids(dim, limit=6)` 把每维度证据截断到 6 条，而实际有的维度有 10 条。

### 修法

上限放宽到 20（即不截断），并加一项构建时检查：**打印悬空证据列表**。
从「事后统计」变成「构建即报」。修后 39/39，悬空 0。

## 6. `check_references.py` 把期望值写死

### 症状

本归档 35 条参考文献，检查器报「参考文献区出现的编号：20 个」。

### 原因

```python
print(f"...{len([n for n in nums if n <= 20])} 个")   # 20 是硬编码
```

从只有 20 条来源的归档继承而来。

### 为什么这是检查器最坏的写法

把**期望值**写死，检查的就变成「PDF 是否等于我以为的样子」，
而不是「PDF 是否等于 sources.csv」——后者才是它该干的。

更糟的是它会**通过**：链接和可见文本都是 35 个、完全对齐，
只有这一行显示 20，看报告的人会以为少了 15 条。

### 修法

期望值改为 `len(sources)`，并同时报出两类问题：

- 编号缺失（`expect - nums`）
- 编号越界（`nums - expect`，即多于来源行数）

反例验证：从 `sources.csv` 删掉一条，立刻报
「1 个链接不在 sources.csv 里（可能编造）」+「编号越界：[35]」。

## 7. `make_references.py` 的分组标题写死篇数

### 症状

生成的参考文献章节里，正文写「下列 20 篇」、分组标题写「核心 RL 方法
（13 篇）」、实际 35 条。三处数字互不一致。

### 原因

整段文本从 `cuda-kernel-rl` 复制而来，其中「20 篇」「13 篇」是那个归档
的真实数字，对本归档全错。

### 修法

- 总数用 `len(rows)`
- 分组标题的篇数用 `len(group)` 填
- 组名为空时自动跳过（本归档没有 infra 层，`infra` 组为空）

### 教训

与 §6 同一个毛病：**把某一次的正确答案写进代码，而不是从数据推出来。**
复制脚本时，凡是出现具体数字的地方都要改；更好的做法是让它们根本不出现。

## 8. 图的 `value` 列用错口径，审计抓出来了

### 症状

审计报：`数值 10（fig2_evidence.csv）在主张 c-budget 及其全部证据里都找不到`。

### 原因

fig2 的两根柱子分别是「工作数」和「证据条数」。我把 `value` 列填成了
**证据条数**（budget 维度 10 条），但正文与主张里说的是**工作数**
（「9 篇讨论了预算」）。审计按 `value` 去主张里找，自然找不到 10。

### 修法

`value` 列只放「能在主张里找到的那个数」，即工作数；证据条数放在
单独的列里供画图用。并在生成脚本里写明原因，避免下次改回去。

### 值得记的一点

**审计在这里是对的，图是错的。** 我最初的直觉是「图上有 10，主张里也该有
10」，去改主张迁就图——但 10 是证据条数，不是任何一句结论里的数。
正确做法是让 `value` 表示**可被论证引用的量**。

## 9. 表格空 caption：未登记的图表会被静默渲染成怪样子

### 症状

五维框架表的 caption 是空的，PDF 里显示成一个没有标题的表格。

### 原因

`build_paper_json.py` 的 `TABLES` 是空列表（「表格直接写在正文里」），
于是 `md_to_tex.py` 查 `TABLE_TITLES` 取不到标题，落到 `\caption{}`。

同时审计报「表未生成」——产物约定放在 `tables/<id>.md` 或 `.csv`，
而我把数据放在了 `data/`。

### 修法

1. 登记 tab1（含 `title` 与 `cites`）
2. 建 `tables/tab1.md` 满足产物约定
3. 正文加「表 1 给出这五个环节的对应关系」，避免「正文没引用表」

### 教训

**硬编码的图表清单会限制审计能看到的范围。** 未登记 = 不被检查 = 出错
也没人报。这与上一轮 fig4/tab3 的问题同源，属于**复发**——
说明当时只修了那两张图表，没修「新增图表必须登记」这个流程。

## 10. `write_validation_line.py` 的静默回退

### 症状

新写的脚本从 `validate_research_dir()` 按属性取 `s.sources`，抛
`AttributeError`，被 `except` 兜住后打印警告、用了**硬编码默认值**。
而默认值恰好是对的（35/39/9/5），于是写进 REPORT.md 的数字看起来正常。

### 为什么危险

数字对不代表代码对。下次换个归档，默认值就会写成错的，
而警告只有一行，很容易被 `Select-Object -Last 1` 过滤掉。

### 修法

- 改为 dict 取值 `s["sources"]`
- 读不到就**报错退出**，不用默认值兜

### 教训

**异常兜底时不要用「看起来合理的默认值」。** 它在正确时会掩盖错误，
在错误时会生产错误数据——两头都坏。宁可直接失败。

## 给框架的建议

1. **图表的 `value` 列应有语义约束。** 现在只要能在主张里找到就算通过，
   但「找到的数是不是同一个量」机器判断不了。可要求 `data/*.csv` 增加
   `quantity` 列（`papers` / `evidence` / `speedup`），审计按 `quantity`
   去主张里找对应的名词。
2. **「新增图表必须登记」应该是脚本强制的。** 现在靠人记得改
   `FIGURES`/`TABLES` 列表，忘了就静默出错（本轮与上轮各一次）。
   可在 `md_to_tex.py` 里检测：正文出现的图片文件名若不在 `paper.json`
   的 figures 里，直接报错。
3. **`decide_agent.py` 那种「人工判定表」值得做成通用机制。** 筛查到
   最后一层必然要人判，把判据与理由固化成可复查的数据结构，
   比散落在对话里好。
