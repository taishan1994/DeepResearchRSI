 Abstract

 
 Large language model (LLM) coding agents develop software through
experimentation, offering an opportunity to design the serving systems
supporting their own operation. Effective serving requires coordinating
implementation and operating decisions under session dependencies,
latency constraints, and correctness requirements. We introduce
ServerBench, a benchmark for agentic design of complete, specialized
LLM serving systems. Agents experiment against a common objective,
 dollars per dollar : latency-qualified token value per dollar of GPU cost. Stateful replay preserves session
dependencies, and independent verification checks the submitted system.
Across 11 coding-agent models and three deployments, Claude Sonnet
5.5 achieves 2.97 dollars per dollar on Gemma E4B, 4.87 × 4.87\times the vLLM
reference; 22 of 33 runs yield verified systems,
and 13 exceed the strongest baseline. Our analysis identifies three findings: high-value designs
coordinate capacity improvements with load selection; agents interpret
performance feedback through workload-relevant experiments; and reliable delivery requires
verification of the execution paths introduced by optimization.
Overall, ServerBench supports systematic study of how agents translate service
objectives and feedback into effective, verified serving
systems for given task specifications.

 

 
 1 Introduction

GPT 6.1 Sol offers lower-cost gains; Claude reaches higher value.

 Large language model (LLM) coding agents build on code-generation
capabilities ( Zheng et al., 2025 ; Zhou et al., 2026a ) , using tools
and execution feedback to undertake software development and professional
workflows ( Yang et al., 2024 ; Xiao et al., 2025 ; Chan et al., 2025 ; Sun et al., 2026 ) . These
workflows depend on LLM serving systems, which run models and handle
requests ( Kwon et al., 2023 ; Zheng et al., 2024 ; Zhou et al., 2026b ) . This creates an
opportunity for coding agents to design these systems. Service providers
need correct model execution and timely responses. We therefore ask:
 how can coding agents design LLM serving systems while
satisfying given deployment and service constraints? 

 
 Figure 2 : Agents design the server and choose how many sessions it serves
at once for a given model, GPU allocation, and workload. Replay preserves
shared context and dependencies between requests; final checks assess
model correctness and complete workload execution. 
 
 
 Despite rapid progress in agent-driven systems optimization, existing
benchmarks evaluate individual kernels, code patches, or servers under
preset test conditions
 ( Ouyang et al., 2025 ; Nangia et al., 2026 ; Williams et al., 2026 ; Yeon et al., 2026 ; Xu et al., 2026 ) ,
leaving three gaps in evaluating how agents design complete serving systems:

 
 • 
 
 Oversimplified workloads. Prior benchmarks issue
independent requests or fixed prefill, decoding, and throughput
scenarios ( Yeon et al., 2026 ; Xu et al., 2026 ) . With uniform request lengths
and fixed batches, a static batch serves nearly as well as a production
engine, so techniques that real deployments depend on, such as
continuous batching and paged attention
 ( Yu et al., 2022 ; Kwon et al., 2023 ) , bring little benefit. Real
applications such as coding agents instead mix short and long requests,
extend a shared context over many turns, and fan out into parallel
subagents, where prefix reuse, memory management, and prefill–decode
interference shape performance
 ( Zheng et al., 2024 ; Srivatsa et al., 2025 ; Agrawal et al., 2024 ; Zhong et al., 2024 ) .

 • 
 
 Speedup-only objectives. Existing benchmarks score speedup
or throughput relative to a baseline
 ( Ouyang et al., 2025 ; Yeon et al., 2026 ; Xu et al., 2026 ) . Such objectives
ignore latency requirements and GPU cost and fix the offered load,
whereas a service provider must decide how much workload to serve
while keeping time to first token (TTFT) and time per output token
(TPOT) within targets.

 • 
 
 Correctness-only validation. Validation typically checks
outputs against a reference implementation or test suite
 ( Ouyang et al., 2025 ; Williams et al., 2026 ; Xu et al., 2026 ) . A serving system must
additionally meet tail-latency targets on the deployed workload and
execute that workload in full, with complete prompts, prescribed output
lengths, and consistent streaming. Optimizations such as speculative
decoding, state reuse, and custom scheduling introduce execution paths
that short or isolated tests rarely exercise.

 

 
 We introduce ServerBench , a benchmark in which coding agents
build a complete LLM serving system for a given model, GPU allocation,
and workload, and decide how much workload it serves
( Figure   2 ). Starting from a minimal Transformers server,
agents plan experiments and revise their systems within a fixed
development budget. ServerBench closes the three gaps with three designs.
 1. Workload: real coding-agent trajectories. ServerBench
replays recorded coding-agent sessions ( SemiAnalysis, 2026a ) 
with their request lengths, multi-turn structure, shared prefixes,
parallel subagent branches, and inter-turn delays. Requests wait on the
responses they depend on, so serving latency governs how much work
completes within the measurement window ( Section   3.2 ).
 2. Objective: dollars per dollar. We price the input and
output tokens of each completed request at fixed API rates, count only
requests that meet both TTFT and TPOT targets, and divide by the GPU
cost of the measurement window ( Section   3.1 ). For example, USD 3.65
of qualified token value over USD 0.83 of GPU cost scores 4.40. The
objective rewards capacity improvements together with a matching load
choice: serving more workload raises gross value only while requests
still meet their latency targets.
 3. Validation: beyond correctness. Latency targets are the
p90 TTFT and TPOT of an SGLang reference with its model-specific
configuration, frozen before development ( Section   3.1 ). The
submitted system is rebuilt in a fresh deployment and replayed on
held-out seeds. Independent checks verify complete prompts, output
lengths, streaming consistency, generation fidelity to the checkpoint,
and held-out answer accuracy; a post-run review inspects code and
recorded actions for prohibited shortcuts ( Section   3.4 ). Only
verified systems receive a score.

 
 We evaluate eleven coding-agent models across three model–hardware
deployments. Claude Sonnet 5.5 achieves 2.97 dollars per dollar on Gemma
E4B, 4.87 × 4.87\times the vLLM serving baseline
( Section   4.2 ). Trajectory analysis identifies three
findings.
 High-value designs coordinate capacity and concurrency. 
Sonnet 5.5 improves its server before raising concurrency, then limits
load when additional sessions worsen TPOT
( Section   4.3 ). Interpreting feedback in workload
context guides optimization. A random-text probe leads one agent to reject an
optimization; workload replies reveal its benefit and lead another to
adopt it
( Section   4.4 ). Verification must match the
deployed workload. Agents’ short or isolated checks can miss long-context
stalls and cross-request crashes; known faults can persist or recur after
edits in submitted systems
( Section   4.5 ).

 
 Our contributions are:

 
 • 
 
 ServerBench, a benchmark for designing complete LLM serving
systems to maximize service value per GPU dollar
( Section   3.1 ). Agents design the server and set the number of
concurrent application sessions.

 • 
 
 An evaluation protocol that replays coding sessions with shared
context and dependent requests, supports experiments designed by agents,
and independently verifies the final system
( Sections 3.2 to 3.4 ).

 • 
 
 A study of eleven coding-agent models across three deployments,
using controlled comparisons and trajectory analysis to explain
successes and failures in system design, experimental judgment, and
verification ( Sections 4.2 to 4.6 ).

 

 

 
 2 Related Work

 
 2.1 Inference System Optimization

 
 Orca and vLLM improve request scheduling and memory management
 ( Yu et al., 2022 ; Kwon et al., 2023 ) . SGLang and Preble exploit prefix reuse
 ( Zheng et al., 2024 ; Srivatsa et al., 2025 ) , while Sarathi-Serve and DistServe
mitigate prefill–decode interference through chunked prefill and prefill–decode
disaggregation ( Agrawal et al., 2024 ; Zhong et al., 2024 ) .
AlphaEvolve and AI-Driven Research for Systems (ADRS) use evaluator
feedback to generate and refine algorithms and system code
 ( Novikov et al., 2025 ; Cheng et al., 2025 ) .
Vortex enables agents to generate and refine sparse-attention algorithms
in a programmable serving system ( Chen et al., 2026 ) .
ServerBench studies whether agents integrate such optimizations into systems under fixed
deployment conditions.

 
 2.2 Inference-Performance Benchmarks

 
 MLPerf Inference standardizes workloads, quality targets, and deployment scenarios
 ( Reddi et al., 2020 ) . Agent-oriented benchmarks assess correctness and
performance: KernelBench tests generated GPU kernels against PyTorch references
for correctness and speedup ( Ouyang et al., 2025 ) , ISO-Bench compares
vLLM and SGLang optimization patches with expert implementations
 ( Nangia et al., 2026 ) , and Φ \Phi -Bench spans kernel completion through
end-to-end infrastructure optimization ( Ding et al., 2026 ) . SWE-Serve tests
production features within SGLang ( Williams et al., 2026 ) , while InferenceBench
evaluates complete servers on prefill, decoding, concurrent throughput,
and a balanced scenario using baseline-relative speedup
 ( Yeon et al., 2026 ) . ServerBench extends this line of evaluation
to response-dependent, stateful sessions and a latency-qualified
revenue-to-cost objective, linking implementation and operating choices
to the service delivered by complete systems.

 
 3 ServerBench

 
 ServerBench evaluates agentic design through a service objective,
stateful workload replay, iterative experimentation, and final verification.
Task configurations appear in Sections   6 and  9 .

 3.2 Stateful Workload and Closed-Loop Replay

 
 Coding sessions contain dependent turns, shared context, and parallel
subagent branches. Using the AgentX harness ( SemiAnalysis, 2026a ) ,
we replay response-dependent turns and parallel branches using recorded
inter-turn delays, with long global idle periods compressed.
Offered concurrency bounds active top-level sessions, whose branches
can issue additional requests. Response times thus affect session
progress and the work completed within the measurement window.

 
 Privacy-preserving reconstruction replaces prompt and tool contents
while retaining request lengths, shared prefixes, and session topology.
Tasks fix reconstructed prompts and output lengths. Shared context
supports computation reuse ( Zheng et al., 2024 ; Srivatsa et al., 2025 ) ,
while retained state and active requests compete for memory. Agents are
responsible for translating these workload characteristics into optimizations
while preserving model behavior and executing the workload in full.

 
 Growing context enables reuse, while new sessions add prefill work
that competes with decoding ( Agrawal et al., 2024 ; Zhong et al., 2024 ) .
Session progress thus combines prompt processing, generation, and retained state.

 
 3.3 Agent Environment and Development Loop

 
 Figure 3 : Stateful replay connects session progress to the agent’s design
experiments (a). Final evaluation verifies the published system and measures
request value against calibrated latency targets (b). 
 
 
 Agents work in an Internet-disabled Harbor sandbox with container or
Modal backends ( Merrill et al., 2026 ) . They receive a minimal server,
read-only model weights, reference configurations, measurement tools, and
the published performance procedure. Task instructions require model fidelity
and complete workload execution and prohibit evaluation manipulation.
Independent correctness-test details are withheld, and trusted evaluation
components remain outside the editable serving implementation.

 
 The tools report latency, throughput, and request value. Agents organize
their own experiments, diagnose bottlenecks, and revise the implementation
 ( Yang et al., 2024 ) . They budget time for replays, diagnostics, and development.
Publishing fixes the implementation and concurrency separately from
performance testing; when the allotted time for development expires,
the last published version becomes the submission.

 
 Agents choose experiment scale: diagnostics isolate suspected bottlenecks,
while complete replays test interacting requests. They decide which
observations warrant further tests, which changes to retain, and when to
publish. Versioned submissions connect these decisions to the implementation
evaluated after development.

 3.4 System Verification

 
 After development, ServerBench rebuilds the submission in a fresh
deployment and replays sessions sampled with seeds disjoint from development. Independent tests and
post-run review check the resulting system ( Figure   3 ).

 
 Workload and output verification.

 
 Replay checks cover complete prompts, output lengths, streaming consistency,
and session progress. Timed replay disables EOS stopping to generate the prescribed output length;
separate EOS probes exercise natural stopping. Reference-scored
continuations check generation against the checkpoint. Held-out questions
compare answer correctness with a plain implementation of the same model,
using the task’s accuracy tolerance to screen for substantial regressions
and shortcuts that bypass model computation.
Fresh deployments also test behavior beyond development state.

 
 Post-run review.

 
 A review agent and human inspection examine submitted code and
recorded actions for checkpoint fidelity, inference semantics, and
workload execution. Review can identify prohibited shortcuts missed by
behavioral tests and overturn automated failures when inspection establishes
compliance with task requirements. These checks determine
score eligibility ( Equation   1 ).

 

 
 4 Evaluation

 
 4.1 Experimental Setup

 
 We evaluate 11 coding-agent models ( Table   1 ): Claude
 ( Anthropic, 2026b ; Anthropic, 2026c ; Anthropic, 2026d ) ,
GPT ( OpenAI, 2026b ) , Kimi ( Kimi Team, 2026 ) , GLM
 ( Z.ai, 2026 ) , DeepSeek ( DeepSeek-AI, 2026 ) , MiMo
 ( Xiaomi MiMo, 2026 ) , and Qwen ( Qwen Team, 2026a ) models.
All use maximum reasoning effort on Qwen3.5 9B ( 2 × 2\times L40), Gemma-4-E4B-it
(Gemma E4B; 1 × 1\times L40), and Qwen3.8 27B INT4 ( 2 × 2\times L40).
In Harbor, GPT models use Codex ( OpenAI, 2026a ) ,
and other models use Claude Code ( Anthropic, 2026a ) .
Each agent–deployment pair allows one 8 hours development run and
a 1,800-second final replay, with at most one rerun for a clearly anomalous
failed outcome.
We report each pair’s strongest verified final submission across the
33 Table   1 entries; development analysis focuses on
30 runs with server execution records.

 
 Baselines are SGLang v0.5.19 and vLLM v0.28.0
 ( Zheng et al., 2024 ; Kwon et al., 2023 ) . SGLang uses each model’s

 4.3 High-Value Designs Coordinate Capacity and Concurrency

 
 Figure 5 : Recorded concurrency paths and final outcomes. Colors mark value relative to
the strongest baseline; labels count runs. Dots below panels mark first
load declarations. 
 
 
 At fixed GPU cost, additional sessions can increase token value but raise
TTFT and TPOT through queueing and contention. Agents must match load
to serving capacity.
 Figure   5 relates recorded concurrency patterns to
final economic outcomes; runs that raise and hold load more often exceed
the strongest reference.
Among runs reaching at least twice the strongest reference, 7 of
17 load decisions improve value on subsequent measurement,
compared with 2 of 23 for verified runs below the reference
score.

 
 Early end-to-end replay gives agents time to develop capacity while
adjusting load. The former group reaches usable replay in a median of
0.90 hours, compared with 2.96 hours for the latter. The optimization
inventory and controlled comparisons in
 Section   10.4 connect these operating decisions
to changes in execution, state management, and scheduling. Higher-value
systems tend to combine more serving optimizations, including speculative
decoding, host-memory state storage, and latency-aware scheduling.
Cross-turn reuse is common to all audited systems.

 
 Controlled comparisons illustrate this distinction. At 16 sessions,
Opus 5.5’s v1 → \to v2 Qwen redesign raises value by 1.32 1.32 – 1.88 × 1.88\times 
on matched seeds. For frozen Gemma systems, Sonnet 5.5 increases value
from 1.30 at two sessions to 2.97 at 32. Sonnet 5.5 also holds four Gemma sessions
while revising the engine, then increases load together with further
implementation changes. The trajectory illustrates capacity development before increasing load.
On Qwen, Opus 5 instead lowers concurrency
from four to two to one as it refines the implementation. Kimi likewise
reduces load to one after identifying long prefills that interfere with
decoding. Load reduction relieves contention; capacity improvements
support more simultaneous work.

 
 Agents estimate the economic operating point in different ways. Opus 5.5
uses a workload simulator to guide Qwen load tests, then retains 16
sessions after a 20-session replay yields more gross value but only
64% qualifying value. Sonnet 5.5 on Gemma compares settings on a fixed
seed: 36 sessions produce more gross value but incur more TPOT
misses, and it submits 32. These decisions match offered load to serving capacity within the latency targets.

 
 4.4 Using Feedback to Guide Optimization

 
 Agents use performance measurements and diagnostic tests to retain,
revise, or abandon changes. Useful feedback requires testing a change
under relevant workload conditions. Costly replays and seed variation
make diagnostic tests and workload analysis essential within the
development budget.

 
 Figure   6 connects retained design decisions to
the tests supporting them. Among runs reaching at least twice the strongest
reference, 49% of retained decisions follow improvements on
workload-relevant tests, versus 25% in failed runs; decisions without
such tests account for 13% and 40%, respectively.
In the other verified groups, 39% remain unconfirmed. These outcomes highlight testing and follow-up when deciding which changes to retain.

 
 Figure 6 : Retained changes more often show workload-relevant gains
in the ≥ 2 × \geq 2\times group (a); representative trajectories show their
follow-up (b). Groups use final value relative to the strongest baseline. 
 
 
 On Gemma, experimental judgment changes whether agents pursue
prompt-lookup speculation. Opus 5 accepts a null result from a synthetic
random-text probe and omits the optimization. Opus 5.5 investigates its
initial null result using 60 replies from replay, repairs its
simulator, and measures 2.09–2.34 accepted tokens per step before adopting
speculation. At a fixed assumed draft cost, a corrected, length-matched
probe selects a smaller draft from synthetic text than from workload replies
( Section   11 ).
To test the effect of this workload feedback on the agent’s decision,
we resume Opus 5 from the same checkpoint for two hours per arm,
with or without feedback from its own replay replies.
Only the feedback arm re-adopts speculation;
its server delivers 1.13 1.13 – 1.31 × 1.31\times the qualified value on two fresh
common seeds. Workload feedback improves the agent’s design decision and
its submitted server’s value.

 
 Favorable feedback can also lead agents to retain a configuration that
performs poorly under other workload conditions. In one Opus 5.5 run on Qwen3.8 27B INT4, the agent raises
concurrency from 10 to 16 and revises scheduling, observing a score
increase from 2.20 to 2.99. It recognizes overload and acknowledges that
changing seeds complicate comparison, but judges the additional value
worth the latency losses. Near the deadline, a scheduling repair remains
in warmup, so it returns to the configuration supported by one completed
900-second replay. In the final replay, the same implementation’s
qualified share falls from 76.0% to 16.8% and its score to 0.48.

 
 Workload coverage can be checked cheaply. Our CPU scan of the
workload generator over 128 additional seeds takes only 7.71 seconds:
the development draw lies near the fourth percentile of initial stream
availability, while the final draw is near the median. The agent had
inspected corpus statistics, yet used an unusually light initial branching
condition to validate its final configuration
( Section   10.5 ).

 
 Null and favorable results both require checking what the test exercises.
Inspecting test inputs and profiling workload variation helps agents
select representative and demanding conditions for costly replay,
supporting decisions to retain, revise, or abandon a design.

 
 4.5 Verification Must Match the Deployed Workload

 
 Verification checks the request boundaries and state transitions affected
by changes to admission, scheduling, and state reuse, including after
subsequent edits. Figure   7 shows sparse coverage
at submission time: only 5 of the 33 entries have recorded checks of
natural stopping on the submitted system under load or long context.

 
 Figure 7 : Workload-relevant checks on submitted implementations (a).
Related symptoms precede submission in 8 of 11 not-passed runs (b);
markers distinguish responses and recorded submission times. 
 
 
 Admission policies require checking which requests can make progress.
On Qwen3.5 9B, Qwen3.8-Max-0902 tightens admission to protect TPOT, then checks
a short prompt and a replay completing 11 requests. Its submitted
policy leaves a range of permitted prompt lengths unable to enter
execution even after other requests finish. Final evaluation stalls on
a 315K-token input in this range. The successful short tests leave the
new policy’s prompt-length boundaries unchecked.

 
 State reuse requires checking behavior across requests. On Qwen3.8 27B
INT4, Kimi’s replay exposes a prefix-cache exception alongside a numerical
error. The agent repairs the numerical path and successfully retests an
isolated long prompt with a fresh engine. A separate check of the
submitted cache succeeds on the first insertion but crashes when the same
prefix is inserted again; the exception also recurs in final evaluation.
The isolated test misses prefix reuse across requests.

 
 Opus 5.5 on Gemma explicitly tests the operating conditions made
relevant by its design. After adding preemption and cache restoration to coordinate TTFT
and TPOT, it reduces cache capacity to force these paths to execute.
The stress test exposes invalid outputs from uninitialized cache storage.
The defect predates the preemption change. The agent repairs cache access,
checks that unused slots filled with NaNs cannot affect valid computation,
and reruns forced preemption while comparing resumed outputs with isolated
execution. The final system retains these repairs. Reduced-pool replication
passes 0/3 tests with the repair reverted and 3/3 after repair.

 
 Reliable delivery requires testing admission boundaries, shared state,
and recovery, then rerunning affected checks after repairs.

 5 Conclusion

 
 ServerBench evaluates agentic design of complete, specialized LLM serving
systems through an economic service objective, stateful closed-loop
replay, and independent verification. Results across three deployments
show substantial gains alongside uneven delivery. Trajectory analysis
and controlled comparisons highlight three priorities: coordinating
capacity improvements with operating load, designing experiments around
workload characteristics and variation, and verifying the execution paths
introduced by system changes.

 
 Limitations

 
 Our evaluation covers three model–hardware deployments and one coding-trace
source. Development and final draws share a corpus; reconstructed inputs
preserve workload structure without reproducing original coding tasks.
Closed-loop replay differs from open-loop production demand, limiting
generalization to other architectures, accelerators, and arrival patterns.

 
 The comparisons characterize measured artifacts. Correlations, source inspection,
and selected trajectories do not establish causal optimization effects or
design success rates. Repeated agent runs and replays are needed to
separate agent variability from workload variability. Version notes record
reported design changes and can omit implementation details. Behavioral tests
and code review have finite coverage, and calibration depends on the reference
engine. Fixed-price token value measures deployment efficiency, excluding
development and other operating costs, rather than realized profit.

 
 Ethical Considerations

 
 Recorded coding sessions can contain sensitive information, and
agent-generated serving code can introduce unsafe behavior. ServerBench
replaces original session content during workload reconstruction and
executes generated code in isolated environments with restricted network
access. Any release of traces or agent trajectories should be reviewed
for sensitive information and comply with source licenses. Post-run code
and action review supports the identification of unauthorized behavior.
Controlled GPU allocations and experiment resource reporting support
responsible use. These controls reduce exposure but do not establish that
arbitrary generated code is safe.

 7 Replay and Reproducibility Record

 
 The replay uses SemiAnalysis’s AgentX ( SemiAnalysis, 2026b ) semianalysisai/cc-traces-weka-062126 coding sessions, with the corpus revision fixed
by the task. It samples session progress under a closed-loop load.
Development and final evaluation use disjoint
seed sets drawn from the same source corpus.

 
 Workload reconstruction and eligibility.

 
 Deterministic reconstruction replaces original prompt and tool contents
while preserving request lengths, shared prefixes, and session topology.
Replay uses recorded end-to-start delays and session dependencies,
including parallel subagent branches. When no requests are in flight,
global idle gaps are capped at 10 seconds by moving all pending timed
events earlier by the same amount, preserving their relative spacing, order,
and dependency constraints. Context eligibility is fixed before development; where necessary,
whole traces are filtered to preserve dependencies without allowing
candidates to truncate prompts. State reuse must preserve all required
states, including recurrent state where applicable.

 
 Development and deployment.

 
 The Transformers starter uses a global request lock and has no cross-request
prefix cache. Agents may change scheduling, batching, memory management,
kernels, parallel execution, and state reuse. Reference configurations
support comparison without prescribing the candidate architecture.
Harbor supports container or Modal backends; evaluation components remain
outside the editable server. Full development tests launch frozen snapshots,
while lightweight checks support shorter experiments. Publishing a version
and measuring its performance are separate operations. Portability checks
test compatibility with the deployment interface. After the final workload
replay, protocol and output tests run while the server remains active.
Final evaluation uses the frozen submission after the development budget ends.

 
 Reproduction record.

 
 Reproduction requires the effective checkpoint and inference configuration,
task and corpus revisions, environment snapshot, agent model identifier and
scaffold, development budget, submitted artifact, chosen
concurrency, and replay seeds. Immutable version records connect intermediate
measurements to code; final results are associated with the submitted artifact.
The record separates construction runs from repeated replays of each
frozen system.

 9 Integrity Review and Agent Configuration

 
 The task prompt fixes model semantics and prohibits reducing work through
truncation, approximate computation, precision reduction, answer retrieval,
or model substitution. It also prohibits identifying evaluation probes to

evaluation components. Computed-state reuse that preserves the specified
semantics is admissible.

 
 The prompt announces post-run review of code and recorded actions by a
separate agent. The review examines the submitted implementation,
version changes, commands, and measurement records. Automated checks
record reported model identifiers, network destinations, and
commands indicating potential undeclared model use. These records support
code inspection alongside the final execution checks.
Human review complements these automated assessments when evaluating
suspected correctness failures and prohibited shortcuts.
Only maximum-reasoning-effort configurations appear in the main comparison; full execution
identifiers belong in the campaign reproducibility record.

 11.3 Verification and Repair

 
 Opus 5.5’s Gemma cache repair masks invalid cache loads, initializes cache
pools, and uses NaN-safe argmax. The full repair passes the 420-page
concurrent check (1/1), all three 330-page checks exercising preemption
and recovery (3/3), and the 330-page check with preemption disabled (1/1).
The submitted v7 also passes all three targeted checks (3/3).
Masking invalid cache loads and zeroing cache pools each passes its
targeted attempt; the full repair passes all three repetitions.
These checks verify correct outputs while exercising the server’s cache
management and recovery paths.
