 RaMP: Runtime-Aware Megakernel Polymorphism
 for Mixture-of-Experts 

   
 
 Vyom Sharma   1  
 Debajyoti Datta   1  

 † † footnotetext: 1 Hippocratic AI.
Correspondence to: Vyom Sharma <vyom@hippocraticai.com>.
 
 Preprint. 
 Abstract

 
 LLM serving systems autotune their GPU kernels offline by timing candidate kernel configurations, like tile sizes, at a range
of batch sizes. This works when
the number of tokens determines a kernel’s work, as in dense layers. However, we show that it does not hold for
Mixture-of-Experts (MoE) layers where the router decides how the tokens are split across experts
and GPUs. We find that the best kernel configuration depends on this split, and not
only on the number of tokens—under expert parallelism, choosing the configuration for each GPU’s actual
token distribution is up to 1.45 × \times faster than the existing choice. The split is not known until the router runs, so it cannot be looked up in advance. Hence, we introduce RaMP, which chooses the kernel configuration at run time from the routing split itself. RaMP compiles top configurations into one polymorphic kernel, and a small cost model on the GPU picks among them in a few microseconds. On serving traffic its cost model was never fit on, the configurations RaMP’s cost model chooses from the kernel’s full configuration space are up to 1.45 × \times faster than those vLLM’s offline autotuner picks for the same kernel on batches of 128 tokens or more (1.27 × \times over all batches), and within 3.5% of an exhaustive search that times every configuration. RaMP’s kernel and choice together make the MoE layer up to 1.84 × \times faster than vLLM’s Triton MoE on batches of 128 tokens or more. In vLLM,
under both tensor and expert parallelism, RaMP lowers time per output token by up to 1.11 × \times over the fastest stock MoE backend.

 

 
 1 Introduction

 
 Figure 1: Before and after RaMP , on three GPUs of one batch (illustrative loads). Today every GPU runs the tile
size chosen from the batch size. RaMP chooses per GPU: smaller tiles waste fewer rows where experts
receive few tokens, and larger tiles halve the tiles where they receive many. 
 
 
 Many of the largest recent language models are Mixture-of-Experts (MoE)
models  ( Shazeer et al., 2017 ; DeepSeek-AI et al., 2024 ; Yang et al., 2025 ; Jiang et al., 2024 ) . Each MoE layer holds many
experts, and a router sends each token to a few of them, so a megakernel computes all experts’
matrix multiplications on whatever tokens each one received  ( Kwon et al., 2023 ; Gale et al., 2023 ) . Large MoEs are
served with tensor parallelism (TP), which splits every expert across the GPUs, or with expert
parallelism (EP), which places whole experts on different GPUs  ( Shoeybi et al., 2019 ; Lepikhin et al., 2021 ; Rajbhandari et al., 2022 ) .

 
 Like any GPU kernel, the MoE kernel is fastest when its configuration, such as its tile sizes, fits
its work. For a dense layer, the work is set by the batch. For an MoE layer, it is set by the batch
 and by how balanced the routing is: how evenly the router spreads the batch’s tokens across
experts and, under EP, across GPUs. Both change throughout serving. Continuous
batching  ( Yu et al., 2022 ) changes the batch on every forward pass, and a production server receives
requests from many domains, which the router treats differently. In traces from vLLM serving eight
MoE models, a few experts often receive several times their even share, and which experts these
are changes with the requests in the batch.

 
 Serving systems nevertheless choose the configuration offline, from the batch size alone:
vLLM  ( Kwon et al., 2023 ) tunes the kernel at a fixed set of batch sizes on uniformly random routing and
uses the nearest entry at run time. When routing is unbalanced, that entry is often the wrong one:
under EP, the best configuration for each GPU is up to 1.45 × \times faster than vLLM’s tuning.

 
 The core problem is to choose from each GPU’s expert load in real time. A batch’s routing exists only
after the router runs, on the GPU, just before the kernel must start. Each configuration is a
separately compiled kernel chosen before the layer runs, and timing candidates on every batch would
take far longer than the kernel itself. Systems that adapt MoE execution at run time change the
parallelism or the expert placement  ( Hwang et al., 2023 ; DeepSeek-AI, 2025b ) , not the kernel configuration.

 
 Therefore, we introduce RaMP, which chooses the MoE kernel configuration on every GPU, for every
forward pass, from the routing that GPU actually receives (Figure  1 ). RaMP compiles many configurations into
one polymorphic kernel that reads which one to run from GPU memory, so switching between them needs
no new launch and costs about 1%.
A small cost model ranks the configurations from the work the GPU’s tokens produce, and
the GPU picks the best in a few microseconds, so the choice adds almost no latency.

 
 On serving traffic the cost model was never fit on, the configurations it chooses from the kernel’s full configuration space are up to
1.45 × \times faster than those of vLLM’s tuning for the same kernel on batches of 128 tokens or more
(up to 1.27 × \times over all batches), and within 3.5% of exhaustive search, an oracle that times every
configuration, on every EP layout we test. Its kernel and choice together make the MoE layer up to 1.84 × \times faster than vLLM’s Triton MoE on batches of 128 tokens or more. Its kernel is also the fastest MoE backend we measure: end to end in
vLLM, under both TP and EP, RaMP lowers time per output token at every load we test, by up to
1.11 × \times over the fastest stock backend on DeepSeek-V3, Qwen3-30B, and OLMoE, with unchanged model
quality.

 
 In summary, we make two contributions that rely on each other:

 
 • 
 
 A cost model, fit offline, that ranks kernel configurations from each GPU’s current routing
at run time, cheaply enough to run on the GPU on every forward pass; and

 • 
 
 A polymorphic MoE megakernel that compiles a menu of configurations, drawn from 98–337
per model, into one kernel and runs whichever one the GPU chooses, written in CuTe
DSL  ( NVIDIA, 2024 ) .

 

 
 2 Background

 
 2.1 MoE Geometry During Inference

 
 An MoE layer replaces the dense MLP with E E experts, and a router sends each token to k k of
them  ( Shazeer et al., 2017 ; Lepikhin et al., 2021 ) . Each expert is a gated MLP: it multiplies the tokens
it receives by a d × 2 ​ h d\times 2h matrix for the gate and up projections and an h × d h\times d matrix for the down projection, where d d is the hidden size and
 h h the expert’s intermediate size. This geometry varies widely across models: Mixtral-8x22B has 8
experts with h = 16,384 h=16{,}384 , while Qwen3.5-35B has 256 experts with h = 512 h=512 .

 
 How the model is spread over GPUs sets the geometry each GPU sees. On G G GPUs, tensor parallelism
(TP)  ( Shoeybi et al., 2019 ) gives every GPU all E E experts, each cut to width h / G h/G , and sums the
partial outputs with an all-reduce. Expert parallelism (EP)  ( Lepikhin et al., 2021 ; Rajbhandari et al., 2022 ) gives every
GPU E / G E/G whole experts and exchanges tokens with an all-to-all before and after the layer; it has
become a common way to serve the largest MoEs  ( DeepSeek-AI et al., 2024 ; DeepSeek-AI, 2025b ) . We write EP8 for EP over 8
GPUs. Either way, each GPU holds a fixed set of experts ℰ g \mathcal{E}_{g} with fixed weight shapes.
What it does not know in advance is how many tokens each of them will receive.

 
 2.2 GPU Kernels on This Geometry

 
 An MoE megakernel computes all of a GPU’s experts in one launch  ( Kwon et al., 2023 ; Gale et al., 2023 ) . Like any
matrix multiplication on a GPU, it cuts its output into tiles. Each tile goes to a
thread block on one of the GPU’s streaming multiprocessors (SMs; H200 has 132), which streams
slices of both inputs from memory into shared memory and accumulates the tile on the tensor
cores  ( NVIDIA, 2024 ) . The tile sizes decide how well this works. A larger tile reuses every value
it loads across more of the output, so it reads less memory per operation, but it needs more
shared memory and registers, fewer tiles fit on an SM at once, and a small product yields too few
tiles to keep every SM busy. Whether a kernel is limited by memory or by arithmetic depends on how
many output rows share each loaded weight  ( Williams et al., 2009 ) , so the best tile sizes change with the
shape of the product, and the wrong ones are costly. Across the eight models we study, the tile
sizes that are fastest on batches of fewer than 32 tokens run 1.7–6.1 × \times slower than the best ones
on batches of 512 tokens or more.

product are the n e n_{e} tokens routed to expert e e . The kernel cuts them into tiles of b c b_{c} rows
and pads the last one: an expert with 5 tokens and b c = 16 b_{c}=16 fills one tile and pads 11 rows

 Routing matters to the kernel because it decides how the tokens fill tiles. Consider two GPUs that
each hold 16 experts and receive 128 tokens. On the first, routing is balanced and every expert
receives 8 tokens: 8-row tiles are exactly full, while 32-row tiles are three-quarters padding. On
the second, four experts receive 30 tokens each and eight others receive
one token each: 8-row tiles now
cut each busy expert into four tiles, and each tile reads that expert’s weights again, while one
32-row tile per expert reads them once. Both GPUs have the same number of tokens, and Equation  1 
favors a different configuration on each. Under EP this happens on every forward pass, on every
GPU, and the slowest GPU sets the layer’s time.
Whether a given change in the load moves the best configuration, and by how much, depends on the
geometry and on the batch.

 
 Real serving shows the same effect. In one recorded batch of 256 tokens of Qwen3-30B on EP8, the
GPUs’ fastest configurations range from 6- to 32-row tiles and grow with the
tokens each GPU receives, while vLLM’s tuning gives every GPU 24-row tiles. Across
seven models on EP8, the eight GPUs of a batch with 128 or more tokens need 4–6 different
configurations on average, and in at most 16% of these batches is a single configuration best on
every GPU.

 
 2.4 Choosing a Configuration

 
 MoE serving systems, like most GPU kernels, choose the configuration offline
(Section  5 ). vLLM’s tuner times every
configuration at 18 batch sizes, from 1 to 4,096 tokens, on random router scores that make every
expert equally likely, and keeps the fastest for each. At run time, vLLM’s tuning uses the
entry nearest the current batch size, on every GPU. DeepGEMM chooses its tiles with a heuristic over the matrix
shape, and FlashInfer profiles its kernels over a range of token counts  ( DeepSeek-AI, 2025a ; FlashInfer Team, 2025 ) .
Each is a function of the batch size alone, shared by every GPU.

 
 Let 𝒞 \mathcal{C} be the configurations a kernel supports, and t c ​ ( 𝐧 g ) t_{c}(\mathbf{n}_{g}) the kernel’s time
under configuration c c on load 𝐧 g \mathbf{n}_{g} . The layer waits for the slowest GPU, and each GPU’s
configuration affects only its own time, so the layer is fastest when every GPU runs the best
configuration for its own load:

 

 
 
 t layer = max g ⁡ t c g ​ ( 𝐧 g ) , c g ⋆ = arg ​ min c ∈ 𝒞 ⁡ t c ​ ( 𝐧 g ) . t_{\mathrm{layer}}=\max_{g}\,t_{c_{g}}(\mathbf{n}_{g}),\qquad c_{g}^{\star}=\operatorname*{arg\,min}_{c\in\mathcal{C}}\;t_{c}(\mathbf{n}_{g}). 
 
 (2) 
 
 
 Timing every configuration on each GPU’s actual load and keeping the fastest finds c g ⋆ c_{g}^{\star} ;
we call this exhaustive search , the oracle against which every choice in this paper is
measured. It is a reference, not a method: it runs every candidate on every batch.
The batch size does not determine 𝐧 g \mathbf{n}_{g} : many loads share one B B , and under EP each GPU
receives a different one. A function of B B alone therefore cannot follow a change in c g ⋆ c_{g}^{\star} 
that routing causes. Not every change in the load moves c g ⋆ c_{g}^{\star} , and different configurations
can take almost the same time, so how much this costs is an empirical question. On batches of 128 tokens or more,
giving each GPU its own best configuration is up to 1.45 × \times faster than vLLM’s tuning, and the gap
is largest when each GPU holds few experts (Section  4 ).

 
 Solving Equation  2 at run time is constrained in three ways. First, 𝐧 g \mathbf{n}_{g} is
known only after routing, and only on GPU g g . Second, the choice is made on every forward pass, so
it must take far less time than the kernel, and t c ​ ( 𝐧 g ) t_{c}(\mathbf{n}_{g}) cannot be measured; it must be
predicted from 𝐧 g \mathbf{n}_{g} alone. Third, serving systems capture each forward pass in a CUDA graph, which records every kernel and
its launch parameters once and replays them, so that the CPU does not launch kernels one by
one  ( Kwon et al., 2023 ) . A configuration chosen after routing therefore cannot be a different kernel; the
captured kernel itself must be able to run any c ∈ 𝒞 c\in\mathcal{C} .

 
 3 RaMP

 
 RaMP solves Equation  2 on every GPU, after routing, inside the captured forward pass. It replaces measurement with a prediction that only has to rank the
configurations (Section  3.1 ), makes the choice in the kernel that already groups
tokens by expert (Section  3.2 ), and runs the choice in one kernel that holds every
candidate (Section  3.3 ). Each part answers one constraint of Section  2.4 :
the time must be predicted, the load exists only on the GPU, and the captured forward pass fixes the
kernel.

 
 3.1 The Cost Model

 
 Choosing c g ⋆ c_{g}^{\star} exactly requires t c ​ ( 𝐧 g ) t_{c}(\mathbf{n}_{g}) for every configuration, and only
running the kernel gives it. The obvious substitutes fall short. Timing the candidates on the live
load would cost more than the kernel itself. A per-GPU table, indexed by each GPU’s token count, is cheap, but
it treats two loads with the same count as the same work, which Section  2.3 showed
they are not. It is also tied to one layout: at another EP degree, the same count spreads over a
different number of experts.

 
 Choosing does not need the time, only the order of the times, and that order is set by a few counts
that the load determines and the configuration fixes. Consider how the kernel spends its time. All
tiles of a configuration have the same shape, and a padded tile does as much work as a full one, so
the work is set by the tiles the kernel launches rather than by the tokens it receives. While the GPU
is full, tiles run S c S_{c} at a time, so the time follows the waves W c W_{c} , and a nearly empty last wave
costs as much as a full one. Each tile also moves a slice of its expert’s weights and a block of
token rows, traffic that grows with the tiles T c T_{c} . That traffic has a floor: every expert that
receives a token must have its weights read at least once, however its tokens are tiled, and this
floor dominates small batches, where the kernel waits on memory. What remains is the fixed cost of a
launch. RaMP therefore predicts each configuration’s time as

 3.3 The Kernel

 
 The captured forward pass fixes which kernel runs after the selection kernel. One way to branch
anyway is a conditional node, which picks a kernel from a value in GPU memory. Each costs about
8.4  μ \mu s per layer, or about 0.4 ms per decode forward pass across Qwen3-30B’s 48 MoE layers,
more than the choice could save on a small batch. But the graph fixes only which kernel runs and its
launch shape, not what the kernel does.

 
 RaMP therefore compiles every menu entry into one polymorphic kernel. Each thread block reads
 c ^ g \hat{c}_{g} from GPU memory and runs that entry’s code. Holding many entries in one kernel has two
costs, and both are small. The grid is sized for the largest tile count any entry can produce, and
blocks beyond the chosen entry’s count exit at once, which costs 0.2%. All entries share one
shared-memory buffer, so the menu is drawn from one occupancy class; within it, each entry runs at
1.00 × \times its standalone time on a menu of three and at a median of 1.01 × \times on a menu of six. Six
entries are enough: they capture nearly all of the choice’s benefit, within 1–2% of a menu of
twelve at the MoE layer, while keeping every entry’s shared memory and registers close to its own.

 
 A choice is only as good as what it can choose from. The kernel is written in CuTe
DSL  ( NVIDIA, 2024 ) and computes both expert matrix multiplications and the gated activation in one
launch, in FP8 with 128 × 128 128\times 128 block scaling as used by DeepSeek-V3  ( DeepSeek-AI et al., 2024 ) . Its
configuration space covers 2 to 64 rows per tile, tile width, pipeline depth, persistent and grouped
launch orders, and split-K for large reduction dimensions: 98–337 valid configurations per model
and layout.
Appendix  A.8 describes its construction, and we will release the kernel at a later date.

 
 4 Evaluation

 
 This section evaluates RaMP on real MoE serving traffic, first end to end in vLLM and then down to
the configuration each GPU chooses. On serving traffic its cost model was never fit on, the configurations it chooses from the full configuration space are up to 1.45 × \times faster than vLLM’s tuning on batches of 128 tokens or more (up to 1.27 × \times over all batches), and within 3.5% of exhaustive search on every EP layout. Its kernel and choice together make the MoE layer up to 1.84 × \times faster than vLLM’s Triton MoE on batches of 128 tokens or more, and in vLLM, under TP and EP, it
lowers time per output token at every load we test, by up to 1.11 × \times over the fastest stock backend.

and with the share of large batches, as Section  4.2 shows: on open-loop traffic at
EP32, RaMP is 1.18–1.22 × \times faster than vLLM’s tuning on the same kernel.

 
 4.2 Where the Speedup Comes From

 
 The end-to-end gain has two sources, RaMP’s kernel and the configuration it chooses for each GPU.
We separate them at the MoE layer, then test the choice on its own.

 What pays is choosing from each GPU’s own load, which no policy keyed on the batch size can do. Even the simplest
such policy, a per-GPU table, needs RaMP’s mechanism, since the count exists only on the GPU after
routing; at the EP degree it was tuned for, it comes within 3% of RaMP. The cost model adds two
things a table cannot. How the tokens spread over a GPU’s experts adds up to 1.07 × \times on batches of
128 tokens or more at EP16 and EP32. And the cost model carries over to new layouts: a per-GPU table
tuned at a model’s other EP degrees is 1.09 × \times from exhaustive search, against 1.04 × \times at its own
degree, while the cost model, with the layer’s dimensions added to its terms and fit on seven
models, is within 1.9% of exhaustive search on the eighth (geometric mean).

 
 Why the cost model works. It ranks configurations almost exactly, with a rank correlation of
0.97–0.99 with the measured order, which is all the choice uses. Its terms matter: a formula built
from the tile count alone (the tiles, the tiles per SM, and their logarithm, fit by ordinary least
squares) is 6.7% from exhaustive search on batches of 128 tokens or more, against 1.3% for
Equation  3 (geometric mean over 18 EP layouts). Nor can a table keyed on the same inputs
replace it: over the 21 EP layouts of Appendix  A.2 , tables keyed on a GPU’s token
count and a measure of its balance, such as its padding or active experts, are 3.1–4.8% from
exhaustive search on these batches, against 1.4% for the cost model,
because a few buckets lose how each expert’s tokens fill tiles and waves. The model’s rare mispicks fall on GPUs that seldom set the layer’s latency;
removing them changes the result by under 0.1%.

 
 When the choice matters. When every GPU holds every expert, each GPU computes the whole batch’s routing,
and at a given batch size the best configuration changes little. This is the case offline
tuning was built for, and RaMP’s choice matches the trace-tuned table to within 2%, while its MoE
layer is 1.09–1.17 × \times faster than vLLM’s Triton MoE (Table  11 ). Balanced expert placement
does not remove the imbalance under EP, because the most loaded experts change from batch to batch.
It lowers the imbalance by at most 11 percentage points, and RaMP’s gain is unchanged, within its 95%
interval, on all six layouts we test (Table  8 ). Even re-balancing every 128
forward passes leaves the most loaded GPU 11–56% above the mean on EP8 (Table  7 ).

 
 The choice pays most as each GPU holds fewer experts. On Qwen3-30B, the most loaded GPU holds 52% more
than the mean at EP8 and 188% more at EP32, and RaMP’s gain over the trace-tuned table on held-out
batches of 128 tokens or more grows from 1.14 × \times to 1.32 × \times ; on DeepSeek-V3, the excess grows from
45% to 132% and the gain from 1.00 × \times to 1.15 × \times (Tables  6 and  5 ). It also grows with
the share of large batches, which open-loop traffic carries far more of than the recorded traffic: on
Qwen3-30B, 14–52% of forward passes carry 128 tokens or more under open-loop arrivals, against
4%. Weighted by the open-loop mix at 32 requests per second, RaMP’s gain over vLLM’s tuning on the
MoE layer is 1.16–1.23 × \times on four of six EP layouts, close to that of exhaustive search.

 
 5 Related Work

 
 MoE kernels. MoE megakernels and grouped kernels include vLLM’s Triton MoE  ( Kwon et al., 2023 ; Tillet et al., 2019 ) ,
MegaBlocks  ( Gale et al., 2023 ) , ScatterMoE  ( Tan et al., 2024 ) , DeepGEMM  ( DeepSeek-AI, 2025a ) ,
FlashInfer’s CUTLASS path  ( FlashInfer Team, 2025 ; NVIDIA, 2024 ) , Alpha-MoE  ( Aleph Alpha, 2025 ) , and
SonicMoE  ( Guo et al., 2025 ) . They differ in how they gather tokens, fuse the activation, and overlap
memory with compute; MegaBlocks, for example, casts the layer as a block-sparse product with a
fixed 128 × 128 128\times 128 block, chosen by benchmarking dense matrix multiplications before any routing
exists. These works make one kernel faster and choose its configuration
statically or from the batch size. RaMP instead chooses which configuration to run for each GPU on
every forward pass, and the same choice applies to any kernel that exposes several configurations.

 
 Load balance and placement. Training adds capacity limits and auxiliary losses that push
the router toward balance  ( Lepikhin et al., 2021 ; Fedus et al., 2022 ) ; FasterMoE replicates popular experts during
training  ( He et al., 2022 ) , and Tutel switches the parallelism strategy at every iteration to follow
the changing load  ( Hwang et al., 2023 ) . At serving time, DeepSeek-V3 replicates popular
experts  ( DeepSeek-AI et al., 2024 ; DeepSeek-AI, 2025b ) , and Huang et al. (2023) buffer and rebalance experts. These methods reduce the imbalance between GPUs by deciding where experts
and tokens go. RaMP handles what they leave: the imbalance that remains from batch to batch, which
balanced placement lowers by at most 11 percentage points, and the imbalance among each GPU’s own experts, which no
placement sees. It runs on whatever placement they produce.

 
 Autotuning and run-time kernel selection. Halide, TVM, Ansor, and AutoTVM search
configuration spaces offline, guided by measurements or a learned cost
model  ( Ragan-Kelley et al., 2013 ; Chen et al., 2018a ; Zheng et al., 2020 ; Chen et al., 2018b ) ; like
RaMP’s, AutoTVM’s model needs only to rank candidates. Triton autotunes kernels for each input
shape  ( Tillet et al., 2019 ) , and DeepGEMM chooses tiles from the matrix shape  ( DeepSeek-AI, 2025a ) .
DietCode  ( Zheng et al., 2022 ) is the closest: it compiles micro-kernels for dynamic shapes, uses a
cost model offline to choose among them for each shape, and dispatches at run time with a decision
tree trained on those choices. In all of these, the input to the choice is a
shape that the CPU knows before the kernel launches. For an MoE layer, the deciding input is a
vector, each GPU’s per-expert load, and it exists only on that GPU, after routing, in the middle of
the captured forward pass. RaMP therefore evaluates a closed-form ranking model on the GPU and
switches configurations inside one polymorphic kernel, with no CPU involved.

 
 Serving and batching. Continuous batching  ( Yu et al., 2022 ) , paged attention  ( Kwon et al., 2023 ) ,
chunked prefill  ( Agrawal et al., 2024 ) , and structured programs  ( Zheng et al., 2024 ) decide how many tokens each
forward pass carries. They treat the batch size as the kernel’s problem size; for an MoE layer, the
router changes the problem again before the kernel runs.

 
 6 Limitations

 
 RaMP is evaluated on one node of eight H200 GPUs. EP16 and EP32 replay each GPU’s recorded load
without the exchange of tokens between GPUs; serving them across nodes, where each GPU holds the
fewest experts and the choice pays most, is the natural next step. On one node, RaMP’s end-to-end gain comes mostly from its kernel; the
choice pays most at higher EP degrees, which we evaluate by replay. We evaluate FP8 with 128 × 128 128\times 128 block scaling in
vLLM; other precisions, GPU generations, and serving systems are left to future work.

 
 The cost model counts the tiles, waves, and active experts a configuration produces, but a kernel
can apply further optimizations whose cost these counts do not capture: the reduction of split-K’s
partial results, tile orders chosen for L2 reuse, separate tile shapes for the up and down
projections, and two-CTA matrix multiplications on newer GPUs. How the cost model should account
for these optimizations, and how they interact with routing, is a direction for future research.

 
 7 Conclusion

 
 Serving systems choose an MoE kernel’s configuration from the batch size, but the router decides how
the batch’s tokens split across experts and GPUs, and the best configuration follows that split.
RaMP makes the choice where the split is known: on each GPU, after routing, on every forward pass. A
cost model ranks the configurations from each GPU’s load, and a polymorphic kernel runs whichever
one it picks. On serving traffic the model was never fit on, the configurations it chooses from the full configuration space are up to 1.45 × \times faster than vLLM’s tuning on batches of 128 tokens or more and within 3.5% of exhaustive search over all batches,
and in vLLM RaMP lowers time per output token by up to 1.11 × \times over the fastest stock backend under
both TP and EP. As expert-parallel serving spreads models over more GPUs, each GPU holds fewer
experts, its share of the batch grows less balanced, and choosing from routing pays more.

 A.1 The Cost Model on Held-Out Loads

 
 Figure  6 shows the cost model of Section  3.1 on loads from a
domain it was not fit on, for Qwen3-30B on EP8. Its terms account for the measured time across four
orders of magnitude of load: the waves carry most of the time and set its steps, the tiles add the
traffic that grows with the load, and the fixed cost and the active experts set the floor at small
loads (a). Over every configuration, its predictions order the measured times with a rank
correlation of 0.99 (b). On two GPUs of one batch, it picks the fastest tile size on both: 2-row tiles for the least loaded GPU
and 32-row tiles for the most loaded one (c).

 
 Figure 6: The cost model on held-out loads , Qwen3-30B on EP8. (a) Each term’s share of the
predicted time for one configuration, and the measured time. (b) Predicted against measured time
for every configuration. (c) Measured and predicted time of each tile size on the least and most
loaded GPU of one batch, relative to the best; stars mark the configuration the model picks.

 A.8 The Polymorphic Megakernel

 
 RaMP’s kernel is written in CuTe DSL  ( NVIDIA, 2024 ) for Hopper and runs both expert projections of
a GPU’s experts in one launch.

 
 Operand layout. Both projections use FP8 WGMMA instructions with FP32 accumulation. The
expert’s weights are the A operand, 64 output columns per instruction, and a tile’s tokens are the
B operand, so the tokens of a tile form the instruction’s N dimension. Both operands are K-major in
128-byte-swizzled shared memory, and one weight layout serves both projections. A thread block
covers 256 or 512 output columns with one producer warpgroup, which loads operands, and several
consumer warpgroups, which compute; setmaxnreg moves registers from the producer to the
consumers.

 
 Fusion. Each tile runs in three phases. In the up-projection, the producer gathers the
tile’s token rows in the layout the selection kernel wrote and loads the interleaved gate and up
weights with TMA, and the consumers multiply and apply the 128 × 128 128\times 128 block scales. In
registers, the consumers then compute the gated activation, quantize it to FP8 with a per-token
scale that also folds in the router’s weight, and store it to shared memory. In the
down-projection, TMA loads the down-projection weights, the consumers multiply the FP8
intermediate, and the BF16 result is added into the layer’s output with bulk asynchronous
reductions.

 
 Polymorphism. Every menu entry is compiled into the same kernel, which branches on the
index the selection kernel writes. Entries share the thread-block size and may differ in rows per
tile, pipeline depth, tile width, persistence, and launch order; the served menus use one tile
width. The grid covers every entry’s tiles, and blocks outside the chosen entry’s grid exit at
once. All entries share one shared-memory buffer, sized for the largest entry, and one register count
that covers every entry (Table  12 ).
