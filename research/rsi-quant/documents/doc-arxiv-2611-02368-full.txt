 Abstract

 
 Agents are increasingly used for coding tasks, but the inference cost of large language models (LLMs) limits where they can run. Quantization reduces model size, but its effects on coding agents that execute and revise programs remain underexplored. We compare BF16 with 4-bit AWQ and GPTQ for Qwen2.5-Coder-Instruct (7B, 14B, and 32B) and Devstral-Small-2507 (24B) on OJBench coding problems across three seeds. We detect no statistically significant accuracy loss for any of the coding agents. However, final accuracy can conceal substantial behavioral changes: AWQ reduces Qwen-7B one-shot solves from 17 to 0 while increasing loop-based solves from 10 to 25. All Qwen-32B successes involve tool use, whereas Devstral rarely makes a valid executor call. Failure profiles also differ: Qwen-32B produces far more compilation errors than the smaller Qwen models, rising slightly under quantization, while Devstral’s failures shift significantly from runtime errors toward wrong answers and timeouts. These findings indicate that quantization robustness in coding agents should be assessed through solution trajectories, tool use, and failure modes, in addition to final accuracy.

 

 
 1 Introduction

 
 Large Language Models (LLMs) ( Jaech et al., 2024 ; Team et al., 2025 ) are increasingly used in agentic coding systems that go beyond single-pass text generation. These agents can invoke execution tools, inspect program outputs, and revise their solutions over multiple steps ( Hong et al., 2025 ; Guo et al., 2024 ; Lai et al., 2023 ; Chen et al., 2024 ) . This interaction changes how coding capability should be evaluated: a model that produces an incorrect program initially may still reach a correct solution after execution feedback. Recent benchmarks such as OJBench ( Wang et al., 2025 ) provide challenging settings for studying this behavior. OJBench contains competition-level programming problems and places greater emphasis on reasoning and code correctness than typical interview-style benchmarks.

 
 Efficient deployment of these agents remains challenging because repeated LLM inference and tool interaction increase computational and memory costs. Quantization is a widely used approach for reducing these costs ( Frantar et al., 2023 ; Xiao et al., 2023 ; Liu et al., 2024 ) . In particular, weight-only methods such as AWQ and GPTQ can substantially reduce model storage while retaining high-precision activations. However, reasoning performance can be sensitive to low-bit quantization, especially on difficult tasks where small perturbations can affect multi-step generation ( Liu et al., 2025 ) . Most existing studies evaluate this effect using single-pass model outputs. Coding agents introduce a different setting because quantization can influence not only the generated program, but also tool invocation, iterative refinement, and the final failure mode.

 
 This distinction raises an important question: does similar final accuracy imply that a quantized coding agent behaves similarly to its full-precision counterpart? Our results suggest that it does not. Quantization can preserve final accuracy while changing solve trajectories, tool-use patterns, and terminal failure modes. These effects are hidden when coding agents are evaluated only by their final score. In this work, we present, to the best of our knowledge, the first empirical study of 4-bit weight-only quantization in execution-feedback coding agents. We evaluate BF16, AWQ, and GPTQ versions of Qwen2.5-Coder-Instruct ( Hui et al., 2024 ) at 7B, 14B, and 32B scales, together with Devstral-Small-2507 ( Mistral AI, 2025 ) . All models use vLLM with an OpenAI-compatible tool schema and a Python execution tool and are evaluated over three random seeds on OJBench. We investigate three research questions:

 
 RQ1: How robust is end-to-end coding-agent performance to 4-bit quantization?

 
 RQ2: Does end-to-end accuracy conceal changes in coding-agent solution trajectories?

 
 RQ3: Does quantization change how coding agents fail, not just how often?

 2 Related Work

 
 Recent work on coding agents extends single-pass code generation by incorporating program execution and iterative revision. Studies on self-debugging show that LLMs can use execution feedback to identify and correct errors in generated programs ( Chen et al., 2024 ) . Existing evaluations cover real-world data-science tasks through DSBC ( Kadiyala et al., 2025 ) , automated program repair ( Puvvadi et al., 2025 ) , interactive application environments such as AppWorld ( Trivedi et al., 2024 ) , multilingual repository-level tasks through SWE-PolyBench ( Rashid et al., 2025 ) , and competition-level programming through OJBench ( Wang et al., 2025 ) .
AWQ ( Lin et al., 2024 ) and GPTQ ( Frantar et al., 2023 ) are widely used methods for 4-bit weight-only quantization. Prior single-pass studies indicate that quantization generally preserves reasoning performance, although smaller models and more difficult tasks experience greater degradation ( Liu et al., 2025 ) . However, these studies do not examine how quantization affects coding agents that can execute and revise their outputs. We address this gap by asking whether the execution loop absorbs quantization-induced errors, and whether the size–robustness ordering observed in single-pass settings still holds when the agent can run its code.

 
 3 Experimental Setup

 
 This section describes the setup used to evaluate BF16 and AWQ/GPTQ 4-bit quantized models on competitive coding tasks within an execution-based agentic workflow.

 
 3.1 Dataset: OJBench

 
 We evaluate on OJBench ( Wang et al., 2025 ) , a benchmark of 232 competition-level problems from China’s National Olympiad in Informatics (NOI) and the International Collegiate Programming Contest (ICPC). OJBench supports solutions in both Python and C++; we use Python only, so all solutions are written, executed, and judged in Python. We use all 115 Easy and Medium problems because all model–precision configurations scored 0% on Hard. Evaluation across three seeds yields 345 problem–seed observations per configuration.

 
 3.2 Evaluation Setup

 
 Models and Quantization We evaluate Qwen2.5-Coder-Instruct ( Hui et al., 2024 ) at 7B, 14B, and 32B, spanning scales at which size may interact with quantization, plus the agent-oriented 24B Devstral-Small-2507 ( Mistral AI, 2025 ) as an out-of-family comparison. Each model is run at BF16 and as W4A16 variants produced with AWQ ( Lin et al., 2024 ) and GPTQ ( Frantar et al., 2023 ) via llmcompressor ( AI and vLLM Project, 2024 ) (256 calibration samples, max sequence length 1,024).

 
 Agent Framework. Each model is served with vLLM in a multi-turn execution-feedback loop using an OpenAI-compatible tool schema, with tool calls parsed from the generated text. The agent has one tool, python_executor(code, stdin) . It writes code, tests it on the problem’s examples, reads the feedback, and revises for up to five tool calls per problem. All runs use nucleus sampling (temperature 0.6 0.6 , top- p p 0.9 0.9 ), 32,768 32{,}768 -token context, and three seeds. Full prompt and loop in Appendices  A.3 and  A.4 .

 
 Evaluation Metrics. Accuracy is the proportion of final programs passing all official OJBench test cases. Each failed attempt is assigned one terminal category: Invalid Return (IR; runtime exception), Wrong Answer (WA), Time Limit Exceeded (TLE), Compilation Error (CE), or Memory Limit Exceeded (MLE). We also record tool calls per problem, distinguishing one-shot solves (no tool calls) from loop-based solves (at least one execution round). Because every precision is evaluated on the same problems and seeds, outcomes are paired; we apply an exact two-sided McNemar test to the 345 paired observations, with b b and c c the discordant pairs solved by only the first or only the second precision, and p < 0.05 p<0.05 as the threshold. For the behavioral measures, we use Fisher’s exact test for solve paths and tool-use rates, and a chi-square test for failure distributions. Because each analysis involves eight BF16-versus-quantized comparisons, we also report Holm-adjusted p p -values. Because the three seeds of a problem are correlated, we additionally treat each problem as one unit: we report 95% confidence intervals from a cluster bootstrap over the 115 problems (20,000 resamples, keeping all three seeds of a problem together) and p p -values from a permutation test that swaps precision labels within each problem.

 4 Empirical Findings

 
 We investigate how weight-only quantization affects Python coding performance on OJBench for execution-feedback agents across BF16, AWQ, and GPTQ 4-bit precisions. Table  1 reports accuracy, Figure  1 the failure-mode distribution, and Appendix  A.2 the paired tests and tool-use statistics.

 
 RQ1: How robust is end-to-end coding-agent performance to 4-bit quantization? 

 
 We evaluate whether replacing BF16 weights with W4A16 AWQ or GPTQ changes final coding accuracy in execution-feedback agents. We compare accuracy across Qwen-2.5-Coder scales and Devstral-Small-2507, together with paired statistical tests in Table  3 . This establishes whether quantization-induced perturbations remain visible after the complete agentic execution process and whether the effect is consistent across quantizers and model configurations. Because we run eight BF16-versus-quantized comparisons, we apply a Holm correction, and because the three seeds of a problem are correlated, we also repeat the analysis with each problem as one unit. Under both analyses, no comparison shows a statistically significant accuracy loss. Qwen-32B shows the largest drop, about 3 points under both quantizers, but it does not reach significance after correction ( p Holm = 0.21 p_{\mathrm{Holm}}=0.21 for AWQ) or at the problem level ( p = 0.051 p=0.051 ).

 
 Finding: Quantization has limited effect on final accuracy for all agents. Qwen-2.5-Coder-32B shows the largest drop, but it does not reach statistical significance. 

 
 RQ2: Does end-to-end accuracy conceal changes in coding-agent solution trajectories? 

 
 We analyze successful trajectories using one-shot solves, execution-loop solves, tool-use rate, and mean executor calls (Tables  4 and  5 ). Across precisions, Qwen-7B shows the clearest behavioral shift: one-shot solves fall from 17 under BF16 to 0 under AWQ and 3 under GPTQ (AWQ: 17 → \rightarrow 0; GPTQ: 17 → \rightarrow 3), while loop-based solves rise from 10 under BF16 to 25 under AWQ and 20 under GPTQ (AWQ: 10 → \rightarrow 25; GPTQ: 10 → \rightarrow 20). This shift remains significant when each problem is treated as one unit, and it also holds on problems solved by both precisions. Devstral moves in the opposite direction, with valid tool use falling from 8.7% under BF16 to 1.2% under GPTQ (GPTQ: 8.7% → \rightarrow 1.2%), where all 19 successful solves are one-shot. Malformed tool calls are rare for the Qwen models, but most of Devstral’s tool calls do not follow the tool schema, which keeps its recorded tool use low; quantization still reduces how often it tries the tool (AWQ: 42.0% → \rightarrow 27.0%; GPTQ: 42.0% → \rightarrow 21.4%). The Qwen models also differ from each other at BF16: Qwen-32B uses tools on 71.3% of problems and produces no one-shot solves, whereas Qwen-14B uses tools on 31.6% of problems with a near-balanced split of 21 one-shot and 18 loop-based solves. These results show both model-specific solve strategies and different levels of behavioral stability under quantization.

 
 Finding: Models exhibit distinct tool-use regimes, but quantization does not preserve them uniformly. Qwen-32B remains loop-dependent, Qwen-14B stays relatively balanced, Qwen-7B shifts toward loop-based solving, and Devstral becomes almost entirely one-shot under GPTQ. 

 
 RQ3: Does quantization change how coding agents fail, not just how often? 

 
 We compare terminal failure categories (IR /WA /TLE /CE /MLE) across precision settings, and test whether each failure distribution differs from BF16 using a chi-square test with Holm correction (Table  2 ). For Qwen-7B, AWQ shifts failures slightly away from Wrong Answer and toward Invalid Return (WA: 65.0 → 59.7 65.0\rightarrow 59.7 ; IR: 21.7 → 29.0 21.7\rightarrow 29.0 per seed). This suggests that quantization can change the type of terminal failure even when final accuracy changes little. The pattern differs for larger models. Qwen-32B exhibits substantially more Compilation Errors than the smaller Qwen models, with CE rising slightly under quantization. Devstral follows another pattern, with fewer Invalid Returns but more Wrong Answers and Time Limit Exceeded cases after quantization. This is the clearest change, and it is statistically significant under both quantizers.

 
 Finding: Quantization can reshape failure profiles differently across models rather than producing one universal failure pattern. 

 
 5 Conclusion

 
 We evaluated 4-bit weight-only quantization in execution-feedback coding agents on OJBench, comparing BF16, AWQ, and GPTQ across Qwen2.5-Coder (7B, 14B, 32B) and Devstral-Small-2507. Quantization reduces checkpoint storage by about 3.4 × \times and causes no statistically significant accuracy loss for any agent after correcting for multiple comparisons, although Qwen-32B shows a consistent nominal drop. More importantly, similar final accuracy can hide large behavioral shifts: Qwen-7B moves strongly from one-shot to loop-based solving after quantization, while Qwen-32B remains fully loop-dependent. Quantization also changes terminal failure profiles differently across models. These results show that quantized coding agents should be evaluated through accuracy, solve trajectories, tool use, and failure modes rather than final accuracy alone.

 
 Limitations and future work. Our study focuses on one competition-level benchmark, one execution-feedback scaffold, and W4A16 quantization, with Python as the solution language. Because OJBench is challenging, absolute solve counts are modest, so we emphasize effects that hold at the problem level. Extending this analysis to other benchmarks, languages, and bit-widths, and to end-to-end efficiency measures such as latency and memory, is a natural next step. Within these limits, 4-bit quantization appears practical for execution-feedback coding agents, but its reliability should be evaluated within the complete agentic workflow.

 A.3 Coding Agent Execution Prompt

 
 The following system prompt was used to instruct the coding agent during problem solving. It guides the agent through a structured write–test–fix workflow with code execution for verification.

 
 
 You are a competitive programming assistant. Solve problems step-by-step:
 1. Read the problem carefully
 2. Write Python code to solve it
 3. Create test input from the problem’s examples
 4. Call python_executor tool to test your code with the test input
 5. Check if the output matches expected output
 6. If wrong, fix the code and call python_executor again
 7. Once correct, return your final solution in a Python code block
 Input reading patterns:
   - int(input()) for single number
   - map(int, input().split()) for multiple numbers on one line
 Always test your code before giving the final answer!
 

 

 
 The python_executor(code, stdin) tool is not described in the prompt text itself. It is supplied to the model through the chat template’s OpenAI-compatible tool schema, and tool calls are parsed from the generated text. The tool description reads: “Execute Python code with optional stdin input. Use this to test your solution before giving the final answer.” The 30 s execution timeout and the five-call budget are enforced by the harness and are not disclosed to the model in advance. When the budget is reached, the model receives one additional user message: “You have reached the maximum number of tool calls. Please provide your final solution in a Python code block now.” 

 
 A.4 Algorithm

 
 Each turn consists of a single model generation. If the generation contains no tool call, it is taken as the final answer. Otherwise every tool call in the generation is executed and its output, truncated to 2,000 characters, is appended to the conversation. The tool-call budget K K is checked once per turn rather than once per call, so a turn containing several calls can carry the total past K K ; this occurred in roughly 10% of problem attempts. When the budget is reached, the model is prompted once more to emit its final solution. If the accumulated conversation exceeds the 32,768-token context limit, the oldest assistant and tool messages are dropped before generation.
