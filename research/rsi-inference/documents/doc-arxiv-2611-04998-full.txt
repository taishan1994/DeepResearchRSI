 Abstract. 

 Purpose-built kernel agents can now write high-performance GPU kernels. As
base models grow stronger, though, even a naive agentic loop beats human
experts on many operators, so both the purpose of a kernel agent and the way
it should be designed need rethinking. Yet existing kernel agents generally
lack cross-run knowledge accumulation and reuse, as well as continued
evolution at the architectural level: each run starts from the same initial
knowledge and merely outputs the best-performing kernel found during that
search, without retaining the knowledge gained through optimization for
subsequent runs; meanwhile, once the kernel architecture is fixed early,
later iterations are largely confined to local optimization within it. 

 We present ForgeKernel, a kernel-generation system for continued optimization. It is
designed to accumulate and reuse knowledge across runs while enabling continued
evolution of kernel architectures. It combines two mechanisms. First, it
analyzes the hardware behavior of a high-performance reference and distills
its validated architectural decisions into reusable knowledge of hardware
mechanisms rather than imitating its source code. Second, it self-evolves by
sealing a kernel that passes correctness and performance validation and using
it as the reference for the next optimization run, allowing the optimization
results of one run to inform subsequent runs and providing a basis for
revisiting and adjusting the kernel architecture. 

 Across 27 operators and 29 input configurations on NVIDIA Hopper
and Blackwell GPUs, ForgeKernel matches or beats its expert reference on 25 of
them, for a +10% geometric mean. On Ascend 910C, on the public case set of all 8
level-4 operators in the CANN-Bench Season 1 final leaderboard,
ForgeKernel leads the per-operator public best, with a +25.1%
geometric-mean lead, while its full-suite submission ranks first on that
benchmark’s A3 leaderboard. As of 2026-10-30, public submissions
generated by ForgeKernel rank first on all three CANN-Bench 2.0
solution leaderboards (Ascend 910C, 950DT, and 950PR) and on the SOL-ExecBench
FlashInfer-Bench track. 

 Keywords:  GPU kernels, code generation, large language models, self-evolution, performance optimization

 1. Introduction 

 Modern machine-learning systems increasingly demand high-performance GPU
kernels. New operators and model architectures, including sparse attention
indexers  ( DeepSeek-AI, 2025 ) , gated delta
networks  ( Yang et al., 2024 ) , and latent-attention
variants  ( DeepSeek-AI, 2024 ) , continue to appear and further expand the
computational patterns that require optimization. Each such pattern is a new
optimization task: work partitioning, dataflow, and pipeline organization
have to be determined again for the concrete operator, input shape, and
hardware. 

 Faced with this continuing demand for kernel development, agents that
automatically write and optimize operators have drawn attention. Prior work
has built agents dedicated to kernel
optimization  ( Chen et al., 2025 ; Wang et al., 2025 ; Dong et al., 2025 ; Wei et al., 2025 ; Han et al., 2026 ; Luo et al., 2026 ) , organizing generation, evaluation, and
iterative improvement into a dedicated workflow, and has surpassed expert
implementations on some tasks. These workflows still have two structural
limits. On tasks that fall short of the expert reference, optimization traces
show that architectural decisions, such as work partitioning, dataflow, and
pipeline organization, are often fixed in the early attempts. Subsequent
iterations tune within that architecture and rarely revise these decisions
from performance feedback. In addition, producing
a high-performance kernel in a single run does not mean that its validated
findings have become cross-run knowledge that can guide later architectural
design and implementation. 

 Overall, an operator-specific agent should close these two limits. First,
performance feedback should revise architectural decisions, rather than
leaving optimization inside an early choice of work partitioning, dataflow,
and pipeline organization. Second, validated findings should become cross-run
knowledge that guides later architectural design and implementation. 

 Guided by these design objectives, we introduce ForgeKernel, a self-evolving operator agent
system (Figure  1 ). To address these two problems, ForgeKernel starts
optimization from architectural design rather than existing code, and uses
a hardware knowledge base to retain and reuse measurement-validated
optimization experience. 

 For architectural design, ForgeKernel uses a high-performance reference implementation
as a design reference and starting point. It separates architecture from coding,
with a dedicated architecture agent reviewing and adjusting architectural
decisions so that optimization is not confined to code-level tuning within a
fixed architecture. Building on this separation, self-evolution enables
continual reflection on the architecture as a whole and iterative improvement,
reducing the risk of becoming trapped in local optima. 

 For knowledge accumulation, ForgeKernel distills mechanisms discovered during
optimization and validated through independent experiments on the target
hardware into cross-run knowledge that guides architectural design and
implementation in subsequent tasks. Reference updates provide new performance
baselines, while accumulated knowledge provides reusable evidence for
optimization decisions; together, they support continued optimization.

 This paper makes the following contributions: 

 • 

 We propose a kernel optimization method centered on architectural
decisions. It separates architectural design from code implementation,
guides implementation through explicit architectural decisions, and revises
these decisions based on performance feedback. When optimization encounters
a structural bottleneck, the method revisits work partitioning, dataflow,
or pipeline organization rather than only tuning locally within a fixed
architecture. Across runs, it also reassesses an existing implementation’s
architecture rather than directly carrying it forward. 

 • 

 We propose a measurement-validated mechanism for accumulating and
reusing knowledge across runs. Hardware mechanisms discovered during
optimization are validated through independent probes on the target GPU
before being stored in a knowledge base shared across operators and input
shapes. This knowledge guides architectural design and implementation
planning in subsequent runs, converting findings from individual runs into
reusable knowledge. 

 • 

 We implement ForgeKernel, a self-evolving operator optimization system that
integrates architectural revision, reference updates, and knowledge reuse.

 2. Background 

 2.1. Kernel Design 

 GPU kernel design requires mapping an operator’s computation onto the parallel
execution and memory structures of the target hardware. For a given operator
and input configuration, designers must determine how to partition computation
across thread blocks and threads, lay out data across memory levels, and
pipeline data transfers with computation
  ( NVIDIA Corporation, 2022 ; NVIDIA Corporation, 2026 ; NVIDIA Corporation, 2024 ; Thakkar et al., 2026 ; Shah et al., 2024 ) .
These choices jointly affect data reuse, memory access overhead, and hardware
resource utilization, so different implementations of the same operator can
exhibit substantial performance differences. 

 Kernel optimization involves both revising these structural design choices
and refining instructions, synchronization operations, and resource
configurations within a given structure. When performance is limited by work
partitioning, data layout, or pipeline organization, local parameter tuning
alone may be insufficient to eliminate the bottleneck, requiring the
corresponding design choices to be reconsidered. Kernel optimization therefore
involves not only parameter search but also analysis and modification of the
implementation structure. 

 2.2. Kernel Agent 

 As large language models (LLMs) improve in code generation and reasoning,
researchers have begun using specialized LLM-based agents to write and optimize
kernels. These systems are referred to as kernel agents. Given an operator,
an input configuration, and a target GPU, a kernel agent generates candidate
implementations, compiles them and checks their correctness, measures execution
performance, and iteratively revises the code based on feedback to search for
a functionally correct and high-performance kernel. 

 3. Design 

 ForgeKernel separates architectural planning from kernel implementation, coordinating
an architecture agent and a coding agent through design plans and measurement
feedback. Figure  2 shows the system architecture. 

 Figure 2 . ForgeKernel architecture. 

 3.1. Overview 

 Kernel optimization requires both structural design and detailed implementation.
Structural design determines how computation and data movement are organized
on the target hardware; implementation turns those choices into correct,
executable code. Combining both responsibilities in one agent risks allowing
compilation, debugging, and local edits to dominate the design context and
anchoring further optimization to the current implementation. ForgeKernel separates
these responsibilities so that architectural choices can be reconsidered from
measurement evidence without making the existing code structure the starting
point for every revision. 

 The architecture agent owns design decisions and plan revisions. Given the
operator definition, input configuration, target hardware, and reference
evidence, it determines computation organization, dataflow, scheduling, and
hardware mapping, and specifies what evidence would validate these choices.
Its output is a milestone plan. The coding
agent owns realization of that plan: it implements the required computation,
data access, and synchronization, handles compilation and debugging, and
performs local optimization within the plan’s constraints. Changes to those
architectural constraints are handled through plan revision by the architecture
agent. 

 The interface between the agents is a design plan in one direction and
implementation feedback with measurement evidence in the other. The coding agent receives design
requirements, interfaces, and acceptance conditions, but not the reference
kernel implementation. The execution harness enforces this boundary, checks
correctness, measures performance, and validates the mechanisms required by the
plan. These checks determine whether implementation can advance or needs
further repair; when optimization stalls or the plan cannot proceed, the
trajectory and measurements return to the architecture agent for reassessment. 

 This separation assigns architectural reasoning, code realization, and measured
acceptance to distinct parts of the system while retaining a feedback loop
between them. Sections  3.2 and  3.3 
describe the two agents in detail. Self-evolution extends the loop through plan
revision and reference updates (§ 3.4 ), while the hardware
knowledge base retains validated mechanisms for reuse
(§ 3.5 ). 

 3.2. Architecture Agent 

 The architecture agent combines operator requirements, reference measurements, and existing hardware knowledge to formulate architectural decisions and milestone plans. Feedback-driven design revision is described in § 3.4 . 

 Architectural decisions. 

 The architecture agent first determines the candidate implementation’s computation organization, dataflow, and mapping to the target hardware. Decisions cover kernel decomposition, data dependencies, and intermediate-result storage, as well as computational tiling, thread roles, register budgets, and shared-memory layouts. Together, these choices specify how computation and data movement interact. 

 Architectural decisions must state the design choices, supporting evidence, and expected effects, distinguishing direct observations from hypotheses that remain to be tested. The reference implementation’s measured performance determines relative performance targets, while its resource usage and execution characteristics inform subsequent mechanism validation. Knowledge entries used in the design are explicitly cited in the plan. 

 Milestone planning. 

 The architecture agent organizes architectural decisions and subsequent optimization tasks into an ordered milestone sequence M 0 , M 1 , … , M k M_{0},M_{1},\ldots,M_{k} . The initial milestone M 0 M_{0} requires the implementation of the key structural decisions above to produce a verifiable initial implementation; subsequent milestones perform fine-grained tuning within that structure. 

 Each milestone specifies implementation tasks, decision rationales, expected costs, and prerequisite dependencies, together with correctness, performance, and mechanism-validation conditions. Dependencies between decisions determine the implementation order, and decisions that must be implemented together to take effect form a single implementation unit. In particular, M 0 M_{0} focuses on correctness and architectural constraints without imposing an absolute performance threshold; subsequent milestones are assessed against their respective optimization objectives. Milestones describe tasks through design requirements and interface contracts, without including the operator’s implementation code. 

 3.3. Coding Agent 

 The coding agent translates design requirements into an operator implementation according to the architecture agent’s milestone plan. It follows decision dependencies and consults the knowledge entries cited in the plan to implement the computation, data access, and synchronization required by the current milestone. The harness checks candidate correctness, performs paired timing of the candidate and its declared reference within the same measurement job when that reference can run alongside the candidate, and collects the execution and resource characteristics needed for mechanism validation. Reference-free black-box arms use separate post-stop confirmation channels instead. 

 The harness determines whether a candidate passes acceptance based on correctness-test results and the milestone’s performance and mechanism-validation conditions. For acceptance items that require a performance improvement, the measurements described above determine whether the gain exceeds the measurement noise threshold. Mechanism validation checks the execution or resource characteristics specified in the plan to determine whether the implementation satisfies the corresponding design constraints and exhibits the expected behavioral changes. After acceptance, the coding agent advances to the next milestone; otherwise, it continues modifying the implementation based on the check results. If optimization stagnates or acceptance cannot proceed, the system returns the implementation trajectory and measurement evidence to the architecture agent for the revision process described in § 3.4 . 

 3.4. Self-Evolution 

 Self-evolution encompasses plan revision within an optimization run and reference updates across runs. 

 When optimization stagnates, the executable optimization decisions in the current plan are exhausted without reaching the target, or milestone acceptance cannot proceed, the system triggers reassessment of the current design by the architecture agent. The architecture agent combines implementation trajectories, measurement evidence, and supplementary probe experiments to revise architectural decisions and the corresponding milestone plan. 

 The revised plan is re-executed according to decision dependencies. Local adjustments resume from the relevant tasks; structural changes to computation organization or dataflow restart implementation from the earliest affected decision, including M 0 M_{0} when necessary. Subsequent implementation and measurement evaluate each revision. If no performance improvement can be attributed to the change, the change is reverted and its failure conditions are recorded to inform subsequent diagnosis. 

 Beyond revising the current plan, the system can use an accepted implementation as the reference for the next optimization run, extending optimization through its own outputs without requiring a new external expert implementation. This implementation participates in the subsequent run as a measurable black box, with its source code unavailable to that run’s agents. The architecture agent analyzes the updated reference and uses it to formulate architectural decisions and performance targets. The coding agent generates a new implementation according to the corresponding milestone plan, while validated knowledge is retained and reused through the knowledge base. Cross-run iteration terminates when the performance gain in a subsequent run is confirmed not to exceed the measurement noise threshold, or when the budget is exhausted. 

 3.5. Knowledge Validation and Reuse 

 The hardware knowledge base stores hardware mechanisms distilled during optimization and diagnosis, organized by target hardware architecture. Each entry records the mechanism, applicability conditions, trigger symptoms, a minimal runnable example, and known limitations. A candidate mechanism is admitted after passing independent probe validation on the target hardware and providing supporting measurement evidence. 

 During subsequent optimization, the architecture agent selects relevant knowledge based on the task’s measured characteristics and the entries’ applicability conditions, and explicitly cites the entries in milestones for the coding agent to implement the corresponding mechanisms. Milestone acceptance still checks their effects in the current task. The system records the creation and use of entries to support traceability and reuse across runs. 

 4. Evaluation 

 This chapter evaluates the performance of ForgeKernel-generated implementations
and the roles of architecture planning, feedback-driven revision, and knowledge
reuse. § 4.1 describes the setup; § 4.2 reports
public-benchmark results and comparisons with expert libraries and artifacts
from other generation systems; § 4.3 evaluates self-evolution;
§ 4.4 examines the individual designs; and
§ 4.5 uses GQA and DSA cases to examine the roles of the
architecture agent and self-evolution in architecture changes. 

 4.1. Experimental Setup 

 Hardware and tasks. NVIDIA experiments run on Hopper H100 80 GB
(SXM, 132 SMs) and Blackwell B200 (148 SMs) nodes in a shared cluster,
covering attention, matrix multiplication, convolution, GDN, and DSA.
Ascend experiments run on 910C; the per-operator comparison covers
all 8 level-4 operators in
CANN-Bench 1.1.2. Coverage is reported separately for
public leaderboards and per-operator experiments. Input shapes and data
types are listed in Appendix  C . 

 Comparison targets. Per-operator experiments use expert library
implementations and kernels released by other generation systems as
references. Libraries include FlashAttention-4, DeepGEMM, cuBLAS, cuDNN,
FlashInfer, FlashMLA, and FlashQLA; generation systems include K-Search,
Kernel Design Agents, and CAKE. Reference versions are pinned in the execution
environment image and re-timed in our environment. Comparisons with generation
systems evaluate their released artifacts.
Versions and entry points are listed in Appendix  B . 

 Models and run protocol. The arch agent and coding agent of ForgeKernel (§ 3.1 ) use Claude Fable 5.1 and Claude Opus 5,
respectively. By default, ForgeKernel receives a sealed reference that can be run,
timed, profiled, and disassembled, without source access.
The knowledge base accumulates across runs, so its initial state can differ
between runs. Performance targets and budgets are set per task; runs end
when the target is reached, the budget is exhausted, or the run is stopped
manually. Expert-library experiments target parity, while self-evolution
typically targets +5% over the preceding generation; specific
targets and stopping reasons follow the individual run records. Main
performance results select the best optimization run per configuration.
The full system and each variant in the module ablation are run separately
for that experiment. 

 Correctness validation. Candidates must pass the official or benchmark
tolerance test associated with their operator source before performance
measurement. Operators covered by FlashInfer-Bench, including the operators
in the SOL-ExecBench FlashInfer-Bench collection, use FlashInfer-Bench’s
tolerance tests; FlashAttention operators use the official FlashAttention
tolerance tests; other operators likewise use the tolerance criterion of
their source benchmark or implementation. The harness also rejects candidates
that call the reference
implementation directly or delegate computation to it. The source-specific
criteria are summarized in Appendix  A . 

 Timing method. On NVIDIA hardware, we measure device execution time
under cold- L ​ 2 L2 cache conditions. Average device time per call is the total
GPU time over repeated calls divided by the call count. The candidate and
reference use the same timing protocol and cache conditions. Results are
based on repeated measurements. Speedup is
 S = T ref / T candidate S=T_{\mathrm{ref}}/T_{\mathrm{candidate}} , where the numerator and denominator
are the device execution times of the reference and candidate, respectively;
performance gain is ( S − 1 ) × 100 % (S-1)\times 100\% . 

 Ascend experiments use the hosted evaluation harness of CANN-Bench, with
device execution time recorded in msprof’s kernel_details .
Baselines, hardware performance bounds, and scoring rules follow the
corresponding benchmark version. Scores are computed by the hosted service;
results are aggregated separately for each platform. 

 The /goal configuration. The /goal agent follows the
goal-driven setting of JustGoal  ( Chen et al., 2026 ) , using Claude
Fable 5.1 without an operator-specific workflow and with a 24-hour budget
per task. Prompts use a fixed format specifying the operator signature,
input shapes, target hardware (one H100), and optimization goal; copying
code from the web is prohibited. No existing implementation is supplied as a
reference. Generated implementations are subsequently evaluated against expert
libraries. The objective has no preset speedup ceiling.
Optimization state is not retained across sessions, and acquired knowledge
is not transferred between runs. Selected artifacts serve as initial
references for some self-evolution experiments in § 4.3 .

 4.3. Self-Evolution Experiments 

 This section evaluates reference updates across runs: an existing implementation
becomes the next run’s reference. In the default ForgeKernel protocol, this reference
is measurable but source-hidden, and the arch agent analyzes it to develop a
new plan for the coding agent to implement. The DeepSeek-V4.1 case below uses
a source-visible generated reference and a single coding agent, as specified
in its case description.
We evaluate two paths. In the first, an initial implementation is generated
without any existing implementation as a reference; ForgeKernel then
uses that artifact as its reference for further optimization. In the second,
ForgeKernel first uses an expert-library implementation as its reference to generate
generation 0, then uses the preceding generation as the reference for
self-evolution. Generation 0 is the output of the first optimization run.

 4.5. Case Studies: Two Mechanisms for Architecture Changes 

 The two cases illustrate the roles of the architecture agent and self-evolution
in architecture changes. By separating architecture from coding, the
architecture agent explicitly plans and revises interdependent architectural
decisions. The self-evolution case focuses on using an accepted implementation
as the reference for a subsequent run, with renewed analysis and design to
explore further architectural improvements. These roles are complementary:
the former organizes architecture changes, while the latter makes an existing
optimized artifact the starting point for further architecture exploration. 

 Architecture-agent-driven replanning: GQA. 

 The first GQA attention-forward self-evolution round illustrates how the
architecture agent coordinates interdependent changes. The initial
implementation assigns one query block to each thread block (CTA), which
then exits. Rather than proposing only local code changes, the architecture
agent changes this to persistent execution, so that the same CTA processes
multiple query blocks. It organizes cross-block state management and Q-data
prefetching into a staged plan for the coding agent to implement. 

 The coding agent first implements the persistent loop and cross-block state
management, obtaining a local performance gain of approximately
+0.8%. It then adds Q double buffering to load the next
query block’s data early, obtaining a further local gain of approximately
+6.1%. Both steps undergo correctness checks and separate
performance measurements; their local gains cannot be directly added. 

 The round ultimately improves performance over the preceding generation by
+9.9% (Table  2 ), including other changes;
this gain cannot be attributed entirely to the two steps above. The case
highlights how separating architecture from coding supports coordinated
planning: the initial structural change delivers only a modest gain, but
enables subsequent pipeline optimization, with the coding agent implementing
the interdependent changes in dependency order. 

 Architecture reassessment through self-evolution: DSA. 

 The DSA sparse attention-forward case examines how an existing optimized
artifact becomes the starting point for a new round of architecture analysis.
The initial implementation uses non-persistent execution with one resident
CTA per SM. After this implementation becomes the reference, the next round
obtains approximately 4.5% gain within the original architecture, after which
further adjustments provide no effective improvement. Updating the reference
does not require retaining the preceding generation’s architecture, allowing
the system to reassess its computation organization rather than only tune
parameters within that structure. 

 Through diagnostic experiments, the architecture agent finds that each CTA’s
query load, initial KV fills, and final output store lack computation from
adjacent work items to overlap with. A probe removing output stores changes
performance by approximately 6.0%, helping isolate uncovered overhead; this
probe is diagnostic, not a complete candidate implementation. The system
therefore adopts a persistent loop, overlapping one work item’s output store
with the next item’s loads (Figure  7 ), and ultimately obtains
a gain of +7.2% over the preceding generation
(Table  2 ). This case illustrates the role of reference updates
in self-evolution: retaining an existing artifact as a performance reference
while reopening optimization through renewed diagnosis and architecture
analysis, rather than fixing its structure as a constraint on subsequent runs.

 5. Related Work 

 Operator optimization and programming infrastructure. 

 High-performance operator implementations require computation and data access
to be organized according to computational characteristics and target hardware.
FlashAttention uses tiling to reduce device-memory accesses in
attention  ( Dao et al., 2022 ) , while FlashInfer provides customizable,
efficient attention implementations for LLM inference serving
  ( Ye et al., 2025 ) . Translating such designs into efficient code requires
appropriate programming abstractions and compiler support: CUTLASS provides
composable high-performance computational components, and Triton provides a
programming language and compiler for GPU kernels, enabling developers to
express and implement computation partitioning and data organization
  ( Thakkar et al., 2026 ; Tillet et al., 2019 ) . Beyond supporting developers in expressing
designs, another line of work explores automating design choices. For example,
Mirage jointly searches algebraic and scheduling transformations through a
unified representation spanning kernels, thread blocks, and
threads  ( Wu et al., 2025 ) . 

 LLM-based operator generation and optimization. 

 Prior work improves operator generation through feedback-driven iteration,
evolutionary search, and model training. GEAK generates Triton kernels through
a feedback-driven reasoning loop  ( Wang et al., 2025 ) . STARK and Astra combine
multi-agent collaboration with search, profiling, and planning
  ( Dong et al., 2025 ; Wei et al., 2025 ) ; AlphaEvolve combines LLMs with automated
evaluation for evolutionary search  ( Novikov et al., 2025 ) . These methods
focus on code iteration within a single run, without treating architectural
decisions as separately revisable from measurements or using accepted kernels
as references for a new round of architectural analysis. 

 Kevin incorporates multi-turn implementation and execution feedback into
reinforcement learning, while CUDA-L1 uses contrastive reinforcement learning
to improve CUDA optimization  ( Baronio et al., 2025 ; Li et al., 2026 ) . Training
changes the model that emits code, not the revision of architectural
decisions during optimization. 

 EGG fixes the algorithmic structure before hardware tuning, without revisiting
it based on subsequent measurements  ( Han et al., 2026 ) . CuBridge adapts expert
attention kernels to target operators through an executable intermediate
representation, retaining the expert implementation’s structure
  ( Ma et al., 2026 ) . AKO optimizes kernels through a multi-agent workflow,
with a human orchestrator redirecting stalled searches  ( Luo et al., 2026 ) .
Structural choices or search redirections in these workflows are not explicit
architectural decision revisions triggered by measurements. 

 Another line of work retains prior experience and uses it to guide later
generation. KernelClaw stores reusable expert optimization knowledge in
long-term memory and uses short-term memory to avoid repeated backtracking
within a run, replacing the model’s implicit heuristics with expert
knowledge  ( Sun et al., 2026 ) . KLineage progressively simplifies expert
implementations through validated steps, distilling each step into a skill with
explicit applicability conditions for subsequent code generation
  ( Zhang et al., 2026 ) . Both retain knowledge or skills
obtained from the expert side and use them to guide code generation. They do
not store hardware mechanisms validated by independent probes during
optimization as knowledge shared across operators, and later runs do not cite
such entries when setting architectural decisions. 

 ForgeKernel separates architectural design from code implementation, organizing
milestone plans around explicit architectural decisions and revising those
decisions in response to measurement feedback. When structural bottlenecks
limit performance, the system revisits computation partitioning, dataflow,
or pipeline organization rather than only tuning within a fixed architecture.
For knowledge reuse, ForgeKernel distills hardware mechanisms during optimization,
validates them through independent probes on the target hardware, and stores
them in a knowledge base shared across operators and input shapes to guide
architectural design and implementation planning in subsequent runs. Existing
implementations can also become new references: their architectures are
reassessed through measurement rather than carried forward by directly
inheriting their source code. 

 6. Limitations and Future Work 

 Architecture exploration and local optima. 

 ForgeKernel revisits existing architectures through explicit planning and
feedback-driven revision, but exploration is limited by the agents’ ability to
generate candidates, and optimization may settle at local optima. Future work
will investigate planning strategies that broaden the architecture search space
and increase candidate diversity while preserving autonomous exploration and
generalization. 

 Cross-hardware design reuse. 

 Hardware mechanisms in the knowledge base depend on specific architectures and
applicability conditions; transfer to other hardware requires adaptation and
validation. Future work will investigate mechanism abstraction, adaptation, and
validation for cross-hardware reuse while retaining target-specific optimization. 

 7. Conclusion 

 We presented ForgeKernel, a self-evolving agent for kernel optimization. ForgeKernel separates architectural design from code implementation and revises work
partitioning, dataflow, and pipeline organization based on performance
feedback. Across runs, it uses validated kernels as new references
and accumulates hardware mechanisms validated by independent probes in a
shared knowledge base. Reference updates enable further architectural
reassessment, while knowledge reuse carries optimization experience across
runs and operators; together, they support continued self-evolution. 

 With self-evolution and knowledge reuse, ForgeKernel achieves a geometric-mean
speedup of 1.10 × \times over reference implementations from
expert libraries and other kernel-generation systems across 29
configurations covering 27 operators on NVIDIA Hopper and Blackwell
GPUs. On Ascend, it outperforms the per-operator public best on the public
case set of all 8 level-4 operators in the CANN-Bench
Season 1 final leaderboard, with a geometric-mean performance
gain of +25.1%. Public submissions generated by ForgeKernel rank first
on all three CANN-Bench 2.0 solution leaderboards
(Ascend 910C, 950DT, and 950PR) and on the SOL-ExecBench FlashInfer-Bench leaderboard
as of 2026-10-30.

 Appendix A Correctness Judges 

 Correctness validation first follows the official or benchmark tolerance test
associated with each operator source. Operators covered by FlashInfer-Bench,
including those in the SOL-ExecBench FlashInfer-Bench collection, use
FlashInfer-Bench’s tolerance tests; FlashAttention operators use the official
FlashAttention tolerance tests; other operators use the criterion associated
with their source. Within this source mapping, the concrete judges include
DeepGEMM’s aggregate criterion for GEMMs, a relative max-abs bound for
attention gradients, and a scaled tolerance plus a cosine bound for the GDN
and KDA (Kimi Delta Attention  ( Kimi Team, 2025 ) ) state kernels,
whose small outputs would pass a fixed absolute tolerance trivially. The GDN
judges further add correlated-key and long-memory inputs that catch
state-decay shortcuts.

 Appendix E Knowledge-Reuse Provenance 

 Figure  8 aggregates the SM90 run snapshot by source
and adopting operator configuration. Each cell counts distinct external entries;
repeated use across runs is deduplicated. White cells have no qualifying record,
and gray cells denote self-reuse, which is excluded. All 23 recipient configurations
are retained, including the zero-adoption configuration; source rows without any
qualifying outgoing reuse are omitted. The cohort follows the original provenance
plot: MHA and GQA attention variants are separated, and MHA forward is not a
recipient because it is outside that plot’s evaluated configuration set.
This is a provenance cohort, not a census of every evaluated task. 

 Entry origins come from recorded birth cells, falling back to the earliest run
of the originating operator. The original run-group ordering and temporal
exclusions are retained. Adoption uses the milestone-citation and decision-delivery
snapshot, rather than mere retrieval. Where commit lineage is available, delivery
is checked against the best correct implementation; otherwise the extractor falls
back to process records. Thus the snapshot does not independently certify final-code
retention for every entry, and zero denotes no qualifying recorded adoption.
The two examples in Figure  6 (b) show selected entries from
the recorded exchanges, not an exhaustive list or a causal performance attribution.
