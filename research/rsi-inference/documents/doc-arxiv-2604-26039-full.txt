 Abstract 

 The optimal kernel configuration for Mixture-of-Experts
(MoE) inference depends on both batch size and the expert routing
distribution—yet every production system dispatches from batch
size alone, leaving 10–70% of kernel throughput unrealized.
We present RaMP, a routing-aware dispatch framework.
A performance-region analysis derives, from hardware
constants alone, when each optimization helps—correctly
predicting all 8 tested architectures, including 3 unseen.
A four-parameter wave cost model selects the fastest
configuration from the runtime expert histogram, achieving
 0.93 % 0.93\% mean regret versus exhaustive search, fitted from just
10–24 minutes of one-time profiling per model. Because the model
depends only on CTA grid geometry, it is kernel-agnostic: applied
to Alpha-MoE, it delivers 1.14 × 1.14\times with no source modification.
Paired with a co-designed CuTe DSL kernel exposing 134–268
polymorphic configurations, RaMP delivers 1.22 × 1.22\times kernel
speedup over static dispatch and 1.30 × 1.30\times end-to-end speedup
in vLLM serving over Triton ( 1.41 × 1.41\times over DeepGEMM,
 1.13 × 1.13\times over FlashInfer CUTLASS). 

 Index Terms:  mixture-of-experts, kernel dispatch, cost model, GPU optimization,
inference serving

 I Introduction 

 Mixture-of-Experts (MoE) models activate only a fraction of their
parameters per token, enabling models with hundreds of billions of
parameters at manageable inference
cost  [ 1 , 2 , 3 ] . The fused MoE kernel—executing
up-projection, activation, and down-projection in a single GPU
launch—is the critical hot path: on OLMoE-1B-7B, it accounts for
over 60% of per-token latency. Modern implementations are already
heavily optimized with TMA loads, WGMMA scheduling, and multi-stage
pipelines, leaving little room for a single blanket improvement.

by selecting bm = 4 \texttt{bm}{=}4 (more, smaller tiles).
At uniform routing ( β = 1.0 \beta{=}1.0 ), both choose the same
configuration. 

 The deeper problem is that the optimal kernel configuration
depends on the runtime expert routing distribution, which changes
at every forward step. Under skewed routing—the norm in
production, where only 8–14% of experts are active per
layer (§ III-A )—a small token block
( bm = 16 \texttt{bm}{=}16 ) minimizes padding waste. Under balanced
routing, a large block ( bm = 64 \texttt{bm}{=}64 ) reduces wave count.
The configuration space is substantial: 134–268 valid tile
configurations per model on H200. Yet every production system we
examined—vLLM, SGLang, Alpha-MoE, DeepGEMM,
FlashInfer—dispatches from batch size alone, ignoring routing
entirely. We show that this leaves 10–70% of kernel
performance unrealized (§ III ). 

 Our key insight is that a physically grounded cost model—encoding
startup overhead, wave scheduling, per-CTA memory traffic, and
sub-wave nonlinearity as four measurable terms—can dispatch MoE
kernels from the actual expert histogram at runtime. Four
parameters per configuration, fitted from 25 profiling points in
10–24 minutes, suffice because the model decomposes performance
into physically distinct terms. Crucially, the cost model depends
only on the CTA grid size, not the kernel implementation: applied
to a third-party kernel (Alpha-MoE) with no source modification, it
delivers 1.14 × 1.14\times over their own JIT
dispatch (§ V-C ). The vLLM-specific integration
is orthogonal engineering; the cost model framework applies to any
fused MoE kernel that exposes a tunable configuration space. 

 We formalize the conditions under which each kernel optimization
helps through four performance-region variables 
(§ IV-A ): compute density ( ρ \rho ), L2
pressure ( λ \lambda ), wave utilization ( ω \omega ), and K-reduction
depth ( κ \kappa ). These variables, derived from problem geometry
and hardware constants alone, correctly predict optimization
applicability for all 8 architectures tested—including 3 unseen
models profiled from scratch with no prior knowledge. 

 Contributions. 
(1) We characterize the static dispatch problem, showing that
routing variation leaves 1.22 × 1.22\times geomean performance on the
table and that three natural alternatives each
fail (§ III ).
(2) We introduce a performance-region analysis and four-parameter
wave cost model achieving 0.93 % 0.93\% mean regret versus exhaustive
search across 8 architectures, generalizing to unseen models and
third-party kernels (§ IV-A – IV-B ).
(3) We co-design a CuTe DSL kernel with 134–268 polymorphic
configurations and validate end-to-end in vLLM, delivering
 1.30 × 1.30\times speedup over Triton FP8, 1.41 × 1.41\times over DeepGEMM,
and 1.13 × 1.13\times over FlashInfer CUTLASS on
OLMoE (§ IV-C – V-E ). 

 II Background 

 II-A MoE Inference and Expert Routing 

 Mixture-of-Experts (MoE) models partition each feed-forward layer
into E E independent expert networks. A lightweight gating network
selects the top- k k experts per token, routing each token to only
a small fraction of the total parameters. This conditional
computation enables models with hundreds of billions of parameters
while activating only a few billion per token: OLMoE  [ 2 ] 
contains 7B total parameters but activates only 1B, and
DeepSeek-V3  [ 1 ] contains 671B with 37B active. 

 Crucially, the routing decision is input-dependent :
different tokens activate different expert subsets, and the
distribution changes at every forward step. We quantify routing
skew via entropy-normalized balancedness 
 β = H ⁡ ( 𝐜 ) / ln ⁡ E \beta=H(\mathbf{c})/\ln E ( β = 1 \beta{=}1 : uniform; lower
values: skewed). The trend toward fine-grained MoE
(DeepSeek-V3: E = 256 E{=}256 ; Qwen3: E = 128 E{=}128 ) amplifies this
variability, making the optimal kernel configuration
increasingly input-dependent (§ III-A ). 

 II-B Fused MoE Kernel Anatomy 

 A fused MoE kernel executes all three phases of the expert
computation in a single GPU launch:
 Phase 1 (up-projection) loads expert weight tiles via TMA
and computes 𝐇 e = 𝐗 e ​ 𝐖 1 , e \mathbf{H}_{e}=\mathbf{X}_{e}\mathbf{W}_{1,e} 
through WGMMA matrix-multiply-accumulate instructions;
 Phase 2 applies the SwiGLU nonlinearity with in-register
FP8 re-quantization, avoiding any write to HBM;
 Phase 3 (down-projection) computes the final output and
scatters it back to the token positions via atomic add.
By keeping the intermediate activations in registers between
phases, the fused kernel eliminates two HBM round-trips per expert
per token that a multi-kernel implementation would incur. 

 On Hopper GPUs, each CTA uses warp specialization: 128 producer
threads issue TMA weight loads and cp.async activation
gathers into a multi-stage shared memory pipeline, while
 wn × 32 \texttt{wn}\times 32 consumer threads drain the pipeline
through WGMMA instructions that read directly from shared memory
descriptors. The producer fills the next pipeline stage while the
consumer computes on the current one, overlapping memory latency
with compute. 

 The kernel is parameterized by a tile configuration 
 c = ( bm , bn , wn , stg ) c=(\texttt{bm},\texttt{bn},\texttt{wn},\texttt{stg}) ,
specifying the token block size (how many tokens each CTA
processes), weight sub-tile width, consumer warp count, and
pipeline depth (number of buffered stages), respectively.
The CTA grid depends on the expert token distribution: 

 | 
 grid ⁡ ( c ) = ∑ e ⌈ c e / bm ⌉ ⏟ M-tiles (routing-dependent) × ⌈ N / ( bn ⋅ wn ) ⌉ ⏟ N-tiles (config-dependent) \mathrm{grid}(c)=\underbrace{\textstyle\sum_{e}\lceil c_{e}/\texttt{bm}\rceil}_{\text{M-tiles (routing-dependent)}}\times\underbrace{\lceil N/(\texttt{bn}\cdot\texttt{wn})\rceil}_{\text{N-tiles (config-dependent)}} | 
 | 
 (1) | 

 Because the M-tiles term depends on the routing distribution,
different values of β \beta at the same batch size  S S produce
grids differing by 1.6 − 10 × 1.6{-}10\times 
(Figure  1 ), which in turn demand different
configurations.

 III Challenges and Opportunities 

 Before presenting our solution, we characterize the static dispatch
problem quantitatively: how much performance do production systems
leave on the table by ignoring the routing distribution? 

 III-A Routing Variation in Production 

 We instrument OLMoE ( E = 64 E{=}64 ) and Qwen3 ( E = 128 E{=}128 ) with routing
hooks on four downstream tasks (MMLU, GSM8K, code generation,
and open-ended chat; 12 prompts per model, yielding 9,728 and
192,103 per-layer routing observations, respectively).

 III-C Why Simpler Approaches Fall Short 

 Three natural responses to this problem each prove insufficient: 

 Approach 1: Finer-grained bucket dispatch. 
Triton’s lookup rounds M M to the nearest power-of-2 anchor.
Doubling the number of anchors captures batch-size variation more
precisely, achieving 1.05 × 1.05\times geomean improvement over standard
buckets. However, this approach still
misses routing variation within a bucket: two invocations
with the same M M but different β \beta require different configs. 

 Approach 2: Exhaustive online search. 
Evaluating all 134 configs at each invocation would cost
 134 × 48 ​ μ ​ s = 6.4 ​ ms 134\times 48\,\mu\text{s}=6.4\,\text{ms} , which is orders of
magnitude larger than the 20 − 300 ​ μ 20{-}300\,\mu s kernel it aims to
optimize. Runtime exhaustive search is impractical. 

 Approach 3: Simple linear cost model. 
A 2-parameter model ( T = a + b × grid T=a+b\times\mathrm{grid} )
captures the gross scaling trend but misses wave
quantization : kernel time jumps sharply at CTA grid multiples of
 SM ​ _ ​ COUNT = 132 \mathrm{SM\_COUNT}{=}132 . On DSv3 ( N = 512 N{=}512 , yielding only
2 N-tiles), this model produces 37.5 % 37.5\% max regret because the
grid-time relationship is concave in the sub-wave region rather
than linear. 

 Takeaway 2: An effective dispatch must be
(a) sub- 50 ​ μ 50\,\mu s for runtime use,
(b) routing-aware (dispatching from the expert histogram, not
 M M alone), and
(c) physically grounded to capture wave quantization.

 IV-A MoE Performance Regions 

 On a highly-optimized fused MoE kernel, no single optimization
helps universally. GROUP_M swizzle is essential on Mixtral but
irrelevant on OLMoE. Split-K fills idle SMs on DSv3 at decode
batch sizes but degrades performance on Mixtral. Small token
blocks reduce padding under skewed routing but increase wave count
under balanced routing. The question, therefore, is not how to
make the kernel faster in general, but rather when each
optimization helps and how to select the right combination at
runtime. 

 We answer this question by identifying four variables from the
problem geometry ( E , N , K ) (E,N,K) , each targeting a specific hardware
bottleneck. For each variable, we explain why it captures an
effect that no simpler metric addresses. 

 Compute density ( ρ \rho ): 

 | 
 ρ = N ⋅ K ttn ⋅ tile_k \rho=\frac{N\cdot K}{\texttt{ttn}\cdot\texttt{tile\_k}} | 
 | 
 (2) | 

 This quantity counts the number of WGMMA tile operations per CTA.
 Why not use raw FLOPs or arithmetic intensity instead? 
Raw FLOPs ignore pipeline overhead, which dominates at small grids:
each CTA pays a fixed startup cost (pipeline fill, mbarrier setup,
TMA descriptor initialization) regardless of compute volume.
Arithmetic intensity (FLOPs/byte) captures the balance between
compute and memory bandwidth, but not between compute and pipeline
fill. By contrast, ρ \rho captures precisely this ratio. When
 ρ < ρ c \rho<\rho_{c} , startup overhead exceeds useful compute per CTA,
and the kernel becomes pipeline-dominated . The critical
threshold ρ c ≈ 186 \rho_{c}\approx 186 follows from the ratio of
single-CTA startup cost ( 24 ​ μ 24\,\mu s median on H200) to effective
WGMMA throughput ( 130 130  ns/tile including pipeline stalls),
consistent with the empirically observed crossover at
 ρ c ≈ 200 \rho_{c}\approx 200 . 

 L2 pressure ( λ \lambda , κ \kappa ): 

 | 
 λ = ⌈ N / ttn ⌉ , κ = K / tile_k \lambda=\lceil N/\texttt{ttn}\rceil,\qquad\kappa=K/\texttt{tile\_k} | 
 | 
 (3) | 

 In a fused MoE kernel, the dominant memory pattern is weight
loading via TMA. When two CTAs processing different M-tiles for the
same expert execute concurrently, they access the same weight
column; if it remains in L2, the second CTA avoids an HBM fetch.
L2 is the only level where inter-CTA weight reuse occurs: L1 is
per-SM and holds only the current pipeline stage, while registers
and shared memory hold accumulators and buffers, not prior tiles. 

 GROUP_M swizzle addresses L2 pressure by reordering the CTA grid so that
groups of adjacent M-tiles share weight columns before advancing.
The condition is whether the weight footprint exceeds effective L2
capacity. With L ​ 2 eff = 0.75 × 60 ​ MB = 45 L2_{\mathrm{eff}}=0.75\times 60\,\mathrm{MB}=45  MB (NCU confirms 72–78% of L2 sectors available for
weights): 

 | 
 λ ⋅ κ > L ​ 2 eff ttn ⋅ tile_k ⋅ sizeof ⁡ ( FP8 ) = 45 ​ MB 32 ​ KB = 1440 \lambda\cdot\kappa>\frac{L2_{\mathrm{eff}}}{\texttt{ttn}\cdot\texttt{tile\_k}\cdot\mathrm{sizeof(FP8)}}=\frac{45\,\mathrm{MB}}{32\,\mathrm{KB}}=1440 | 
 | 
 (4) | 

 This threshold correctly predicts GROUP_M applicability for all
8 models with zero exceptions (Table  III ):
Mixtral ( λ ⋅ κ = 6144 \lambda\cdot\kappa=6144 ) and the three Regime-B
unseen models exceed it, while OLMoE ( 128 128 ) and DSv3 ( 112 112 )
fall far below. 

 Wave utilization ( ω \omega ): 

 | 
 ω = grid ⁡ ( c , S , routing ) / SM ​ _ ​ COUNT \omega=\mathrm{grid}(c,S,\text{routing})\;/\;\mathrm{SM\_COUNT} | 
 | 
 (5) | 

 Why measure waves rather than SM occupancy? SM occupancy
(warps per SM) is a per-SM metric that quantifies instruction-level
parallelism within a single SM. The variable ω \omega captures a
qualitatively different phenomenon: GPU-wide grid
quantization . Increasing the grid from 131 CTAs
( ω = 0.99 \omega{=}0.99 , one nearly-full wave) to 133 CTAs
( ω = 1.01 \omega{=}1.01 , two waves with the second nearly empty)
approximately doubles wall-clock time. This quantization cliff
is invisible to occupancy metrics. Notably, ω \omega is the
 only routing-dependent variable : different expert
distributions at the same batch size  S S produce different
 ω \omega values, which in turn select different configurations. 

 K-reduction depth ( κ \kappa ):
 κ = K / tile_k \kappa=K/\texttt{tile\_k} .
 Why treat this separately from ρ \rho ? A deep
K-dimension creates a qualitatively different opportunity:
splitting the K-reduction across multiple CTAs (split-K) can fill
idle SMs at sub-wave operating points. This technique is
beneficial only when κ ≥ 48 \kappa\geq 48 and ω < 0.2 \omega<0.2 .
Split-K with sk = 4 \mathrm{sk}{=}4 quadruples the grid, so the
original grid must contain fewer than 33 CTAs for the expanded grid
to remain within one wave. At higher ω \omega , the two-launch
overhead (approximately 10 − 15 ​ μ 10{-}15\,\mu s) outweighs the
parallelism benefit, causing split-K to degrade performance. The
threshold κ ≥ 48 \kappa\geq 48 ensures that sufficient reduction work
exists to amortize this overhead. The distinction from ρ \rho is
fundamental: ρ \rho measures compute density per CTA , while
 κ \kappa measures reduction depth across CTAs 
(Figure  6 ). 

 Fig. 6 : Split-K fills idle SMs at sub-wave operating points.
(a) Standard kernel: 3 CTAs occupy 3 of 8 SMs ( ω = 0.38 \omega{=}0.38 ,
62% idle).
(b) Split-K=4: K-reduction partitioned across 4 CTAs per expert,
yielding 12 CTAs that fill both waves ( ω = 1.5 \omega{=}1.5 , all SMs active). 

 These four variables are sufficient because they cover the
hardware axes that vary across operating points: per-CTA compute
( ρ \rho ), cache pressure ( λ \lambda ), grid-level parallelism
( ω \omega ), and reduction depth ( κ \kappa ). Register pressure,
shared memory limits, and TMA alignment constrain which configs
 exist but do not vary at runtime.

 IV-B Wave-Based Cost Model 

 The performance regions identify which optimizations are
applicable to a given model. We now construct the cost model that
selects which specific configuration is fastest for the
actual routing distribution observed at runtime. 

 Formulation. We decompose a fused MoE kernel’s execution
time into four terms, each capturing a physically distinct
component of GPU kernel scheduling: 

 | 
 T ⁡ ( c ) = a ⁡ ( c ) ⏟ startup + b ⁡ ( c ) ​ g SM ⏟ waves + c ⁡ ( c ) ​ g ⏟ per-CTA + d ⁡ ( c ) ​ log ⁡ ( g + 1 ) ⏟ sub-wave T(c)=\underbrace{a(c)}_{\text{startup}}+\underbrace{b(c)\,\tfrac{g}{\mathrm{SM}}}_{\text{waves}}+\underbrace{c(c)\,g\vphantom{\tfrac{g}{S}}}_{\text{per-CTA}}+\underbrace{d(c)\,\log(g{+}1)\vphantom{\tfrac{g}{S}}}_{\text{sub-wave}} | 
 | 
 (6) | 

 where g = grid ⁡ ( c , routing ) g=\mathrm{grid}(c,\text{routing}) is the CTA count from
Eq.  1 and SM = 132 \mathrm{SM}{=}132 on H200. 

 Term-by-term interpretation. 
(1)  a ⁡ ( c ) a(c) : the startup cost of one CTA—pipeline fill,
mbarrier initialization, TMA descriptor setup—independent of
how many CTAs run.
(2)  b ⁡ ( c ) × g / SM b(c)\times g/\mathrm{SM} : the cost of wave
scheduling ; g / SM g/\mathrm{SM} counts how many sequential waves the
GPU must execute. The continuous ratio g / SM g/\mathrm{SM} (rather
than ⌈ g / SM ⌉ \lceil g/\mathrm{SM}\rceil ) linearizes the wave count;
the staircase jumps at wave boundaries are absorbed into the c × g c\times g term during OLS fitting.
(3)  c ⁡ ( c ) × g c(c)\times g : the cost that scales per CTA, dominated by
HBM weight traffic. Each CTA loads one weight tile
( ttn × tile_k \texttt{ttn}\times\texttt{tile\_k} bytes); more CTAs means
more total traffic when L2 misses.
(4)  d ⁡ ( c ) × log ⁡ ( g + 1 ) d(c)\times\log(g{+}1) : captures diminishing
returns of CTA parallelism in the sub-wave regime ( g < SM g<\mathrm{SM} ),
where adding CTAs to a partially-filled wave provides decreasing
marginal utilization. 

 Because g g depends on the routing distribution
(Eq.  1 ), T T becomes a function of both the
configuration and the runtime expert histogram. 

 Why not merge the wave and CTA terms? 
The coefficients b / SM b/\mathrm{SM} and c c are fitted independently
by OLS and capture different physical effects: b b tracks SM
scheduling overhead (constant per wave), while c c tracks memory
traffic (proportional to the number of CTAs). Models with high
 λ \lambda (many N-tiles, high L2 pressure) exhibit large c c but
small b b ; models with low λ \lambda show the reverse. Merging
them into a single k × g k\times g term forces a shared coefficient,
increasing mean regret from 0.93 % 0.93\% to 8.1 % 8.1\% . 

 Progressive refinement. We validate each term’s
contribution through ablation (§ V-B ).
The 3-param model separates wave and CTA effects,
halving mean regret. The 4th term ( log \log ) is critical for
DSv3’s sub-wave regime ( n tiles = 2 n_{\mathrm{tiles}}{=}2 , grid always
 < SM <\mathrm{SM} ), where the grid-time curve is concave rather
than linear; it reduces DSv3’s max regret from 37.5 % 37.5\% to
 1.5 % 1.5\% . A 5th term ( g 2 g^{2} ) provides negligible further
improvement, confirming four terms are sufficient. 

 The log ⁡ ( g + 1 ) \log(g{+}1) term activates adaptively : it is included
only for configs whose median profiling grid falls below
 SM ​ _ ​ COUNT \mathrm{SM\_COUNT} (the sub-wave region). Configs with larger
grids use the 3-parameter base ( d = 0 d{=}0 ). This selective
activation prevents overfitting on multi-wave models while
capturing sub-wave concavity on architectures like DSv3. 

 Fitting. Three or four parameters per config are fitted
via ordinary least squares from profiling at 5 batch sizes
 × \times 5 balancedness levels = 25 =25  points per config.
 Why OLS rather than a learned model? We compared OLS
against a Random Forest (50 trees, max depth 5) and an MLP
(32 × \times 16 hidden units) trained on the same 25 points per
config with features [ g / SM , g , log ⁡ ( g + 1 ) ] [g/\mathrm{SM},g,\log(g{+}1)] . On
held-out test points, the MLP achieves 2.0 % 2.0\% mean regret
(vs. OLS 6.8 % 6.8\% ), but with 624 parameters per config fitted
from 25 samples, it is severely overparameterized. OLS wins on
deployment cost (4 floats per config, no ML framework dependency),
physical interpretability ( a ≈ a\approx pipeline fill, b ≈ b\approx 
wave overhead, c ≈ c\approx per-CTA traffic), and
cross-architecture generalization—the parameters cluster by
performance region (§ V-D ) because they
capture hardware physics, not model-specific artifacts. Fitting
requires a single matrix solve (under 1 ms per config).
End-to-end profiling takes 10–24 minutes per model. 

 Extensibility. Adding a new optimization dimension
(e.g., GROUP_M) appends C new C_{\mathrm{new}} configs to the pool
and profiles them at the same 25 points. The profiling cost grows
 linearly in the number of dimensions, not multiplicatively
as in combinatorial autotuning. 

 Runtime dispatch. At serving time, the cost model
evaluates all configs against the current expert histogram via a
single fused Triton kernel on GPU that performs a bincount,
vectorized cost evaluation, and argmin, all in approximately
 38 ​ μ 38\,\mu s. The dispatch result is cached per step and keyed on
total token count M M ; subsequent MoE layers reuse the cached
config. At each new step, the cache is cleared and the first
layer re-dispatches from the fresh routing histogram.
The total memory footprint is
4 floats × \times 268 configs × \times 4 bytes = 4.3 =4.3  KB per
model.

 IV-C Co-Designed Fused MoE Kernel 

 A routing-aware cost model requires a configuration space wide
enough to exploit routing variation. Alpha-MoE exposes 2 tile
families; DeepGEMM fixes bm = 128 \texttt{bm}{=}128 . We implement a
1,738-line CuTe DSL  [ 9 ] fused 3-phase kernel (W8A8 FP8,
 128 × 128 128{\times}128 block scales) that exposes 134–268 valid
configurations per model on H200. 

 The kernel implements the standard fused MoE forward pass: Phase 1
gathers token activations via cp.async and computes
up-projection through WGMMA; Phase 2 applies SwiGLU with
in-register FP8 re-quantization (no HBM write); Phase 3 computes
down-projection and scatters via cp.reduce.async.bulk .
Producer-consumer warp specialization with stg -deep
pipelines hides TMA latency. 

 Configuration diversity. Hardware constraints (shared
memory ≤ 227 \leq 227  KB, register budgets, WGMMA alignment) yield
134 valid configs for Regime-A models and 268 for Regime-B
(GROUP_M variants included). Configs span four tile families
( ttn ∈ { 256,512 } \texttt{ttn}\in\{256,512\} ), pipeline depths 1–5, and token
blocks bm ∈ [ 2,104 ] \texttt{bm}\in[2,104] . Two design choices expand the
space: dynamic register allocation (supporting
 bm up to 104 vs. 72 in prior work) and grid
overlaunch (upper-bound grid with early-exit, eliminating GPU-to-CPU
sync for exact grid computation). 

 Polymorphic modes. GROUP_M swizzle, split-K ( sk = 4 \mathrm{sk}{=}4 
in grid z-dimension), tile families, and compile variants are all
selected at compile time but dispatched at runtime by the cost
model. Split-K partitions Phase 1’s K-reduction across 4 CTAs,
filling idle SMs at sub-wave operating points
(Figure  6 ). CuTe DSL compiles each configuration
in ∼ 5 {\sim}5  s via TVM-FFI JIT. 

 IV-D Runtime Dispatch 

 At serving time (Figure  5 ), a single fused
Triton kernel performs three operations: (1) expert histogram via
atomic bincount, (2) vectorized cost evaluation of
Eq.  6 for all configs, and (3) argmin to select
the optimal config. Total latency: ∼ 38 ​ μ {\sim}38\,\mu s, amortized to
 < 2.5 ​ μ {<}2.5\,\mu s per MoE layer via per-step caching. The result is
transferred to Python via a single .item() call; no
additional CPU-GPU sync occurs. 

 Both static and routing-aware modes launch the same compiled
kernel binary —the only difference is config selection. Any
observed speedup is therefore attributable to better dispatch, not
kernel implementation differences. 

 The cost model formulation (Eq.  6 ) depends only
on the CTA grid, not the kernel. Profiling a new backend requires
only timing its configs at 25  ( S , β ) (S,\beta) points and fitting via
OLS; no source modification is needed. This kernel-agnostic
property is validated experimentally in
Table  VI . 

 Per-step amortization. The dispatch result is cached for
all MoE layers within a single forward step. This is justified by
the low cross-layer β \beta variance ( 0.0008 0.0008 , measured across
9,728 per-layer observations); per-layer dispatch provides only
 1.02 − 1.04 × 1.02{-}1.04\times additional gain (§ V-E ).
The total memory footprint is
4 floats × \times 268 configs × \times 4 bytes = 4.3 =4.3  KB per
model.

 VI Related Work 

 MoE training systems. 
MegaBlocks  [ 10 ] , Tutel  [ 11 ] ,
FasterMoE  [ 12 ] , and ScatterMoE  [ 13 ] 
optimize communication and compute for MoE training.
SonicMoE  [ 8 ] achieves near-roofline training throughput
via IO-overlapping kernels. These address training; our work
targets single-GPU inference dispatch. 

 MoE inference kernels. 
Alpha-MoE  [ 5 ] provides a JIT-tuned fused kernel
( ∼ 2 {\sim}2  hours per model);
DeepGEMM  [ 6 ] offers JIT-compiled grouped GEMM with
fixed bm = 128 \texttt{bm}{=}128 ;
FlashInfer  [ 7 ] integrates CUTLASS kernels with
autotuning. All use static per- M M dispatch. Our cost model is
 kernel-agnostic : it improved Alpha-MoE’s own kernel by
 1.14 × 1.14\times  (§ V-C ) without source modification. 

 Autotuning and performance modeling. 
vLLM  [ 4 ] , SGLang  [ 14 ] , and
Triton  [ 15 ] select configs via offline sweeps;
TVM/Ansor  [ 16 ] searches via learned cost models.
All scale combinatorially with optimization dimensions and produce
static dispatch tables; our wave model adds new dimensions at
 linear profiling cost.
The roofline model  [ 17 ] classifies compute- vs. memory-bound kernels; the ECM model  [ 18 ] adds cache hierarchy
effects. Our region analysis extends this to MoE dispatch: where
roofline predicts bottleneck type , our variables predict
which specific optimizations help, with thresholds derived
from hardware constants. 

 VII Conclusion 

 We presented RaMP, demonstrating that routing-aware kernel
dispatch is a fundamental missing axis in MoE inference
optimization. A performance-region analysis derived from hardware
constants identifies when each optimization helps across all
8 tested architectures. A four-parameter wave cost model achieves
 0.93 % 0.93\% mean regret and 1.22 × 1.22\times kernel speedup over static
dispatch. Because the model depends only on CTA grid geometry, it
is kernel-agnostic : applied to Alpha-MoE with no source
changes, it delivers 1.14 × 1.14\times . Deployed in vLLM, the full
system achieves 1.30 × 1.30\times end-to-end speedup over Triton FP8,
 1.41 × 1.41\times over DeepGEMM, and 1.13 × 1.13\times over FlashInfer
CUTLASS on OLMoE, and 1.10 × 1.10\times on Qwen3.5-A3B. 

 Limitations. 
(1) Validated on Hopper W8A8 FP8; extending to Blackwell requires
re-profiling but not re-derivation.
(2) Single-GPU scope; expert-parallel communication is orthogonal.
(3) At S = 1 S{=}1 or under perfectly uniform routing ( β = 1 \beta{=}1 ),
routing-aware and static dispatch converge by design.
As MoE architectures continue to scale expert counts and routing
complexity, we believe routing-aware dispatch will become
a standard component of inference serving stacks.
