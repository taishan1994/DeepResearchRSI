ServeTwin:
A Benchmark-Validated Simulator for Distributed LLM Architecture Exploration

 Abstract. 

 Evaluating distributed LLM serving designs on physical clusters is costly. Yet existing simulators provide only subsets of the capabilities needed for realistic design exploration: stateful closed-loop execution, timing prediction without profiling target hardware, and direct execution of unmodified serving benchmarks. We present ServeTwin, a closed-loop simulator that couples specification-driven analytical timing with a stateful serving loop. This coupling captures feedback among request completion, scheduling, queue state, and KV-cache evolution, including prefill–decode disaggregation and multi-turn agent workloads. 

 ServeTwin avoids target-hardware operator profiling through iSTAGE, an analytical trace generator that derives per-iteration traces from model
and engine specifications while representing ragged batches and discrete engine mechanisms such as CUDA-graph batch padding. It further decomposes execution time into component-owned throughput, scheduler, and runtime costs. This ownership lets unaffected parameters transfer across platforms and confines recalibration to changed hardware or software components. ServeTwin implements a vLLM-compatible interface and runs unmodified serving benchmarks. Against real deployments, it reproduces InferenceX’s steady-state throughput–interactivity frontier with a 3.6% mean error and predicts LMBenchmark’s multi-turn performance with a 9.9% error while tracking KV-cache evolution. Pre-silicon sweeps reveal that the preferred HBM bandwidth–capacity tradeoff reverses across workload states and that increasing concurrency shifts the bottleneck from memory bandwidth to scheduler and runtime overheads. Together, these capabilities enable practical exploration of distributed LLM serving systems before target hardware is available.

 1. Introduction 

 Large Language Model (LLM) serving extends far beyond accelerating isolated tensor operations; it has evolved into a highly dynamic systems engineering challenge. Fundamentally, the autoregressive nature of LLMs dictates a strict two-phase execution for every request: a prefill phase that processes the prompt to generate a KV cache, followed by an iterative decode phase. While modern engines like vLLM  ( Kwon et al., 2023 ) and SGLang  ( Zheng et al., 2024 ) employ continuous batching  ( Yu et al., 2022 ) to dynamically mix these phases and maximize throughput, the differing compute profiles of prefill and decode have driven a recent architectural shift. Today, modern deployments physically disaggregate these two phases onto separate workers, coupling them via KV cache transfer  ( NVIDIA, 2025b ) . This architectural complexity is further amplified by agentic workloads. Unlike simple pass-through queries, agentic clients introduce a strict multi-turn dependency, issuing subsequent requests only after receiving the previous response. This shift transforms LLM serving into a highly interactive, stateful system loop, demanding sophisticated evaluation.

 Production metrics like TTFT and queue transients emerge from a continuous feedback loop: serving state dictates each iteration’s batch, while hardware execution time updates the subsequent state (e.g., queue depth and KV-cache occupancy). Consequently, faster hardware inherently alters the batches themselves, rendering fixed-batch models inadequate. While evaluating architectural improvements under these dynamic conditions is critical, the prohibitive scale and cost of LLM infrastructure drives an urgent demand for high-fidelity simulators that capture this end-to-end dynamic environment. Rapidly evolving agentic workloads compound that demand. 

 Existing simulators fail to capture this continuous loop. Analytical models (e.g., GenZ  ( Bambhaniya et al., 2024 ) , LLMCompass  ( Zhang et al., 2024 ) ) evaluate static workloads without queueing feedback, while serving simulators (e.g., LLMServingSim  ( Cho et al., 2024 ) , Vidur  ( Agrawal et al., 2024 ) ) reproduce scheduling but rely on rigid physical hardware profiles. Crucially, current tools fundamentally fail at dynamic state management, particularly in prefill/decode disaggregation. For example, LLMServingSim treats prefill/decode disaggregation as a simple pipeline cut. It lacks a way for the prefill worker to temporarily hold the KV cache if the decode worker is busy. As Figure  1 shows, this creates a fundamental simulation failure, not just a timing inaccuracy. Multi-turn workloads simply crash because requests attempt to enter the decode phase without any queue to safely wait in. 

 ServeTwin reconnects this severed feedback loop and resolves these state failures, as illustrated in Figure  2 . Running unmodified multi-turn benchmarks, it completes execution under deployment-equivalent KV budgets by properly staging the waiting path. Each iteration, it constructs a batch mirroring production LLM engines (e.g., vLLM, SGLang), strictly enforcing admission control, cross-worker KV transfers, and multi-turn states. To process this without empirical profiles, we introduce iSTAGE—extending STAGE  ( Man et al., 2026 ) to translate the batch into a symbolic trace, calculating latency directly from hardware specifications.
Feeding this precise timing back to advance the system state naturally dictates the next batch composition. 

 Integrating an analytical model within a dynamic serving loop poses profound challenges. First, serving batches are inherently ragged; naïvely padding them to maximum dimensions for analytical graphs overestimates execution time by up to 146 × \times . Second, theoretical FLOPs and memory bandwidth cannot capture discrete runtime mechanisms (e.g., KV page walks, kernel launches) that heavily skew step latency. Finally, continuous end-to-end simulation demands exceptionally lightweight trace generation. iSTAGE overcomes these hurdles through (1) statistics-preserving batch binding, (2) first-order modeling of discrete engine mechanisms, and (3) aggressive trace reuse. 

 We validate ServeTwin across two distinct evaluation paradigms. For steady-state performance, InferenceX  ( SemiAnalysis, 2026 ) evaluates system throughput and interactivity frontiers. Because it largely operates without the unpredictability of prefix-cache hits, ServeTwin easily tracks physical performance with just a 3.6% mean error. In contrast, LMBenchmark  ( LMCache Team, 2025 ) introduces the chaotic dynamics of multi-turn serving. In this environment, real-time prefix-cache hits constantly shift the execution timing balance between prefill and decode (P/D) phases, dynamically cascading into admission control and queueing variations. Despite this extreme runtime complexity where prior methods simply crash, ServeTwin successfully captures these transient dynamics within a 10% error margin. 

 This paper makes the following contributions: 

 (1) 

 Stateful Serving Model: A dynamic serving model that explicitly tracks request scheduling, multi-turn sessions, and KV-cache lifecycles, featuring occupancy-coupled admission for prefill/decode disaggregation rather than simplistic fixed-delay handoffs (§ 3.2 –§ 3.4 ). 

 (2) 

 Spec-Driven Execution (iSTAGE): An analytical trace generator that derives execution timings directly from hardware and model specifications, eliminating the need for empirical profiles while remaining lightweight enough to operate inside the serving loop (§ 3.5 ). 

 (3) 

 Component-Owned Cost Decomposition: A mechanism-attributed cost ledger that separates specification-driven throughput from host-control and runtime-mechanism costs. Each term family is assigned an observable ablation footprint and an owning component, enabling selective recalibration only when that component changes instead of global overhead fitting or per-point retuning (§ 3.6 , § 4.2 –§ 4.4 ). 

 (4) 

 Benchmark-Validated Architectural Exploration: Validation against unmodified public benchmarks across hardware generations, serving stacks, and deployment scales, followed by spec-driven hardware sweeps that reveal a workload-dependent trade-off between HBM bandwidth and capacity and a bottleneck shift from memory physics toward runtime control overheads (§ 4.5 –§ 4.8 ). 

 2. Background and Motivation 

 2.1. LLM Serving as a Stateful System 

 LLM serving entails two distinct phases: prefill (processing prompts to generate a KV cache) and decode (iteratively generating tokens, expanding the cache). Modern engines dynamically reconstruct batches every iteration via continuous batching and chunked prefill, while leveraging prefix caching for history reuse. Crucially, execution is fundamentally state-dependent. A request is admitted only if sufficient KV memory exists; otherwise, it queues or preempts. Because discrete runtime mechanisms often reshape physical execution (§ 3.5 ), simulators must explicitly track the dynamic system state (e.g., KV occupancy) that governs batch composition, rather than merely counting requests. 

 2.2. Prefill/Decode Disaggregation and KV Transfer 

 Disaggregated architectures  ( Patel et al., 2024 ; Zhong et al., 2024 ; Qin et al., 2025 ) isolate prefill and decode workers to prevent long prompts from stalling token generation. This necessitates transferring the KV cache between workers. However, this handoff is not a static network delay. Production systems (e.g., Dynamo  ( NVIDIA, 2025b ) with NIXL  ( NVIDIA, 2025a ) ) implement a pull mechanism where decode workers fetch KV blocks only when they have sufficient free capacity. If decode memory is full, the cache remains staged on the prefill worker, creating upstream backpressure. Accurate simulation requires tracking this occupancy-coupled admission and the resulting capacity-driven dependencies (§ 3.3 ). 

 2.3. Benchmarks Used in This Paper 

 We validate ServeTwin using two distinct benchmarks. 

 InferenceX   ( SemiAnalysis, 2026 ) maps the steady-state balance between throughput and interactivity. We validate our simulator against the public hardware performance data published online by SemiAnalysis. 

 LMBenchmark   ( LMCache Team, 2025 ) captures dynamic, multi-turn behaviors like admission pressure and transient delays. We validated this by deploying an in-house DGX H100 with NVIDIA Dynamo and vLLM, directly matching ServeTwin’s behavior with physical telemetry data extracted via Prometheus and Grafana. 

 2.4. Existing Simulation Approaches 

 Serving Simulators. Tools like LLMServingSim  ( Cho et al., 2024 ; Cho et al., 2026 ) , Vidur  ( Agrawal et al., 2024 ) , and AgentServeSim  ( Rajib et al., 2026 ) model continuous batching and scheduling but fundamentally rely on hardware-profiled latencies. Furthermore, they omit critical stateful semantics: LLMServingSim relies on open-loop trace replay that breaks multi-turn session dependencies, and models prefill-to-decode disaggregation as an unconditional pipeline cut lacking staged-KV backpressure. Vidur and AgentServeSim similarly lack occupancy-coupled KV lifecycles. 

 Analytical Models. GenZ  ( Bambhaniya et al., 2024 ) and LLMCompass  ( Zhang et al., 2024 ) estimate execution timings directly from hardware specifications, enabling architectural exploration. However, they evaluate static workloads offline (i.e., snapshots), completely lacking the dynamic closed-loop scheduling required to iteratively update batch compositions. 

 STAGE. STAGE  ( Man et al., 2026 ) synthesizes symbolic tensor graphs for distributed LLM workloads and includes an inference case study. Its abstraction, however, models prescribed workload graphs rather than a stateful serving loop: it does not represent KV-cache lifecycles, queueing feedback, or the scheduler-generated ragged batches that change at every iteration. Adapting it for serving therefore requires the serving-specific mechanisms described in § 3.5 .

 3. ServeTwin Design 

 3.1. Overview 

 Figure  2 illustrates ServeTwin’s closed-loop architecture. Unmodified clients interact via a lightweight wall-clock-to-simulated-time interface. Each iteration executes four stages: (1) The stateful serving loop admits and batches requests under dynamic memory and token budgets, tracking KV lifecycles. (2) iSTAGE binds the batch shape to a symbolic tensor graph, emitting a Chakra execution trace  ( Sridharan et al., 2023 ) . (3) ASTRA-sim  ( Won et al., 2023 ) evaluates the trace; employing a structural network simulator rather than closed-form equations captures topology-dependent collective communication overheads. (4) The resulting execution time advances the simulated clock and updates system states to drive subsequent batching. 

 3.2. Serving-State Simulation 

 While the baseline scheduling logic builds upon LLMServingSim  ( Cho et al., 2024 ; Cho et al., 2026 ) , we redesign its internal state management to achieve strict closed-loop fidelity. Through this redesign, ServeTwin models production systems like vLLM and SGLang, supporting continuous batching, chunked prefill, radix-tree prefix caching, and capacity-driven preemption. To track these dynamics, we introduce a KV lifecycle registry featuring Dynamo-inspired pull-based handoffs (§ 2.2 ), occupancy-coupled admission, tiered memory, and a dedicated multi-turn session layer. Finally, iSTAGE and ASTRA-sim replace the legacy profile-based backend, enabling fully spec-driven simulation. 

 Figure 3. Capacity-driven KV handoff in disaggregated serving. Decode-side capacity regulates KV transfers, naturally backpressuring the prefill stage when the pool is full. 

 3.3. Disaggregated KV Lifecycle 

 In ServeTwin, a request’s KV cache transitions through an explicit state machine (Figure  3 ), from initial allocation to eventual eviction or demotion. Unlike a simplistic pipeline cut, this lifecycle enforces two critical couplings. First, admission is occupancy-coupled : decode-side memory saturation blocks admission, naturally inducing backpressure on the prefill queue. Second, KV transfer is strictly consumer-driven : staged KV awaits an explicit pull from the decode worker (modeling NIXL-style handoffs  ( NVIDIA, 2025a ) ). Decoding commences only upon full KV arrival or suffix recomputation, supporting both full and layer-wise transfers. 

 Implementation components include a prefill-side registry with heartbeat leases, a decode-side wait queue, bandwidth-constrained transfer tracking, radix-tree-aware delta pulls, and a recompute fallback. By explicitly modeling these mechanisms, ServeTwin captures crucial second-order dynamics—such as localized queue buildups, network backlogs, and KV-induced admission stalls—that unconditional pipeline models obscure. 

 3.4. Multi-turn Sessions as Simulator State 

 Unlike traditional trace-driven approaches that statically unroll conversations into independent requests, ServeTwin tracks multi-turn sessions as internal simulator state. A session issues a subsequent turn only after the preceding response is fully generated, reflecting strict inter-request dependencies and optional tool-execution delays. Because context accumulates continuously across rounds, the integrated prefix cache (§ 3.2 ) translates shared history into cache hits and minimal delta transfers. 

 Furthermore, ServeTwin supports tiered KV memory management: blocks evicted from HBM can be demoted to host memory and promoted back upon subsequent hits, with all data movement strictly constrained by the host-to-device interconnect bandwidth. Additionally, speculative decoding is analytically incorporated via a parameterized per-step acceptance length. Collectively, these state-tracking mechanisms capture the workload semantics inherent to the multi-round agentic scenarios evaluated by LMBenchmark.

 3.5. Spec-Driven Execution Modeling with iSTAGE 

 While STAGE  ( Man et al., 2026 ) provides foundational spec-driven graph synthesis for distributed LLM workloads, it does not model the dynamic serving state or KV-aware ragged batches produced by a serving scheduler. To bridge this gap, we develop iSTAGE (Inference STAGE) , which extends and retargets this symbolic execution modeling specifically for serving. This enables accurate, profile-free timing evaluation based purely on hardware specifications. iSTAGE achieves modularity via configuration files rather than hardcoded backends. As summarized in Table  2 , its templates support a wide spectrum of modern architectural features. This breadth is essential for architectural exploration, as varying model structures fundamentally shift system bottlenecks across compute, bandwidth, memory capacity, and communication. 

 However, integrating these models into an iterative serving loop introduces three unique challenges absent in training simulations: (1) modeling irregular (ragged) batches without padding-induced cost distortions; (2) capturing discrete engine mechanisms that alter latency independently of theoretical FLOPs/bytes; and (3) ensuring trace generation is lightweight enough for per-iteration execution. As illustrated in Figure  4 , iSTAGE resolves these by replacing naïve rectangular schemas with statistics-preserving batch binding and applying capture-size padding to reflect actual engine discreteness. 

 Ragged Batches. 

 Symbolic execution graphs typically require rectangular inputs, but LLM serving batches are inherently ragged, comprising requests with varying new tokens ( q i q_{i} ) and KV lengths ( k ​ v i kv_{i} ). Padding to the maximum lengths (max-folding) substantially overestimates compute costs, especially in mixed prefill–decode batches. 

 To resolve this without losing analytical efficiency, we observe that the underlying cost model depends only on aggregate statistics: total tokens ( ∑ q i \sum q_{i} for dense GEMMs), attention FLOPs ( ∑ q i ​ k ​ v i \sum q_{i}kv_{i} ), and KV footprint ( ∑ k ​ v i \sum kv_{i} ). Therefore, iSTAGE binds the graph dimensions to statistics-preserving averages: Seq = 1 n ​ ∑ q i \mathrm{Seq}=\frac{1}{n}\sum q_{i} and KVSeq = ∑ q i ​ k ​ v i / ∑ q i \mathrm{KVSeq}=\sum q_{i}kv_{i}/\sum q_{i} as shown in Figure  4 a. This guarantees exact token and attention FLOP counts, while precisely matching the KV footprint during pure-decode phases ( q i = 1 q_{i}{=}1 ). 

 Against exact ragged computation, iSTAGE yields a median step-time error of 3.7 % 3.7\% (p95 11 % 11\% ) on mixed prefill–decode batches, versus 268 % 268\% for max-folding. Across all iterations, including pure decode, iSTAGE’s median error is 1.1 % 1.1\% . 

 Engine Discreteness. 

 Beyond batch representation, accurate simulation must account for runtime engine interventions that alter physical workloads. For instance, execution engines routinely pad decode batches to match pre-compiled CUDA-graph capture sizes. This padding constitutes real computational work; in MoE models, it artificially increases the number of distinct experts fetched from HBM, changing actual latency independently of the logical token count (Figure  4 b). To capture this, iSTAGE explicitly models the engine’s discrete behaviors and capture lists as first-order effects (Table  2 ). Consequently, in ServeTwin, performance curve shapes emerge inherently from structural mechanisms, while fitted constants merely calibrate baseline levels. 

 Keeping Trace Generation Affordable. 

 Serving simulations run tens of thousands of iterations, making on-the-fly trace generation a major performance bottleneck. This overhead historically forced analytical models to rely on offline, single-shot evaluations. To overcome this, iSTAGE avoids redundant work by aggressively reusing previously generated traces. It caches recurring batch shapes, collapses identical model layers (layer folding), and skips through repeated decode steps. This reuse does not sacrifice accuracy; layer folding, for example, remains perfectly exact by explicitly re-adding the per-collective network latencies (§ 3.6 ). Ultimately, these caching optimizations (§ 4.7 ) make trace generation lightweight enough to run efficiently inside the closed loop on a single CPU, without GPU acceleration. 

 3.6. Component-Driven Latency Modeling 

 Hardware specifications easily provide baseline times for compute and memory traffic. However, real-world execution includes complex overheads like host scheduling, KV cache traversal, and network startups. If a simulator lumps all these delays into a single, generic "overhead" constant, it cannot accurately predict performance when hardware or software configurations change. 

 To address this, ServeTwin breaks down every overhead by its actual root cause—a principle we call component ownership . Every delay in our model must map to a specific system operation, scale based on clear variables (like request count or context length), and remain unchanged unless that specific operation changes. Consequently, the total time for each iteration is the sum of three distinct components:

For prefill, we use a compute utilization curve that scales with the number of tokens.  Crucially, these mechanism costs do not overlap with the network simulator. While ASTRA-sim handles the actual data transfer time, our calibrated terms isolate only the auxiliary startup and synchronization delays; the two components divide the work clearly without double-counting. Table  3 summarizes these costs and their system owners. To prevent these terms from becoming unjustified fitting parameters, ServeTwin enforces three strict rules: 

 (1) 

 Use specifications directly: Peak compute, memory bandwidth, and engine capture lists are drawn strictly from hardware and software specifications, never from curve fitting. 

 (2) 

 Ground terms in observation: We introduce overhead terms exclusively when warranted by empirical scaling trends. For instance, a cost profile scaling with context length isolates KV-cache traversal, whereas an overhead persisting across hardware transitions signifies software-stack overheads. 

 (3) 

 Fix and reuse values: Calibrated parameters are frozen and consistently applied across all operating points and platforms, provided their underlying components remain unaltered. This breaks away from conventional practices—such as tuning a generic overhead percentage—that overfit a single scenario and fail to generalize. 

 Separating these sources is critical for accuracy. For instance, on a high-batch H200 decode step, throughput physics takes 12.7 ms, but control and mechanism overheads add 11.1 ms—comprising nearly half the total time, not just a rounding error. 

 By adhering to component ownership, ServeTwin makes falsifiable predictions: removing a term primarily affects the serving conditions it represents (§ 4.3 ), parameters transfer safely across platforms (§ 4.4 ), and swapping a component requires re-calibrating only its specific owner (§ 4.5 ). 

 4. Evaluation 

 4.1. Experimental Setup 

 Our evaluation answers five research questions based on the predictions of our component-driven model: 

 • 

 RQ1 (Attribution): When we remove one overhead term, does accuracy degrade where we expect it to (§ 4.3 )? 

 • 

 RQ2 (Transferability): Can the same parameters be reused across different hardware systems without re-calibration, and when only one component changes, is it sufficient to re-calibrate only the parameters associated with that component(§ 4.4 )? 

 • 

 RQ3 (Fidelity): Does the simulation accurately reproduce both steady-state and transient serving dynamics (§ 4.5 , § 4.6 )? 

 • 

 RQ4 (Cost): Is the simulator lightweight enough for extensive design sweeps (§ 4.7 )? 

 • 

 RQ5 (Design): Can high-fidelity simulation alter pre-silicon design decisions (§ 4.8 )? 

 Configurations and Workloads. Our primary evaluation uses DeepSeek-R1 (671B MoE, FP8) on 8 × \times H200 and H200/B200 disaggregated deployments (Dynamo with SGLang workers). For transient dynamics (§ 4.6 ), we deploy Qwen3-32B on a 2 × \times H100 setup and validate against Prometheus/Grafana telemetry on LMBenchmark. To isolate pure pipeline overheads and prevent mixing KV transfers with collective communications (e.g., TP/EP), we strictly assign one GPU for prefill and one for decode, restricting NVLink traffic solely to KV transfers. To evaluate binding accuracy (§ 3.5 ), we analyze 44,220 iterations across 10 runs, encompassing steady-state decode, chunked prefill, and multi-turn contexts (up to 21K tokens). 

 Validation Methodology. To ensure an exact comparative validation, we execute unmodified benchmarks through our endpoint interface (§ 3.1 ). We calibrate model parameters using a subset of the measurement points from the public InferenceX dashboard and evaluate the resulting model on the remaining held-out points.

 4.3. Sensitivity Analysis of Cost Terms 

 We conduct an ablation study to verify the necessity of the individual cost families in Table  3 . By removing one term at a time, we evaluate whether prediction errors (reported as absolute percentage points, pp, in Figure  5 ) increase specifically under the serving conditions each term is designed to represent. Omitting the GEMM utilization term increases prefill prediction error by 56 56  pp, showing that peak compute rates alone do not capture effective GEMM performance. Per-step host control: Removing this increases small-batch decode error by 47 47 pp, demonstrating that CPU overhead remains significant even for small GPU batches. DPA synchronization: Removing this increases DPA-decode error by 40 40 pp. Other terms (e.g., KV traversal, collective costs) similarly dominate prediction errors under their corresponding conditions. These results justify maintaining separate cost terms rather than using a generic, interchangeable correction factor, an approach that conceptually aligns with LIMINAL  ( Davies et al., 2025 ) .

 4.6. Transient Serving Fidelity: LMBenchmark 

 To evaluate transient dynamics, we use LMBenchmark  ( LMCache Team, 2025 ) serving Qwen3-32B FP8 on two H100 GPUs (1 prefill, 1 decode worker) with vLLM and prefix caching. The baseline configures 1 user, 20 rounds, 2 QPS, 1K-token shared prompt, 10K-token history, and 100-token output. We evaluate three more variants: ISL × \times 2 (20K history), OSL × \times 10 (1K output), and USERS × \times 20 (20 users). 

 Before the main run, 0.5 s-interval two-round warm-ups and short requests populate reusable KV prefixes. During execution, users append to and resend accumulated conversations. Consequently, cache-hit rates naturally rise as repeated prefixes replace cold prefills. We update hardware specifications (memory capacity, HBM bandwidth, peak compute) to H100 and model inputs to Qwen3-32B at TP1. For the MoE-to-dense GEMM shift, we solely re-anchor the prefill GEMM utilization curve based on the baseline scenario. Despite shifting from SGLang to vLLM, we retain the H200 software overheads (KV-traversal, kernel launches, host costs, and CUDA-graphs). 

 Figure  7 compares simulations against actual measurements. ISL × \times 2 increases KV occupancy and cold-prefills, peaking the prefill queue at 16 requests. Initial reuse boosts hit rates, but growing contexts accelerate evictions, eventually lowering hit rates and forcing renewed prefills. Similarly, USERS × \times 20 distributes the 2 QPS across 20 separate per-user histories. These compete for the fixed KV pool without sharing prefixes, causing evictions before reuse. This sustains prefill workloads and lowers cache-hit rates. 

 Conversely, OSL × \times 10 prolongs decoding, keeping KV blocks active. During warm-up, prefills accumulate while decode capacity is busy, causing a decode-admission spike. Longer responses delay subsequent multi-turns, causing cache-hit rates to rise slower than the baseline. However, high cache-hit rates ultimately reduce prefill work, though they cannot eliminate the extended decode phase.

 4.7. Simulation Efficiency 

 Three forms of reuse cut trace-generation overhead. First, we generate each heavily repeated end-to-end trace expression once and reuse it. Second, rather than simulating individual layers, we exploit the layer-wise repetition of a Transformer to jump analytically to the end of all layer executions, a further 4.9 × 4.9\times . Third, a shape cache groups slightly varying tensor shapes (e.g., batch sizes or sequence lengths) into size-based buckets that share one entry, instead of caching every shape separately. Consequently, all experiments, including full calibration sweeps, execute deterministically on a single commodity CPU in minutes.

 Bandwidth vs. Capacity. 

 Figure  8 compares the sensitivity of two workloads to HBM bandwidth and capacity: independent single-turn requests ( W1 : 1K-input/1K-output, fixed concurrency of 64) and multi-turn sessions ( W2 : 20 users, 20 rounds per user, 11–13.2K-token prompts, and 100-token outputs). Both workloads use Qwen3-32B FP8 in a two-GPU H100 configuration with one prefill worker and one decode worker (1P1D). We separately scale HBM bandwidth and the usable memory pool to { 0.7 , 1 , 1.4 } × \{0.7,1,1.4\}\times their baseline values, varying one while holding the other fixed. After subtracting the fixed model-weight footprint,
the capacity sweep yields effective KV budgets of 14.1, 33.3, and 58.8 GiB, respectively. 

 For W1 , increasing bandwidth to 1.4 × 1.4\times baseline improves throughput by 24 % 24\% , whereas increasing the memory pool provides no throughput benefit. Reducing the pool to 0.7 × 0.7\times baseline lowers throughput by 5 % 5\% . These results are consistent with the baseline pool accommodating the active KV working set at the configured concurrency, while memory traffic during decoding remains a performance constraint. Although additional capacity can support larger batches when concurrency is increased, it provides no throughput gain under this fixed workload setting. 

 For W2 , increasing bandwidth to 1.4 × 1.4\times baseline has little effect on end-to-end throughput. Increasing the memory pool to 1.4 × 1.4\times baseline, however, improves throughput by 22 % 22\% and reduces median TTFT from 12.55 s to 0.068 s. The prefix-cache hit rate rises from 22 % 22\% to 93 % 93\% , while median queueing delay falls from 10.46 s to approximately 0.01 s. These changes are consistent with improved retention of reusable multi-turn contexts, reducing repeated prefill computation and queueing pressure. The limited throughput response to additional bandwidth suggests that accelerating memory-bound operations alone does not address the dominant serving constraints in this configuration. 

 Together, these workloads illustrate that the benefits of additional bandwidth and capacity depend on active KV demand, prefix reuse, and the stages that limit serving performance. In particular, capacity can improve responsiveness at a fixed user count by preserving reusable contexts across turns. Evaluating bandwidth–capacity trade-offs therefore requires accounting for cache residency and queueing dynamics alongside concurrency.

 Bandwidth vs. Scheduler and Runtime Costs. 

 Figure  9 evaluates hardware scaling versus software overhead reduction on a validated H200 setup (DeepSeek-R1 FP8, 1K-input/1K-output). Panel (a) shows an aggregated TP8 configuration, while Panel (b) presents a disaggregated deployment scaling to extreme concurrencies. 

 Under low loads (e.g., concurrency 128), hardware bandwidth dominates. Because software queues and communication delays are practically non-existent at this stage, performance scales directly with memory bandwidth, increasing throughput by 28 28 – 63 % 63\% . However, Panel (b) reveals a striking reversal under extreme loads. At a concurrency of 2048, tripling the bandwidth makes raw token generation 60 % 60\% faster, but overall throughput stalls completely, and median TTFT degrades to 52.96 s. The hardware computes faster, but the software (scheduler and inter-worker synchronization) fails to manage the massive influx of requests, causing severe traffic congestion. Conversely, holding hardware fixed and cutting these Scheduler and Runtime costs by 40 % 40\% increases throughput by 60 % 60\% and halves TTFT to 22.92 s. This indicates that at high concurrency, the binding constraint shifts from memory bandwidth to scheduler and runtime costs.
Crucially, the root cause of bottlenecks shifts depending not only on the workload characteristics but also on the current concurrency level being served.

 Batch-Dependent Limits to Hardware Gains. 

 Figure  10 presents a controlled decode-step comparison across different hardware platforms (H200, B200, GB200) to complement the sensitivity study. B B denotes the active batch size on a single decode worker, rather than system-wide concurrency. The total decode step time is decomposed into three model-attributed components: Throughput Cost (analytical trace execution), Scheduler Cost (exposed host CPU work), and Runtime Cost (KV traversal, sequence setup, kernel launch, and collective setup residuals). This comparison uses no capture padding, so the Scheduler component contains only exposed host work. 

 We utilize the hardware calibration profiles from § 4.4 . H200 and B200 share identical runtime coefficients, isolating the pure effect of their hardware specification differences. For GB200, the per-step Scheduler cost (host control) is explicitly reduced from 1.8 ms to 0.635 ms. Consequently, the GB200 results represent a transferred platform-model prediction rather than an empirical measurement. 

 This breakdown explains why hardware upgrades fail to deliver proportional performance gains at small batch sizes. At a low batch size ( B = 1 B=1 ), Runtime Cost dominates, accounting for 63–77% of the total step time. Upgrading from H200 to B200 reduces the Throughput Cost from 1.67 ms to 1.09 ms ( 1.53 × 1.53\times faster), but the total step time only marginally improves from 9.34 ms to 8.76 ms ( 1.07 × 1.07\times ). 

 Conversely, at a high batch size ( B = 32 B=32 ), Throughput Cost accounts for a significantly larger share. Moving from H200 to B200 reduces this cost from 10.94 ms to 6.64 ms ( 1.65 × 1.65\times faster), resulting in a more substantial total step time reduction from 21.34 ms to 17.04 ms ( 1.25 × 1.25\times ).

 5. Related Work 

 Simulators and Analytical Models. Beyond the tools discussed in § 2.4 , most simulators (e.g., APEX  ( Lin et al., 2024 ) ) are validated solely on custom internal testbeds. LIMINAL  ( Davies et al., 2025 ) bounds decode performance using a single lumped overhead term. In contrast, ServeTwin isolates specific mechanism costs to accurately model state-dependent queueing behaviors. 

 Overhead Characterization. While KernelSight-LM  ( Yao et al., 2026 ) profiles host-side overheads via direct instrumentation, ServeTwin complements this approach by analytically inferring these overheads from public measurements and verifying them through component-level parameter transfer. 

 Disaggregated Systems. ServeTwin directly models the underlying mechanisms of modern disaggregated serving architectures pioneered by Splitwise, DistServe, and Mooncake. 

 6. Conclusion 

 ServeTwin predicts LLM serving performance by integrating a KV-lifecycle state machine with a specification-driven analytical backend. Validated against independent public benchmarks, it achieves a 3.6 % 3.6\% mean error on InferenceX frontiers and reproduces queue and cache-reuse dynamics in multi-turn scenarios. By updating calibration parameters strictly based on architectural changes, ServeTwin successfully transfers to new platforms, predicting GB200 NVL72 performance within a 2 % 2\% margin. This capability allows architects to generate serving curves directly from pre-silicon specifications. Finally, our design studies demonstrate that hardware upgrade priorities must align with workload states and service targets.
