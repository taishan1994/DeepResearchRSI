Abstract.
Animation is pervasive on the Web, the CSS animation property alone appears on over three-quarters of webpages.
Yet existing webpage code generation benchmarks target static screenshots, user-triggered interactions, or isolated motion graphics, leaving the ability of multimodal large language models (MLLMs) and coding agents to reconstruct complete animated webpages largely unexplored. To fill this gap, we introduce AnimWeb-Bench, the first benchmark for animated webpage code generation from videos.
It comprises 124 real-world webpages spanning 7 application domains and 33 animation types, with 91.9% of pages combining multiple types, each paired with a reference video and the static assets of the original webpage. We further propose a human-aligned, two-dimensional evaluation protocol: Static Appearance Fidelity measures structure, text, color, and visual similarity on aligned keyframes, while Animation Fidelity tracks UI components across frames and compares their position, size, velocity, and appearance with those in the reference video.
Evaluating 14 MLLMs and three coding agents reveals: (1) reproducing webpage animations is substantially more difficult than reproducing static appearance; (2) explicit frame inspection and render feedback improve the reconstruction quality of coding agents; and (3) rapid, continuous changes are harder to reproduce than discrete state transitions. Our code and dataset are available at starry1001.github.io/AnimWeb-Bench-website .

1. Introduction
Motion is part of the Web’s basic visual vocabulary. The CSS animation and transition properties appear on 77% and 85% of the nearly 8 million mobile pages crawled by the HTTP Archive ( HTTP Archive, 2022 ) , and about half of all pages ship a prefers-reduced-motion query to adapt that motion to users’ needs ( HTTP Archive, 2025 ) .
On these pages, animation is functional rather than decorative: it signals system feedback, preserves continuity across state changes, and directs attention ( Chang and Ungar, 1993 ; Heer and Robertson, 2007 ) .
At the same time, front-end code is increasingly written by Multimodal Large Language Models and coding agents: 84% of developers use or plan to use AI tools in their development process ( Stack Overflow, 2025 ; Zhao et al., 2026 ) , and generating a webpage from a visual reference has become a prominent use case targeted by a growing line of benchmarks ( Si et al., 2025 ; Gui et al., 2025a ) .
Several benchmarks have been proposed to evaluate MLLMs on front-end code generation, but most of them focus on static webpage reconstruction from screenshots ( Laurençon et al., 2024 ; Yun et al., 2024 ; Si et al., 2025 ; Gui et al., 2025a ) . A few studies extend the evaluation to user-triggered interactions. Interaction2Code ( Xiao et al., 2025a ) represents each interaction with screenshots captured before and after a user action, while IWR-Bench ( Chen et al., 2026 ) and WebVR ( Dai et al., 2026 ) use demonstration videos to evaluate the reconstruction of interactive webpages. However, these benchmarks primarily target discrete state changes triggered by user actions rather than animations that unfold continuously over time.
This raises a question that existing evaluations leave open: can AI systems reconstruct not only the visual states of a webpage, but also the continuous dynamics connecting them?
Figure 1 . Overview of the AnimWeb-Bench task and evaluation. Given a reference video and the static assets of a real webpage (top), an MLLM or coding agent generates a single HTML file, which is rendered and recorded in a browser (bottom). Static Appearance Fidelity compares aligned keyframes. Animation Fidelity compares the trajectories of matched UI components.
Answering this question requires moving beyond static appearance and discrete interactive functionality to evaluate the continuous temporal behavior of visual elements. This poses additional challenges: a model must infer motion trajectories, timing, easing, and synchronization from the reference video and express them in executable code. Animation2Code ( Ji et al., 2026 ) took a first step answering it, reconstructing web animation code from videos, but on isolated motion graphics scored within a cropped region.
Real webpages are harder. Many components move in sequence with distinct timing and easing, while coexisting with the page’s layout, text, and media.
Reconstruction requires inferring which components move, when, and how fast. Evaluation requires judging the motion of each component, which frame-level similarity cannot see, region-pooled tracks cannot attribute, and binary rubrics cannot grade.
To bridge this gap, we introduce AnimWeb-Bench, to our knowledge the first benchmark for reconstructing complete real-world webpages together with their time-driven animations from videos.
AnimWeb-Bench comprises 124 real-world webpages spanning 7 application domains and 33 animation types.
As a comparison, an AnimWeb-Bench page contains 1,196 HTML tags on average, versus 71 for an Animation2Code sample.
As illustrated in Figure 1 , each task pairs a reference video with the original webpage’s static assets.
To evaluate the generated webpages, we design a human-aligned protocol with two complementary dimensions: Static Appearance Fidelity , which compares structure, text, color, and visual similarity on aligned keyframes, and Animation Fidelity , which tracks UI elements across frames and compares their position, size, velocity, and appearance with the reference.
All eight metrics correlate with 400 blind pairwise human judgments (Spearman’s ρ = 0.67 \rho=0.67 – 0.74 0.74 ).
We evaluate 14 MLLMs and 3 coding agents on AnimWeb-Bench. Beyond overall performance, we investigate whether coding agents improve over their underlying models and what factors affect their performance, and analyze how different animation types affect reconstruction. Our main contributions are as follows:
•
We introduce AnimWeb-Bench, a benchmark for animated webpage code generation from videos. It comprises 124 real-world webpages spanning 7 application domains and 33 animation types, each paired with a reference video and the original webpage’s static assets.
•
We design a human-aligned evaluation protocol that separately measures how a generated page looks and how it moves.
•
Our comprehensive evaluation of 14 MLLMs and 3 coding agents reveals three key findings: (1) reproducing webpage animations remains challenging for current systems; (2) explicit frame inspection and render feedback improve the reconstruction quality of coding agents; (3) rapid, continuous changes are harder to reproduce than discrete state transitions.
2. Background
2.1. Task Definition
The Animated Webpage Code Generation task aims to reconstruct executable
webpage code by observing the animation effects shown in a reference
video. Given a reference video V r = { I 1 , I 2 , … , I n } V^{r}=\{I_{1},I_{2},\ldots,I_{n}\}
and a set of static assets (e.g., icons, images and embedded videos): A = { a 1 , a 2 , … , a m } A=\{a_{1},a_{2},\ldots,a_{m}\} , a model M M
generates a single executable HTML file C g = M ⁡ ( V r , A ) C^{g}=M(V^{r},A) , with CSS and
JavaScript embedded inline. Rendering and recording C g C^{g} in a browser
produces a video V g = R ⁡ ( C g , A ) V^{g}=R(C^{g},A) (Figure 1 ). The generated video V g V^{g} should
closely approximate V r V^{r} in both visual appearance and animation
dynamics.
2.2. Related Work
UI Code Generation Methods.
Recent advances in multimodal large language models (MLLMs) have spurred a range of methods for generating webpage code from visual inputs.
DCGen ( Wan et al., 2025 ) adopts a divide-and-conquer strategy, DeclarUI ( Zhou et al., 2025 ) integrates segmentation with page transition graphs, and UICopilot ( Gui et al., 2025c ) , LayoutCoder ( Wu et al., 2025 ) , and LaTCoder ( Gui et al., 2025b ) enhance generation through hierarchical or layout-aware modeling.
Instruct4Edit ( Dang et al., 2025 ) provides
a scalable and transparent foundation for natural language-based web editing. ComUICoder ( Xiao et al., 2026b ) promotes component reuse, while EfficientUICoder ( Xiao et al., 2026d ) reduces redundant visual and code tokens.
More recently, Video2Code ( Xu et al., 2026 ) and InterWebCoder ( Xiao et al., 2026a ) extend generation to interactive webpages, focusing on functional correctness and action-triggered state transitions. TTDev ( Wan et al., 2026 ) applies test-driven development method for full-stack website generation and VisualRepair ( Xiao et al., 2026c ) proposes dynamic tool calling and region focusing for front-end bug repair.
Our work complements these efforts by evaluating the reconstruction of continuous webpage animations from videos.
UI Code Generation Benchmarks.
Early benchmarks focus on static webpage reconstruction from screenshots.
WebSight ( Laurençon et al., 2024 ) and Web2Code ( Yun et al., 2024 ) study large-scale HTML generation using synthetic webpages, while Design2Code ( Si et al., 2025 ) and WebCode2M ( Gui et al., 2025a ) introduce real-world data at increasing scales.
MRWeb ( Wan et al., 2024 ) extends evaluation to multi-page websites with external resources, and DesignBench ( Xiao et al., 2025b ) covers generation, editing, and repair across multiple web frameworks. UIBenchkit ( Le et al., 2026 ) provides a unified toolkit for UI2Code methods evaluation.
However, screenshot-based benchmarks cannot evaluate temporal behavior.
Interaction2Code ( Xiao et al., 2025a ) represents individual interactions with before-and-after screenshots, whereas IWR-Bench ( Chen et al., 2026 ) and WebVR ( Dai et al., 2026 ) use demonstration videos to evaluate event-driven interactions and stateful workflows.
These benchmarks primarily capture discrete transitions triggered by user actions, while web animations require recovering continuous dynamics such as trajectories, timing, speed, and easing.
Animation2Code ( Ji et al., 2026 ) directly studies video-to-animation-code generation but focuses on isolated motion graphics rather than complete webpages.
To our knowledge, AnimWeb-Bench is the first benchmark for reconstructing complete animated webpages from videos.

3. AnimWeb-Bench
Figure 2 . Construction pipeline of AnimWeb-Bench.
3.1. Dataset Construction
Figure 2 shows the construction pipeline of AnimWeb-Bench.
Scope.
AnimWeb-Bench focuses on time-driven, page-embedded animations that unfold automatically during the initial page load. We consider animations implemented through DOM elements using CSS or JavaScript, where motion is integrated with the webpage’s layout, text, and media.
Webpage sourcing. We draw webpages from Awwwards ( Awwwards, ) , a web-design showcase whose entries are reviewed by a jury of professional designers and developers. Starting from sites carrying the Animation tag, we crawled up to 100 sites per application domain, collecting 473 URLs of sites submitted between 2025 and 2026. Removing duplicate and inaccessible sites left 452 candidates.
Recording and asset collection. We load each page in headless Chromium (v151.0.7922.34) driven by Puppeteer ( Puppeteer Contributors, ) with a 1920 × 1080 1920\times 1080 viewport and record it at 30 fps (H.264, MP4) from navigation start. Each recording lasts 2–15 s (mean 5.91 s) and covers the page’s initial animation sequence, or one full cycle of a looping animation.
We also crawl and deduplicate the static assets needed for reconstruction, i.e., images, icons, and embedded videos (46.1 per page on average).
Annotation and quality control. We first use GPT-5.6 Sol to propose a domain and a set of animation-type labels for each recording from the video and the page source. Three PhD students with front-end development experience then review every instance: they correct the labels, supplement missing assets, and verify that the recording captures the complete animation.

3.3. Evaluation Metrics
Our evaluation protocol compares the generated video V g V^{g} with the reference video V r V^{r} in two complementary dimensions: static appearance and animation.
We first identify keyframes and animation segments in the reference video and align them with the generated video (Section 3.3.1 ).
We then evaluate static appearance on pairs of matched keyframes (Section 3.3.2 ) and animation on the segments between consecutive matched keyframes (Section 3.3.3 ).
3.3.1. Keyframes and Animation Segments
A webpage animation is a continuous process, but treating every video frame independently leads to redundancy and obscures the underlying state transitions.
To obtain a compact and structured representation, we decompose each video into stable states and the animation phases that connect them.
This decomposition separates the visual appearance of each state from the dynamic behavior that transforms one state into the next, which our two evaluation dimensions assess separately.
Figure 4 . Keyframe extraction on an example from AnimWeb-Bench. The last two detected keyframes have nearly identical content and are therefore merged into k 4 k_{4} .
We define a keyframe as a frame where the page has settled into a stable state, and an animation segment as the interval between two consecutive keyframes that contains the animation leading from one state to the next. To locate keyframes, we measure the degree of visual change around each frame.
For each frame I t I_{t} of a video, we compute the similarity between two frames separated by a short temporal window:
(1)

where I t ​ ( p ) ∈ [ 0,255 ] I_{t}(p)\in[0,255] denotes the grayscale intensity of pixel p p in frame t t , Ω \Omega is the set of pixels of the downsampled frames, and h h is the number of frames spanning 0.2 seconds.
The second term is the mean absolute intensity difference between the two frames, normalized to [ 0 , 1 ] [0,1] , so S ⁡ ( t ) S(t) approaches 1 when the page is unchanged and decreases as the change grows.
Comparing frames across a window rather than adjacent frames ensures that slow animations, whose per-frame changes are small, remain visible in the similarity curve.
As illustrated in Figure 4 , S ⁡ ( t ) S(t) stays close to 1 while the page is stable and drops while an animation is in progress, so each valley of the curve corresponds to an animation phase.
Between two consecutive valleys, the curve returns to a plateau, and we take the first frame on this plateau, i.e., the moment at which the page settles, as a keyframe.

4.1. Experimental Setup
Models.
We evaluate 14 MLLMs on AnimWeb-Bench, including 10 proprietary and 4 open-weight models, as listed in Table 4 . For each task, models are provided with the reference video and a set of composite images containing all processed static assets of the original webpage.
Models with native video support (marked with † in Table 4 ) take the reference video directly.
To accommodate models without native video support, we uniformly sample frames from the video at 2 frames per second and input them as an image sequence.
The task is to generate a single self-contained HTML file with inline CSS and JavaScript that reproduces both the appearance and the animations of the reference webpage.
Each generated page is then rendered and recorded using the same configuration as the reference videos, capturing its own animation sequence in full or one complete cycle if it loops.
All other inference parameters follow the default settings recommended by the model providers.
Coding Agents.
Beyond single-pass generation, we further evaluate 3 coding agents, each powered by one of the MLLMs above: Codex ( OpenAI, 2026a ) with GPT-5.6 Sol, Claude Code ( Anthropic, 2026a ) with Claude Opus 5, and Qwen Code ( Qwen Team, 2026a ) with Qwen3.8 Max (0902), all with medium reasoning effort.
Each agent operates in a sandboxed workspace that contains the task inputs, where it can execute commands, create and edit files, and inspect the inputs, but cannot access outside this workspace or the network.
Unlike MLLMs, which receive inputs directly in their context, agents access the inputs as files and can decide how to process them, for example by extracting frames from the video.
To examine how input format affects performance, we evaluate each agent under two settings: Video , which provides the reference video, and Frames , which provides the same 2 fps frames given to the MLLMs.
In both settings, the workspace contains the composite asset images. The agent returns a single HTML file, which is evaluated in the same way as the MLLM outputs.
Human Evaluation.
While automatic metrics provide a fine-grained assessment of model performance, evaluating how users perceive the generated webpages is also essential.
Following Design2Code ( Si et al., 2025 ) , we conduct a pairwise human evaluation.
(1) Participants. We recruit five annotators through a local university mailing list. All annotators hold at least a B.S. degree in computer science or software engineering and have more than two years of web-development experience.
(2) Procedure. We randomly sample 50 webpages from AnimWeb-Bench and use Qwen3.8 Max (0902) as the baseline.
We select eight models and pair the output of each with that of the baseline on every sampled webpage. Throughout the evaluation, annotators follow a guideline ( , 2026 ) that defines the evaluation criteria for static appearance and animation and provides instructions for handling ambiguous cases.
Annotators view the reference video together with the recordings of the two generated pages, and judge each pair separately on static appearance and animation by selecting “Example 1 better”, “Example 2 better”, or “Tie”.
Annotators are blind to which model produced each page, and pairs are presented in randomized order.
The final label of each pair is determined by majority voting among the five annotators.
4.2. RQ1: Overall Performance
Table 4 reports the results of the 14 MLLMs on AnimWeb-Bench.
Figure 5. Comparison of coding agents with their underlying MLLMs in single-pass generation. Codex is additionally evaluated with frame inspection (FI) and render feedback (RF).
Systems Look Right but Move Wrong.
Animation fidelity is low across the board.
Even GPT-6 Astra, the strongest model, scores below 0.46 on every animation metric, and ten of the remaining thirteen models stay below 0.35.
For every model, each animation score falls below each static score, and Velocity is the lowest of all eight metrics.
Because the two dimensions are computed differently, their absolute values are not directly comparable.
Two further observations, however, show that the gap reflects motion rather than scale.
Animation metrics respond to the kind of motion on a page while static metrics do not (Section 4.4 ), and human annotators prefer every evaluated model over the baseline less often on animation than on static appearance (Section 4.5 ).
Current models fail to infer and encode component-level dynamics in three ways.
First, some animated components are missing from the generated page altogether, and their unmatched trajectories lower all four animation scores (Eq. ( 10 )).
Second, even when a component is animated, its trajectory or manner of change may deviate from the reference. For example, sliding along a different path or scaling instead of sliding, which lowers Position and Size.
Third, and most subtle, is the temporal behavior of motion, namely when and how fast each component moves.
Components may move faster, slower, or in a different direction than in the reference, which lowers Velocity.
They may also appear at the wrong time: elements that the reference reveals gradually or one after another may appear all at once in the generated page, leaving time steps at which only one of the matched components is present and thus lowering all four animation scores.
Appendix E illustrates each of these failures on two webpages.
Faithfully recovering how a webpage moves thus remains an open challenge for current models.
Proprietary Models Lead, but Open-Weight Models Are Closing In.
GPT-6 Astra leads all eight metrics, and Claude Fable 5.1 ranks second on every metric.
Among open-weight models, Kimi K3 ranks third in static Text and CLIP, surpassing GPT-6 Sol, and fifth across all animation metrics, outperforming Claude Opus 5 and approaching GPT-5.6 Sol.
DeepSeek V4.1 Flash and GLM 5.3 Flash perform on par with the proprietary Grok 4.7 and Qwen3.8 Max (0902), and all four outperform the two Gemini models and Doubao-Seed-2.1-pro across all metrics.
4.3. RQ2: Coding Agents
Figure 5 compares coding agents with their single-pass MLLMs.
Coding Agents Do Not Consistently Outperform Their Underlying Models.
We compare each agent with its own underlying MLLM, and find that the benefit of agentic generation depends on both the agent and the input format.
Qwen Code outperforms Qwen3.8 Max (0902) on all eight metrics under both settings, with relative gains of 4.3%–24.7% under Frames and 9.7%–36.1% under Video.
Claude Code shows a reversal: it falls below Claude Opus 5 on all eight metrics under Frames, yet surpasses it on all eight under Video, with relative gains of 7.9%–21.7%.
Codex, by contrast, trails GPT-5.6 Sol on six metrics under Frames and seven under Video, with the remaining metrics changing by at most 1.4%.
Comparing the two input formats, Video yields higher scores than Frames on all eight metrics for both Claude Code and Qwen Code, suggesting that video is generally the more informative input.
Unlike the fixed 2 fps frames, a video allows an agent to choose its own sampling rate, for example, sampling densely around transitions, and can thus reveal intermediate states and timing that sparse frames miss.
For Codex, however, Video outperforms Frames on only three metrics, indicating that this flexibility does not automatically translate into better reconstruction.
The way in which an agent perceives visual input is therefore critical to its performance.
Frame Inspection and Render Feedback Improve Agentic Reconstruction.
To understand why Codex lags behind, we examine its execution traces under Video.
We observe that Codex often extracts frames from the video, tiles them into contact sheets (e.g., nine frames per image), and relies on these sheets rather than on the individual frames (Appendix F ).
Such reduced tiles may obscure fine visual details and subtle changes between frames.
We therefore introduce two additional Video settings for Codex.
In Video + Frame Inspection (Video+FI), the prompt instructs Codex to also inspect each source frame individually at its original resolution whenever it builds a contact sheet.
Video + Frame Inspection + Render Feedback (Video+FI+RF) further provides a recording tool that renders the generated page into a video, allowing Codex to compare its output with the reference and revise the code iteratively.
The two enhancements improve Codex in different ways.
Compared with Video, Video+FI improves all eight metrics by 7.3%–22.0% on the static metrics and 11.6%–15.6% on the animation metrics, and outperforms GPT-5.6 Sol on every metric.
Building on Video+FI, Video+FI+RF further raises all four animation metrics by 4.0%–7.0%, whereas the static metrics change by only − 0.3 % -0.3\% to 2.5 % 2.5\% .
Frame inspection thus improves overall fidelity, while render feedback mainly benefits animation, likely because comparing the rendered page with the reference video exposes motion errors that are hard to detect from the code alone.
With both enhancements, Codex outperforms GPT-6 Sol on all eight metrics and Claude Fable 5.1 on six, second only to GPT-6 Astra on most metrics.
These results suggest that the bottleneck of agentic reconstruction lies not only in code generation but also in perception and verification: an agent improves substantially once it observes the reference closely and checks how its own page actually moves.
Because the frame-inspection instruction was derived from Codex’s traces on this benchmark, we treat Video+FI and Video+FI+RF as diagnostic interventions that locate the bottleneck rather than as tuned methods.

4.4. RQ3: Animation Types
To compare performance across animation types, we divide the 124 webpages into three mutually exclusive groups based on animation type labels.
(1) Spatial Motion contains at least one animation that moves components in space, such as translation, rotation, shake, or card flip.
(2) Property Change contains no spatial motion but includes changes beyond visibility, such as scaling, color transitions, text animations, or numeric counters.
(3) Visibility Only contains only animations in which components appear or fade in.
The top part of Table 4 reports the average scores of the 14 MLLMs on each group.
Spatial Motion Is the Hardest to Reproduce.
Animation fidelity declines as the animations involve more motion.
On animation metrics, Visibility Only scores the highest, followed by Property Change, while Spatial Motion scores the lowest, with a Velocity only 56% that of Visibility Only.
This ordering reflects the demands of each group.
Visibility changes only require models to determine when elements appear, and property changes alter the size, color, or content of components with limited motion, whereas spatial motion requires recovering how each element travels over time.
The static metrics behave differently: between Spatial Motion and Property Change, they differ by − 0.8 % -0.8\% to + 7.2 % +7.2\% with no consistent direction, whereas all four animation metrics drop by 8.7%–13.4%.
Animation categories thus mainly affect how well models reproduce motion rather than appearance, which shows that Animation Fidelity captures differences that the static metrics miss.
Rapid, Continuous Changes Are Harder than Discrete State Transitions.
Among individual animation types, the most challenging ones change the page rapidly and continuously, often across many elements at once, such as Card Flip, Twinkling, Text Scramble, Text Fragmentation, Shake, and Numeric Counter Animation.
Their intermediate states shift at nearly every frame, making the timing difficult to infer from the reference video and to express precisely in code.
The easiest types, such as Font Weight Animation, Icon State Transition, and Text Substitution, are instead discrete transitions between two clearly visible states, requiring models only to identify the start and end states and connect them with a simple transition. This contrast is also reflected in the bottom part of Table 4 , where webpages with rapid, continuous changes score lower on all metrics than those with discrete state transitions.
4.5. RQ4: Human Evaluation
Figure 6. Human evaluation results against Qwen3.8 Max (0902) on 50 sampled webpages.
Figure 6 shows the human evaluation results, where higher win rates and lower loss rates indicate better reconstruction.
Human Judgments Align with Automatic Metrics.
In both dimensions, human evaluators rank the models in nearly the same order as our automatic metrics.
GPT-6 Astra is preferred over the baseline on 94% of the webpages for static appearance and 92% for animation, followed by Claude Fable 5.1, Kimi K3, and Grok 4.7, whose win rates decline in the same order as their automatic scores.
DeepSeek V4.1 Flash and GLM 5.3 Flash perform close to the baseline, with comparable win and loss rates, consistent with their automatic scores differing from those of Qwen3.8 Max (0902) by less than 0.03 on every metric.
Gemini 3.1 Pro Preview and Doubao-Seed-2.1-pro lose to the baseline on at least half of the webpages in both dimensions, again matching their low automatic scores. All eight metrics correlate positively with human preferences, with Spearman’s ρ \rho ranging from 0.667 to 0.737 (Appendix D ).
Animations Are Harder for Humans to Distinguish.
Compared with static appearance, every model obtains a lower win rate and a higher tie rate on animation.
The rise in ties is particularly pronounced for weaker models: the tie rates of DeepSeek V4.1 Flash, GLM 5.3 Flash, Gemini 3.1 Pro Preview, and Doubao-Seed-2.1-pro rise from 12%–20% to 30%–40%.
When neither animation closely follows the reference, annotators find little basis to prefer one over the other, echoing our finding in Section 4.2 that reproducing animation remains challenging.
5. Conclusion
We presented AnimWeb-Bench, a benchmark for animated webpage code generation from videos, together with a human-aligned evaluation protocol that measures both static appearance and animation fidelity. Our systematic evaluation of MLLMs and coding agents shows that while current systems reproduce static appearance reasonably well, they still struggle to capture the temporal dynamics of webpage animations. Our experiments further demonstrate the benefits of careful visual inspection and render feedback for coding agents. We hope AnimWeb-Bench will support future research on temporal visual understanding and code generation toward more faithful reconstruction of animated webpages.

Appendix B Dataset Statistics
Table 5 reports the statistics of AnimWeb-Bench. Each video lasts 5.91 s and contains 2.83 animation segments and 35.4 tracklets on average, and each sample comes with 46.1 asset files on average.
Following Design2Code ( Si et al., 2025 ) , we measure code complexity with four metrics: Length is the token count of the HTML code under the GPT-2 tokenizer ( Radford et al., 2019 ) , Tags is the number of HTML tags, DOM Depth is the maximum depth of the DOM tree, and Unique Tags is the number of distinct tags. As shown in Table 6 , an Animation2Code ( Ji et al., 2026 ) sample contains only 71 tags on average, with a DOM depth of 5 and 7 distinct tags, since each sample is a standalone animation snippet rather than a complete webpage. In contrast, AnimWeb-Bench pages contain 1,196 tags, a DOM depth of 18, and 33 distinct tags on average, exceeding all the compared webpage benchmarks.
Appendix C Implementation Details
This section specifies the terms and thresholds used in the evaluation metrics of Section 3.3.
Keyframe alignment.
On downsampled frames, Vis \mathrm{Vis} in Eq. ( 2 ) is computed as
Vis = 0.15 ​ s rgb + 0.10 ​ s gray + 0.10 ​ s hist + 0.10 ​ s edge + 0.10 ​ s cos + 0.45 ​ s layout , \mathrm{Vis}=0.15\,s_{\mathrm{rgb}}+0.10\,s_{\mathrm{gray}}+0.10\,s_{\mathrm{hist}}+0.10\,s_{\mathrm{edge}}+0.10\,s_{\mathrm{cos}}+0.45\,s_{\mathrm{layout}},
where s rgb s_{\mathrm{rgb}} and s gray s_{\mathrm{gray}} are one minus the mean absolute pixel differences in RGB and grayscale, s hist s_{\mathrm{hist}} is the RGB histogram intersection, s edge s_{\mathrm{edge}} and s cos s_{\mathrm{cos}} are the cosine similarities of Canny edge maps and of RGB images, and s layout s_{\mathrm{layout}} compares the connected regions of white, colored, and foreground masks. We set λ = 0.85 \lambda=0.85 . Keyframes are aligned by order-preserving dynamic programming, where a pair can be matched only if s ≥ 0.2 s\geq 0.2 , and each unmatched reference keyframe incurs a penalty of 0.12.
Structure similarity.
All boxes are normalized by the frame width and height. For a matched pair ( b r , b g ) (b^{r},b^{g}) in Eq. ( 3 ), s iou s_{\mathrm{iou}} is the intersection over union of the two boxes; s center s_{\mathrm{center}} is the center proximity computed as in Eq. ( 7 ), applied to the centers of b r b^{r} and b g b^{g} ; s area s_{\mathrm{area}} is the ratio of the smaller box area to the larger one; and s aspect s_{\mathrm{aspect}} is the ratio of the smaller aspect ratio to the larger one.
Trajectory construction and matching.
In Algorithm 1 , IoU \mathrm{IoU} is the intersection over union between a detection b b and the latest box of trajectory τ \tau , App \mathrm{App} is the cosine similarity between the CLIP image features ( Radford et al., 2021 ) of the two box regions, and Ctr \mathrm{Ctr} is the center proximity computed as in Eq. ( 7 ). We set θ a = 0.35 \theta_{a}=0.35 and θ t = 0.82 \theta_{t}=0.82 .

We quantify the agreement between our automatic metrics and human judgments using Spearman’s rank correlation coefficient ρ \rho .
The human evaluation in Section 4.5 yields 400 pairwise comparisons (8 models × \times 50 webpages), each between a model and the baseline.
For each comparison, we encode the majority-vote human preference as 1 1 if the model is preferred, 0 0 for a tie, and − 1 -1 if the baseline is preferred, and compute the difference between the model’s and the baseline’s automatic scores on that webpage.
Each metric is correlated with the human preferences in its own dimension, i.e., static metrics with static appearance judgments and animation metrics with animation judgments.
Ties are retained and assigned average ranks.
As shown in Table 7 , all eight metrics correlate positively with human preferences ( ρ = 0.667 \rho=0.667 – 0.737 0.737 ), supporting their alignment with human judgments.
Appendix E Failure Case Studies
Figure 7. Failure cases on two webpages. Frames are ordered from top to bottom in time.
E.1. Case 1: Rotating Gallery Hero
In the reference (Figure 7 (a)), the navigation bar is present from the start. Two photo clusters at the top-right and bottom-left corners then rotate in depth, the paragraph at the bottom right appears, and the headline is finally revealed line by line through a mask.
Claude Fable 5.1 merges the two clusters into a single diagonal strip spanning the page, which lowers Structure. The strip fades in and drifts toward the bottom left instead of rotating in place, so its tiles deviate in Position, Size, and animation CLIP, and move in a different direction and at a different speed, lowering Velocity. The headline fades in rather than emerging from a mask, so its box appears at full size instead of growing as it is unveiled, further lowering Size.
GPT-6 Sol reproduces the masked headline but not the rotation: its photos become small, static fans of cards, lowering Size and Velocity. Its timeline is also reordered: the photos appear before the navigation bar, and the paragraph only after the headline. Components shown in the reference are therefore missing from the generated page for many time steps, which lowers all four animation metrics.
E.2. Case 2: Curtain-Reveal Portfolio
In the reference (Figure 7 (b)), a loading icon animates on a dark screen. A curtain-like background transition follows, in which brown and orange layers sweep upward. The name is then revealed letter by letter from left to right, and the four photos fade in place one after another.
GLM 5.3 Flash omits the loading screen and the transition entirely. The first reference keyframe and segment therefore have no counterpart, lowering all static and animation metrics. The name fades in as whole words instead of being revealed letter by letter, lowering all four animation metrics. The photos rise from below instead of fading in place, lowering Position and Velocity.
Gemini 3.1 Pro Preview keeps the loading screen but not its animated icon. Its transition fades the background color instead of sweeping the layers upward, so the moving layers find no counterpart, lowering all four animation metrics. The two words of the name swap their vertical order, and the text is misplaced, lowering Structure and static CLIP. The four photos slide up from below all at once instead of fading in one after another, lowering all four animation metrics. They also settle enlarged at the wrong positions, further lowering Structure and static CLIP.
Appendix F Coding Agent Execution Trace
Figure 8. Simplified Codex execution log on one webpage of AnimWeb-Bench across three settings. Lines tagged +FI or +RF are steps added by that setting.
Figure 8 shows a simplified Codex execution log on one webpage across the three settings.
The settings are cumulative: FI adds frame inspection to video input, and RF further adds render feedback.
With video input alone, the agent perceives the animation only through contact sheets of downscaled frames (lines 5–8) and returns its first page without ever viewing it (line 10).
Frame Inspection supplies the same moments at full resolution (line 6), exposing details lost in the thumbnails, but the generated page still goes unseen.
Render Feedback closes this loop: the agent records its own page (line 11), extracts frames to compare with the reference (line 12), and revises the code (line 13), repeating this cycle before returning the final page (lines 14–15).
Only under Render Feedback does the agent observe the output it generates, allowing errors in timing and motion to be corrected.
