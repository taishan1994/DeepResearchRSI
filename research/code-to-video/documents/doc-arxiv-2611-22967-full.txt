Abstract.
Coding agents make videos by writing and refining programs in a build–inspect–edit loop. A finished film costs a
median of $2.85 in model calls and 11 minutes, over a third of that time in builds that block the agent.
We find that much of this time is avoidable, for two reasons. First, 37.5% of the frames of a session’s later films were drawn before, many shifted in time or inside an
edited scene. Second, half of the builds stop at a check, where the agent needs only the verdict, but which builds stop is unknown until the checks finish.
We present CodeReel, a training-free execution layer behind agents’ existing commands.
Exact frame reuse keys each frame by its drawing commands, regardless of its position in time, and reuses each
frame whose key recurs.
Blocking-aware scheduling runs the checks first and starts the render alongside them, at idle priority, unless
the session’s recent builds make a pass unlikely. Scheduling spends CPU to answer sooner and reuse returns it; exact keys let later versions use frames rendered for a failed one as the agent thinks.
We introduce EditLoop, a benchmark of replayable agent sessions whose films are checked against renders from
scratch.
On it, CodeReel cuts the agent’s wait by 36.3% against Rebuild, a warm pipeline with parallel
rendering, and by 57.9% against Sequential, today’s step-by-step pipeline. On time-shifting edits its reuse renders 43.9%, close to the 43.0% whose pixels are new, while Manim-style
caching renders 99.8%. With real agents, the median wait per build is 0.62 × \times
Rebuild’s in Claude Code, on topics never used in development, and 0.67 × \times in Codex CLI. The gain holds
for five models and two frameworks.

Rebuild and CodeReel.
Coding agents such as Claude Code ( Anthropic, 2026a ) and Codex CLI ( OpenAI, 2026a ) produce videos by writing
programs ( Chen et al., 2026b ; Ku et al., 2025 ; Liu et al., 2025b ; Li et al., 2026b ; Lin, 2026 ; Chen et al., 2026c ) . To make an explainer film, the agent writes scene scripts, a narration timeline and assets, and then refines them in a loop ( Fig. 1 a). In each round it builds the program, inspects the errors or the film, and revises the sources. Some revisions fix its own defects, such as text over subjects or captions out of sync with the speech ( Chen et al., 2026b ; Li et al., 2026b ; Lin, 2026 ) ; others answer its user’s change requests. Each build is a tool call the agent waits for. A build runs four steps in sequence, as current pipelines run theirs ( Chen et al., 2026b ; Ku et al., 2025 ) : it synthesizes the narration’s voice, lays out the timeline, checks the whole film and, if the checks pass, renders every frame. It returns a verdict, pass or fail, with the film on a pass and the errors on a fail. In 123 recorded
sessions of Claude Code, a finished film takes a median of 10 builds and costs $2.85 in model calls and 11 minutes. The builds take over a third of that time,
each blocking the agent for a median of 25.5 s.
We find that much of this wait is avoidable ( Sec. 2 ). The first cause is redundancy: 37.5% of the frames of a session’s later films were drawn by an earlier version, yet they are rendered again. The second is a
scheduling mismatch: 51.8% of builds stop at a check before any film is made. The agent waits for the verdict or the film depending on an outcome known only when the checks finish, yet the pipeline runs every build in one fixed order.
Challenges.
Redundancy. An agent revises a film incrementally, so the frames an edit does not touch recur: 30.2% of later films’ frames at the same time in the previous film and 6.5% at another time ( Fig. 1 b and Fig. 3 b). Three kinds of edit make recurring frames hard to identify before rendering. First, an edit to a file that scenes
share changes only some frames of the scenes that read it. But a script draws a whole scene from one clock, with no call, node or layer boundary inside it. Caches keyed by an animation call as in Manim ( The Manim Community Developers, 2026 ) , a scene ( Fourier, 2026 ) , a node or layer ( Foundry, 2018 ; Adobe, 2026 ; The Chromium Authors, 2026 ) or a
file ( Mokhov et al., 2018 ; Curtsinger and Barowy, 2022 ) therefore redraw those scenes whole. Second, a narration edit moves every later scene. An incremental renderer such as kamishibai keys a frame by its index ( kamishibai, 2026 ) and so misses frames that did not change. Third, many edits change little of a frame, such as a few words of a caption. Approximate reuse, as in training-free diffusion caches ( Ma et al., 2024 ; Liu et al., 2025c ; Kahatapitiya et al., 2025 ; Lyu et al., 2025 ) and in edit-time methods that recompute only the edited regions ( Li et al., 2022 ; Nitzan et al., 2024 ; Yu et al., 2024 ) , reuses results whose inputs or features change little. But 32.6% of the changed frames keep an SSIM ( Wang et al., 2004 ) above 0.99 to the frame they replace, so it can keep a stale frame that still shows the old words.
Scheduling mismatch. A failing build
should give every core to its checks, and a passing one should start its render at once. The checks and the render
both process the whole film on the same cores, so a render alongside the checks slows the verdict, and one after them
delays the film. The machine is idle while the agent thinks, but the version to build next is not yet written. Pipelines fix the order that completes the film ( Chen et al., 2026b ; Ku et al., 2025 ) , schedulers for agents schedule around tool calls ( Kim et al., 2024 ; Xu et al., 2024 ; Ye et al., 2026 ; Zhang et al., 2026 ) , and test prioritization
reorders the tests of a suite ( Rothermel et al., 2001 ; Prado Lima and Vergilio, 2022 ) . None orders the work inside a build by what the agent is blocked on.
Our approach.
We present CodeReel, a training-free, model-agnostic execution layer behind the commands agents already call, built on
two observations. First, video programs draw each frame from its time alone ( Remotion, 2026a ) , so the commands a frame issues
determine its pixels. Evaluating them costs 2.7 ms of CPU, against 81 ms per frame for a full render. Exact frame reuse therefore keys a frame by its drawing commands, regardless of its position in time, and reuses every frame whose key was rendered before. Second, a build call is synchronous, so the agent is blocked on the verdict until the checks
return, on the film once they pass, and on nothing once the build has answered. Blocking-aware scheduling runs the
checks first and in parallel, and decides from the session’s history and the machine’s cores whether to render alongside them. In the agent’s think time it works ahead, rendering a failed version’s frames, since a stored frame serves any later
version that draws it. Neither technique changes the verdict or the film of a build from scratch.
On recorded sessions replayed on 32 cores, CodeReel cuts the agent’s wait by 36.3% against Rebuild, a pipeline with warm processes and
workers sized to the machine ( Fig. 1 c shows one build). Against Sequential, that pipeline run step by step as today’s agents run theirs ( Chen et al., 2026b ; Ku et al., 2025 ) , the cut is 57.9%. CodeReel answers failing builds in 0.39 × \times Rebuild’s time. Most of the reduction comes from scheduling, which spends CPU to answer sooner; reuse renders 34.9% fewer frames, returns that CPU and helps most where cores are scarce. Real agents wait less as well,
with a median wait per build of 0.62 × \times Rebuild’s in Claude Code, on topics never used in development,
and 0.67 × \times in Codex CLI.
Of the reuse schemes without stale frames, CodeReel renders the fewest frames. On time-shifting edits it renders 43.9%, close to the 43.0% whose pixels are new, while Manim-style caching ( The Manim Community Developers, 2026 ) renders
99.8%. On programs of another video framework, Remotion ( Remotion, 2026b ) , the agent waits
0.51 × \times as long under CodeReel as under Remotion’s own renderer ( Sec. 4 ).
We contribute:
•
EditLoop : a benchmark of replayable agent sessions, every delivered film checked against a render from

•
Exact frame reuse : frames keyed by their drawing commands, shift-invariant, with cheaper tests first, returning the CPU that scheduling spends ( Sec. 3.2 ).
•
Blocking-aware scheduling : a build ordered by what the agent is blocked on, spending CPU to answer sooner, with work ahead in its think time that exact keys let later versions keep ( Sec. 3.3 ).

CodeReel : a general execution layer that existing coding agents use unmodified, across video frameworks

Evaluating an execution layer for code-to-video agents needs a record of what agents did, in a form any system can
replay. Code-to-video benchmarks grade the film ( Chen et al., 2026b ; Chen et al., 2026c ) , a video-editing benchmark adds the
agent’s runtime and cost ( Gupta et al., 2026 ) , and traces of coding agents record tool durations or turn lengths to benchmark LLM serving ( Zhu et al., 2026 ; Pan et al., 2026 ; Lau et al., 2026 ) . None keeps each program version with the tool calls that built it.
EditLoop keeps both, so every system can replay the same calls in order, and it checks every delivered film against a render from scratch. We release the sessions with the replayer and its correctness gate.
2.1. Sessions and tracks
A session records one agent making one film: every version it committed, every tool call in order with its
timing and outcome, the agent’s think time before each call, and the class of edit each build follows.
The real track has 123 sessions of Claude Code ( Anthropic, 2026a ) with Claude Opus 5.5 ( Anthropic, 2026b ) making
explainer films with cv.js, our Canvas 2D ( WHATWG, 2026 ) runtime ( Fig. 2 ): 1,525 versions, 2,078 tool calls and 1,314 builds. Its films run 52 to 146 s between the 10th and 90th percentiles and are narrated in Chinese and English. Of its builds, 39.0% follow edits of new or removed files,
26.1% of narration lines, 12.6% of one scene’s script and 20.4% of shared
scripts or data. It holds every session
recorded over two weeks that built at least two versions. A scripted user issued every change request. Of the sessions, 60 are on
topics that GPT-6.1 ( OpenAI, 2026b ) wrote for EditLoop, each with three rounds of change
requests that build on one another.
The real track is split by topic: the 33 sessions on topics used to tune any parameter
form the development split, and the other 90, on 72 topics that include all of GPT-6.1’s, the test split.
Timing replays one session from each of 70 topics, drawn with a fixed seed. The reuse study takes the 355 pairs of adjacent delivered versions of 88 test-split sessions.
The model track has 20 sessions of Claude Sonnet 5.5 and Haiku 5.5 ( Anthropic, 2026b ) on 10 test topics. The
Remotion track brings a second framework, Remotion ( Remotion, 2026b ) , with synthetic edits whose classes and think times follow the real track’s:
150 versions in 6 sessions.
2.2. Protocol and metrics
Replay is closed-loop ( Schroeder et al., 2006 ) : a system executes a session’s recorded calls in order, each after the previous one has answered, either at once or after the recorded think time. Caches start cold in every session.
Correctness gate. EditLoop requires the from-scratch consistency of incremental computation ( Hammer et al., 2015 ) , and reports a system’s times only if every build keeps it. A build must return the verdict of a build from scratch and no error that the latter does not report, and every frame of every delivered film must equal a render of that version from scratch (supplementary material).
Metrics. Renderers are compared by render time ( kamishibai, 2026 ) , which misses what blocks the agent. We therefore measure the wait , from a build’s call until the build answers the agent: at the verdict when it fails, after the film when it passes.

The real track yields three findings ( Fig. 3 ).
F1: builds take over a third of a session.
In the median session, tool calls take 37.7% of the time and builds alone 37.0%. Builds take a median of 25.5 s and think times 8.0 s.
F2: half of the builds fail.
51.8% of builds stop at a check, for text over subjects, clipped text, captions out of sync or lint
errors. In these builds the agent waits only for the verdict; in the others, the render waits for the checks.
F3: later films repeat 37.5% of their frames, unevenly.
Over the 291 films after a session’s first in the timed test sessions,
37.5% of the frames repeat, command for command, a frame an earlier film drew. Of all frames, 30.2% repeat at the
same time in the previous film, 6.5% at another time in it, and 0.8% only in an older film. Of these films, 37.8% are over nine
tenths new and 11.7% under a tenth.
Exact reuse removes what F3 repeats; blocking-aware scheduling puts F2’s checks first, overlaps the
render with them unless a pass is unlikely, and works in F1’s think time.
3. Method
CodeReel reduces the agent’s wait in two complementary ways, one per observation of Sec. 1 ( Fig. 4 ): exact reuse across versions removes work and frees CPU, and blocking-aware scheduling spends it on what the agent waits for.
3.1. Model
Video programs.
A video program P P defines a film F P F_{P} , one frame F P ​ ( t ) F_{P}(t) at each time t t of a frame grid. It draws each frame onto a canvas, or lays it out as a page, from t t , its source files and the assets they load. CodeReel relies on the frame contract Remotion states
for its programs ( Remotion, 2026a ) : F P ​ ( t ) F_{P}(t) depends on nothing else, not on randomness, earlier frames or wall-clock time. The runtime and the checks catch programs that break it (supplementary material).
Builds.
As build systems model a build ( Mokhov et al., 2018 ) , a build of P P is a directed acyclic graph G P G_{P} of CPU
operations, each serving a consumer. The verdict 𝖵 \mathsf{V} needs each changed narration line voiced, the timeline laid out, the film checked at sampled times and the sources linted. The film 𝖥 \mathsf{F} needs every frame and the sound rendered, the sound’s levels checked and each segment encoded. A later version is the consumer of frames rendered ahead. The verdict o P ∈ { pass , fail } o_{P}\in\{\mathrm{pass},\mathrm{fail}\} is known at T 𝖵 T_{\mathsf{V}} , when its checks
finish. A failing build answers with its errors at T 𝖵 T_{\mathsf{V}} . A passing one answers at T 𝖥 ≥ T 𝖵 T_{\mathsf{F}}\geq T_{\mathsf{V}} , once its film and the checks that need the film have finished, with the film or those checks’ errors. With times measured from the call and [ ⋅ ] [\cdot] the indicator, the agent waits

Problem.
A session builds versions P 1 , … , P n P_{1},\dots,P_{n} , each given what the builds before it computed. The goal is to minimize the
expected total wait 𝔼 ⁡ [ ∑ i W P i ] \mathbb{E}\bigl[\sum_{i}W_{P_{i}}\bigr] over the outcomes, each unknown when its build starts.
Exactness asks for the verdict
of a build of P i P_{i} from scratch and, when it passes, for its film, frame by frame. Capacity asks that the

( Sec. 3.2 ), and orders the rest by consumer ( Sec. 3.3 ).
3.2. Exact reuse across versions
Reuse must decide, without rendering a frame, whether its pixels can differ from those of a frame rendered before.
Following the first observation, CodeReel keys each frame by its drawing commands. Each part that draws the
frame at time t t of P P , a scene’s drawing or an overlay such as subtitles, records the commands it issues through the
runtime’s supported interfaces, with their arguments and drawing state; images and fonts enter by their bytes. The frame’s key is
(2)
κ P ​ ( t ) = h ⁡ ( σ P ​ ( t ) , ν ⁡ ( a 1 ) , … , ν ⁡ ( a m ) ) , \kappa_{P}(t)=h\bigl(\sigma_{P}(t),\nu(a_{1}),\dots,\nu(a_{m})\bigr),
where σ P ​ ( t ) \sigma_{P}(t) holds the frame’s structural inputs, such as its size, fonts and the order of its parts,
a 1 , … , a m a_{1},\dots,a_{m} are the commands in drawing order, ν \nu is their normalization to the rasterizer and h h is a hash.
Like the keys of build systems ( Mokhov et al., 2018 ) and compositors ( Foundry, 2018 ) , a key is sound if equal keys
imply equal outputs, so every reused output is exact, and tight if equal outputs get equal keys, so no output is computed twice.
Property 1 (Soundness).
For a frame drawn under the frame contract through supported interfaces, on one renderer configuration whose rasterizer draws a frame from its commands alone, with ν \nu merging no two commands that the rasterizer draws differently and h h collision-free: if its key equals
that of a frame rendered before, its pixels equal that frame’s.
A frame drawn through an unsupported interface gets no key and is rendered every time. 98.6% of the frames are keyed, and Sec. 4.4 reports the audit of every key.
Normalizing keys to the rasterizer.
If a key changes while the pixels do not, the frame is rendered needlessly; if it stays while they change, a stale
frame is shown. The normalization ν \nu therefore rewrites only the commands whose rasterization we characterized. For example, the rasterizer places text at a baseline snapped to whole device pixels, so such text enters the key with the snapped baseline. Every other number enters a key exactly.
Following frames through time.
A narration edit changes one line’s duration and moves every later scene, so a cache looked up by time or frame
index ( kamishibai, 2026 ) misses every frame of a moved scene, although none changed. The video framework Fourier follows whole layers that
move ( Fourier, 2026 ) . κ \kappa is shift-invariant , since it holds no absolute time: scenes draw from their local time and
start on whole frames. A scene that the next version P ′ P^{\prime} moves Δ \Delta frames later, its other inputs unchanged, therefore issues at t + Δ t+\Delta the
commands it issued at t t , and κ P ′ ​ ( t + Δ ) = κ P ​ ( t ) \kappa_{P^{\prime}}(t+\Delta)=\kappa_{P}(t) for a frame whose other parts do the same.
The cascade.
Evaluating κ \kappa for every frame would still cost a pass over the program, while the frames an edit cannot reach need
no new key, so cheaper tests come first ( Fig. 4 , right). Static impact works like a build system’s file
dependencies ( Mokhov et al., 2018 ; Curtsinger and Barowy, 2022 ) : a scene’s script draws only inside the scene’s time window, so the frames
inside the windows Ω \Omega that the changed scripts reach go to evaluation. Values read tracks dependencies as
they are used, as incremental computation does ( Hammer et al., 2014 ) : the runtime records hashes of the values each
frame read, such as the timeline, the style or an asset entry. A frame outside Ω \Omega keeps its key when they are
unchanged, so editing one style entry sends to evaluation only the frames that read it. Such a frame issues the same commands as before, so its kept key equals κ P ​ ( t ) \kappa_{P}(t) (Property S1 of the supplementary material). For the remaining frames, evaluating κ \kappa runs
the drawing code and records its commands, as browsers and UI toolkits keep display lists ( The Chromium Authors, 2026 ; Flutter, 2026 ) , without capturing
the frame.
What is reused.
A frame store holds the rendered frames by key, per renderer configuration: a build takes from it every frame whose key it holds and renders
the rest, each missing key once. The film’s encoded segments, which hold pictures only, are reused by their frames’ keys, and the checks’ results wherever static impact and values read keep a key.
Another framework.
The key and the store carry over to any runtime that exposes what each frame draws and keeps the frame contract: in
Remotion ( Remotion, 2026b ) this is the laid-out page, its elements with their computed styles and resources by content,
and frames with new keys go to its own renderer.
3.3. Blocking-aware scheduling
The usual pipeline runs every operation at one priority, in the order that completes the
film ( Chen et al., 2026b ; Ku et al., 2025 ) . Following the second observation, CodeReel schedules each
operation by the consumer that waits for its output: the operations the verdict needs run first, those only the film
needs run alongside them when that pays off, and work no one waits for yet runs in the agent’s think time. Each operation also takes its
consumer’s share of the processor. The verdict’s operations ( Alg. 1 ,
lines 5 and 7 ), and the film’s once the agent waits for it ( line 12 ), run at normal priority. A render started early ( line 6 ) runs at idle priority, which gets only the
processor time the others leave. Work ahead A A runs in the background, at low priority, until the next build
starts ( line 3 ) or blocking work needs memory, and keeps the frames it stored.

Within a build: the verdict first.
On half of the builds the agent waits only for the verdict, whose checks cover the whole film. CodeReel runs the checks
first and in parallel, with the lint alongside them. Its fast checks leave out what a verdict does not need: the checks that read a frame’s texts and images sample frames as a key is evaluated, by running the drawing code without capturing pixels, and they map drawn objects to source lines only after the verdict. With few cores, a build also fails fast , as in
test prioritization ( Rothermel et al., 2001 ; Prado Lima and Vergilio, 2022 ) : the checks that seldom fail run only once the others found
no error, and the build answers at its first errors.
Within a build: the render as a bet.
Starting the render alongside the checks is a bet on the outcome, like the sandboxes that agent serving
prewarms ( Zhang et al., 2026 ) . It saves render time when the version passes and slows the checks in either case, so it pays when the expected saving
exceeds the delay. At idle priority, the render slows the checks by a fraction d d and keeps a share s s of its speed, and the bet pays when the version passes with probability above θ c = d / ( s ⁡ ( 1 + d ) ) \theta_{c}=d/\bigl(s(1+d)\bigr)
(supplementary material). Idle priority keeps the bet cheap, with a measured θ c \theta_{c} of 0.25 on 8 cores and 0.21 on 32. 4 takes the bet when
p ^ > θ c \hat{p}>\theta_{c} , where p ^ \hat{p} is the pass rate of the session’s last five builds of the same kind, with the development split’s as prior. A session’s first build, which rarely passes,
thus renders after its verdict, and later builds render early ( Fig. 1 c), 88.9% of builds on
32 cores and 87.6% on 8.
Across the agent’s think time.
The machine would be idle while the agent reads a failed build’s errors; serving systems use such windows too ( Xia et al., 2026 ) . The build therefore answers at its verdict, cancels any render started early
( line 9 ) but keeps the frames it stored. It then renders the rest of the failed version’s frames into the frame store
as work ahead ( line 10 ), until the next build stops it. By Sec. 3.2 , a stored frame is
exact for any later version that draws it.
4. Experiments
4.1. Experimental setup
Frameworks and hardware.
Every system renders the same programs at 1080p and 30 frames per second: cv.js programs, written for our Canvas 2D runtime and run in headless Chromium, and Remotion ( Remotion, 2026b ) programs, written in React. The machines are 32, 8 or 4 of one server’s cores, with 2 GB of memory per core. 32 cores are abundant, since a render starts fewer workers than there
are cores; 8 are constrained, since a render can use more workers than cores; and 4 are saturated, since frame capture
alone fills them. Every system renders on the CPU (supplementary material).
Baselines.
For the wait, Rebuild is CodeReel without exact reuse and blocking-aware scheduling: one priority for every
operation, the checks in a single browser page with the lint after them, no fast checks or failing fast, and the render
after the checks. It keeps every other mechanism, such as warm browser pages, a resident voice process and workers sized to the machine. Sequential runs a
build’s steps one after another on the same runtime, with cold browser pages, a cold voice process and eight render
workers, as code-to-video agents run theirs ( Chen et al., 2026b ; Ku et al., 2025 ) .
For reuse, we implement on the same films the schemes that tools and caches use. Scene windows re-render the time windows of the scenes whose files changed, and read sets re-render the frames whose files or read values changed. Kamishibai-style fingerprints ( kamishibai, 2026 ) are typical , over a part’s file and timing, or careful , adding every shared script and the whole timeline. Manim-style per-call caching keys each scene whole, by its files and the values it reads, as Manim keys each animation call ( The Manim Community Developers, 2026 ) . Complete keys reuse whole scenes or narration lines when all their frames’ keys recur. The similarity rule reuses a frame as approximate caches do ( Liu et al., 2025c ; Agarwal et al., 2024 ) , on frame thumbnails.
Protocol.
EditLoop’s test split is replayed as in Sec. 2 , each session once per system, back to back on the same cores in alternating order. Replays run without think time, which only work ahead uses ( Sec. 4.3 ). The primary
estimate is the ratio of total waits over builds b b , ∑ b W b / ∑ b W b R \sum_{b}W_{b}/\sum_{b}W^{\mathrm{R}}_{b} with W b R W^{\mathrm{R}}_{b} the wait under Rebuild; 95% intervals come from 2,000 bootstrap resamples of topics ( Efron, 1979 ) . We registered the protocol before any formal run, with three claims: no
stale frame, a ratio below one on 8 and on 32 cores (Holm-corrected ( Holm, 1979 ) , one-sided 2.5%), and a shorter median
wait per build for real agents.

4.6. Ablation study
As Tab. 2 shows, most of the reduction on 32 cores comes from scheduling, which spends CPU to answer sooner, while reuse cuts frames, returns that CPU and helps most where cores are scarce. Added alone to Rebuild, reuse renders 34.3% fewer frames and
shortens the wait to 0.94 × \times on 32 cores but 0.86 × \times on 8, where rendering fills the machine. The verdict first alone, with the checks in parallel and the render alongside them, shortens it to
0.69 × \times on 32 cores with 1.12 × \times the CPU. Removing any one mechanism from CodeReel lengthens the wait, most of all the verdict first (to 1.22 × \times ). Without reuse the CPU rises to
1.27 × \times .
5. Related work
Code-to-video agents. Agents write Manim, web or slide programs refined in a render
loop ( Chen et al., 2026b ; Ku et al., 2025 ; Li et al., 2026b ; Lin, 2026 ; Zhu et al., 2025 ) , check animations in that
loop ( Ma and Agrawala, 2025 ; Liu et al., 2025a ) , drive simulators ( Bai et al., 2026 ) or mix programs with generative models ( Liu et al., 2025b ) . None reuses
more than its framework’s per-call cache, and none targets the agent’s wait.
Reuse. Training-free caches ( Ma et al., 2024 ; Liu et al., 2025c ; Liu et al., 2025d ) , edit-time methods ( Li et al., 2022 ; Nitzan et al., 2024 ; Liu et al., 2026a ) , render caches ( Walter et al., 1999 ; Nehab et al., 2007 ) and video networks
that skip unchanged regions ( Habibian et al., 2021 ; Parger et al., 2022 ; Dutson et al., 2023 ) approximate the full computation. Production tools,
browsers and UI frameworks cache or skip by node, layer, object or component ( Foundry, 2018 ; Adobe, 2026 ; The Chromium Authors, 2026 ; Flutter, 2026 ; React, 2026 ; Jetpack Compose, 2026 ) . Closest to us, Manim keys animation
calls by their inputs ( The Manim Community Developers, 2026 ) , kamishibai fingerprints a frame’s page at the same index ( kamishibai, 2026 ) ,
HyperFrames repeats frames its timeline predicts static ( HyperFrames, 2026 ) , and Fourier fingerprints scenes and layers,
also after a layer moves in time ( Fourier, 2026 ) . Browsers and UI toolkits keep drawing commands as display lists within one page’s lifetime ( The Chromium Authors, 2026 ; Flutter, 2026 ) ; CodeReel keys whole frames by their evaluated commands, so frames of imperative code with one clock are found in any version at any time ( Tab. 3 ). Like build systems and their content-addressed caches ( Mokhov et al., 2018 ; Curtsinger and Barowy, 2022 ; Bazel, 2026 ; Hammer et al., 2014 ) , it is consistent with a build from scratch, but it keys what a program draws instead of what it reads.
Scheduling around agents. Test prioritization runs likely failures
first ( Rothermel et al., 2001 ; Prado Lima and Vergilio, 2022 ) , and agent systems schedule around tool
calls ( Kim et al., 2024 ; Xu et al., 2024 ; Ye et al., 2026 ; Xia et al., 2026 ; Liu et al., 2026b ; Zhang et al., 2026 ; Zheng et al., 2026 ) . CodeReel schedules within a
build by what the agent is blocked on, and the frames it renders ahead need no rollback.
6. Limitations and conclusion
CodeReel shortens a code-to-video agent’s wait by exact frame reuse, which removes repeated work, and blocking-aware scheduling, which spends the CPU it frees on what the agent waits for; neither changes the film a build delivers. On EditLoop, the wait falls by 36.3% against Rebuild and
57.9% against Sequential, and the gain holds across models, harnesses and frameworks.
Our scope is 2D video programs whose drawing a runtime can record. Frames of 3D scenes are
rendered exactly but never reused, footage from generative models lies outside the scope, and an edit that changes most
frames gains mostly from scheduling. Exact reuse for 3D and GPU rendering, and agents that plan their edits around what
can be reused, are directions for future research.
LLM usage statement
LLM coding agents are the subject of this study: EditLoop records their sessions, and Sec. 4.5 runs them
live. GPT-6.1 wrote sixty of EditLoop’s topics, and Claude Opus 5.5 scored the real agents’ films blind to the system. A
coding agent helped implement the system and the experiment scripts, ran experiments under the authors’ direction and
drafted parts of the text from the authors’ notes. The authors checked every result and reference, revised all text and
take full responsibility for the content; no LLM is an author.

Appendix S1 EditLoop in detail
A session records one agent making one film: every version it committed, every tool call in order with its
timing and outcome, the agent’s think time before each call, and the class of edit each build follows.
The real track has 123 sessions of Claude Code ( Anthropic, 2026a ) with Claude Opus 5.5 ( Anthropic, 2026b ) making
explainer films with cv.js, our Canvas 2D ( WHATWG, 2026 ) runtime ( Fig. 2 ). These sessions hold
1,525 versions, 2,078 tool calls and 1,314 builds. Their films last
52 to 146 s between the 10th and 90th percentiles and are narrated in Chinese and
English. Of the track’s builds, 39.0% follow edits that add or remove files, 26.1%
follow edits of narration lines, 12.6% follow edits of one scene’s script and 20.4%
follow edits of shared scripts or data. The track holds every session recorded over two weeks that built at least two
versions. A scripted user issued every change request. Of these sessions, 60 are on
held-out topics, which GPT-6.1 ( OpenAI, 2026b ) wrote for EditLoop. Each held-out
topic has three rounds of change requests that build on one another.
The model track has 20 sessions of Claude Sonnet 5.5 and Haiku 5.5 ( Anthropic, 2026b ) on 10 test topics. The
Remotion track brings a second framework, Remotion ( Remotion, 2026b ) , with synthetic edits. For each of two films
we wrote and each of three random seeds, a generator applies 24 edits in turn. The generator draws each edit’s class and
the think time before each build from those of the real track. This gives 150 versions in
6 sessions. The real track is split by topic. The 33 sessions on topics used to tune
any parameter form the development split. The other 90 sessions, on 72 topics that
include all of GPT-6.1’s, form the test split. Section 4 reports results on the test split. The timed replays take one session from each of 70 topics, drawn with a fixed seed. The reuse study takes the 355
pairs of adjacent delivered versions of 88 test-split sessions.
Format.
A session directory holds four entries. session.json gives the track, framework, topic, date, narration
language, film length, the agent’s model and harness, the machine profile, the framework’s commit, counts, edit classes,
the voice pool and what was scrubbed. manifest.jsonl gives each version’s files by content hash.
calls.jsonl gives, per call, the tool, the agent’s arguments with the project path abstracted, the version the
call saw, the call’s start, recorded duration and exit, a build’s verdict time and edit class, and the think time
before the call. objects/ holds the file contents by hash. A call’s version is the version committed within
2 s of the call’s start or, if there is none, the newest version before the call.
Held-out topics.
GPT-6.1 wrote the held-out topics of the 60 sessions in five kinds (concepts, data,
systems, teaching, products) and two languages. Each topic has three rounds of stacked change requests: a local change,
a global change, and a mixed change that takes something back.
Replay is closed-loop ( Schroeder et al., 2006 ) . A system executes a session’s calls in order, each call after
the previous one has answered, either at once or after the recorded think time. The system’s caches start cold and
persist across versions but not across sessions.
Correctness gate. Approximate reuse is judged by image similarity ( Liu et al., 2025c ) . EditLoop instead
requires the answers of a build from scratch before any time counts, which is the from-scratch consistency of
incremental computation ( Hammer et al., 2015 ) . A build must pass or fail as the build from scratch does, and it must
report no error that the build from scratch does not report. Every captured frame of every delivered film must equal
the frame that a render of that version from scratch captures. The sound must match within the tolerances given below.
Metrics. Renderers are compared by render time ( kamishibai, 2026 ) , which misses what blocks the
agent. The wait therefore runs from a build’s call until the build answers the agent. A build that fails a check
answers at the verdict, and a build that delivers answers after the film and its checks. We also report the time to
verdict, frames rendered, CPU-seconds and peak memory.
The correctness gate in full.
The reference for a verdict is a build from scratch. When both a system and this reference ran every check, the two
verdicts must hold the same errors, each given by its check, element and time. Every frame that a system captures for a
delivered film is compared with one reference shared by all systems, the frames of a render from scratch with no cache
and no key. The encoded film must hold every captured frame. It must also decode as the same system’s render from an
empty cache on as many cores decodes, since the encoder’s output follows the segments that the system cuts and the
cores it has. The sound is compared with that of the render from scratch. It must have the same tracks and channels,
lengths within a frame, and loudness within 0.5 LU overall and within 1 dB in its 20-ms envelope.
The checks.
A build’s verdict comes from machine checks of the film and a lint of its sources ( Tab. S1 ). Most checks
read what a frame draws, its texts with their boxes and its image draws. They sample the film every 40 ms, and the
overlap check samples it every 0.5 s. Three checks read the pixels of sampled frames. Two checks read the sound and the
encoded film and therefore need the film. A passing build runs these two after its render ( FilmCheck in
Alg. 1 ). An error stops the build, and a warning is returned with the film. Across versions, a check keeps
its record at a sampled time under the cascade’s first two tests, that is, when no changed script reaches that time and
the values read by the frame at that time are unchanged. After a change to any other file, the checks take every record
again.

Baselines in detail.
Input hash re-renders every frame of a version that changed. Scene windows re-render the frames inside the old and
new windows of every scene whose file changed. When a file that no scene owns changed, they re-render every frame. Read
sets re-render a frame when the files of the parts it draws or the set of parts it draws changed, or when it read a
value that changed. Kamishibai-style fingerprints follow the hand-written tokens of the incremental renderer
kamishibai ( kamishibai, 2026 ) . Typical fingerprints key a part by its file, its own start and end and the local time.
Careful fingerprints add every shared script and the whole timeline. The animation engine Manim ( The Manim Community Developers, 2026 ) keys an
animation call by hashing the call’s arguments and the scene’s objects as they stand. Manim-style per-call caching keys
a scene in the same way, by its file, the shared scripts, its length, every value its frames read and every value its
script read at load, such as a scene’s start or a line’s timing. It does not key a scene by where the scene sits, and
it keys the subtitles also by the shared scripts that style them. We checked this cache against Manim CE itself on four
kinds of edit. Complete keys cut the film into scenes or into narration lines and reuse a unit whole when the same
sequence of frame keys was rendered before anywhere in the film. They are therefore exact and follow units in time.
They bound what a cache of whole scenes or lines with complete keys could reuse. The similarity rule reuses a frame as
training-free caches reuse features between similar denoising steps ( Liu et al., 2025c ) . It renders every frame at a
quarter of its size and shrinks the frame to a 32 × 18 32\times 18 gray thumbnail. It reuses the previous version’s frame at
the same time when the mean absolute difference of the two thumbnails’ gray levels (0–255) is below a threshold, which
we sweep from 0.1 to 8. HyperFrames ( HyperFrames, 2026 ) , an HTML video framework for agents, renders ports of the
Remotion track’s versions, each port at 1080p with as many frames as Remotion’s own render.
What the scrub keeps.
Every replaced file becomes a placeholder of the same size or length, chosen by the original’s content hash. The
same original therefore always becomes the same placeholder, and the scrub keeps which frames change between versions.
A font is kept when its license allows. Otherwise a substitute font holds every character the narration uses. Voices
become tones over the samples where speech was, so the narration’s cut points and the timeline are unchanged.
Speech-recognition caches are re-keyed. All numbers in the paper are computed on the scrubbed sessions, which are the
ones released.

Rules.
Replays are closed-loop. Caches start cold and are never shared across sessions or replays. A system’s timings count only if every call passes the gate. We built the system and set its parameters on the development split. The early render’s
control group and rule, the fast checks, the page’s part of the key and the place of the key evaluation were designed
with the test split’s replays in view. The data come with a key trace, which gives every frame’s key and read values
for each rendered version, renumbered within the session. They also come with an OpenTelemetry export, with one
invoke_agent span per session and one execute_tool span per call. A datasheet and Croissant metadata
describe the data.

its pixels equal the pixels rendered under that key, provided that (i) the frame’s drawing is deterministic, (ii) the key holds the frame’s

normalization rules below characterize it. This is Property 3.2 with each of its provisos spelled out.

Determinism.
Reads of Math.random , Date.now and performance.now inside render(t) are recorded. The

Normalization rules.
The rasterizer draws text from its glyph atlas at a baseline snapped to whole device pixels, so such text is keyed
by the snapped baseline. The drawing itself is unchanged, and the key follows the rasterizer. This snapping applies to
text drawn by fillText without a width limit, under an axis-aligned transform with positive scales and no
filter or shadow, at a glyph size of at most 256 device pixels, the atlas’s limit, and with a device baseline at least
0.02 pixels from a rounding boundary. Any other text enters a key with its coordinates as given. In a sweep over fonts,
sizes, equal and unequal scales, all baselines, fill and stroke, color, alpha, spacing and the atlas edge, every such
key stands for one picture.
An off-screen canvas or layer forgets its pixel history when it is overwritten whole from a clean state, by a
whole-canvas clearRect or putImageData or by an opaque fillRect under the identity
transform. The canvas’s hash then restarts with its drawing state. Any other drawing keeps the history in the hash.
Chromium keeps a raster state per 2D canvas that follows what the canvas drew before, and resizing the canvas to zero
and back clears this state. Every canvas (the main one, the caption layer and every other layer) is therefore resized
to zero and back before each captured frame. Three renders of a version then agree frame for frame. A frame evaluated
only for its key is drawn on contexts reset in place. It is drawn in full when its drawing reads pixels back or when
the page holds a context other than 2D. The 2D canvas is rasterized in software at full scale. On Remotion pages, what
a frame draws is the laid-out page, with its elements under their computed styles and its resources by content. An
element that cannot be visible, with opacity zero, is keyed by its box alone. Text on these pages is drawn in
grayscale, since with subpixel text a frame’s pixels depend on what the page drew before.

Appendix S3 Scheduling details
Mechanisms and when each is used.
The checks’ text sweep samples the film every 40 ms, and their frame checks sample it every 0.5 s. Within a build,
the sweep runs over k k browser pages in parallel (par), with k = 8 k=8 on 32 cores or more and k = max ⁡ ( 2 , min ⁡ ( 4 , c − 4 ) ) k=\max(2,\min(4,c-4)) on
c c cores below 32. The parallel sweep is used on c ≥ 6 c\geq 6 cores without a software-only rasterizer. The source lint runs
alongside the checks (dag). The fast checks (vp) draw a sampled frame on reset contexts, as the evaluation of a key
does, instead of on a new canvas. They draw a frame whose code reads pixels back in full. The fast checks also keep the
source map, which maps drawn objects to source lines, off the verdict’s path. A check without errors returns at once,
and a check with errors scans the frames its errors name for their source lines. After the verdict, a separate process
at the lowest priority rebuilds the map. The early render (opt) starts alongside the checks on pages of its own, in a
control group of its own marked idle. A passing verdict gives the group a normal share and the first claim on memory. A
failing verdict kills the group whole. A failure known from the files before the verdict, such as a stale narration
text or a lint error, stops the early render at once. The early render starts when p ^ > θ c \hat{p}>\theta_{c}
( Eq. S1 ), with p ^ = ( a + 4 ​ m ) / ( n + 4 ) \hat{p}=(a+4m)/(n+4) . Here n n counts the session’s last five builds of the same kind of edit,
narration changed or not, or the last five of any kind while that kind has fewer than two. The count a a holds those
among them whose checks passed. The rate m m is the development split’s pass rate, 1 / 33 1/33 before a session’s first build

A later build always does on 4, 32 and 64 cores, and on 8 cores unless the five builds counted all failed. The capture
workers evaluate the keys, each worker for its own segments, instead of a pass before the capture (kw). On machines
below 16 cores, builds fail fast (ff). The data, style, determinism and timeline checks, which seldom fail, then run
only once the other checks found no error that stops the build. Operations run at the priorities of their consumers
(pri), which are normal priority, the idle group and nice 19. Within a render, the audio chain runs alongside the frames
(aud), capture pages open early (pre), each worker encodes a segment while it shoots the next (enc), and the workers
are sized to the machine (wk). Rebuild uses every mechanism that applies on the machine except par, dag, vp, opt, kw,

its callers in turn. Renders get no fixed share of the cores.
Within a build: the verdict first.
On half of the builds the agent waits only for the verdict, whose checks sweep the whole film. CodeReel runs the checks
first and in parallel. Their sweep is cut by time over several browser pages, and the lint runs alongside the sweep.
The fast checks of CodeReel also leave out what a verdict does not need. The checks that read what a frame draws,
not its pixels, draw their samples as the evaluation of a key does ( Sec. 3.2 ). The map from drawn objects to
source lines is built after the verdict. Where cores are scarce and the checks that seldom fail would delay the
verdict, a build also fails fast, as in test prioritization ( Rothermel et al., 2001 ; Prado Lima and Vergilio, 2022 ) . The checks that
seldom fail then run only once the others found no error, and the build answers at the first errors that stop it.
Within a build: the render as a bet.
Starting the render alongside the checks is a bet on the outcome, like the sandboxes that agent serving
prewarms ( Zhang et al., 2026 ) . The early render saves render time when the version passes and slows the checks in either
case. At idle priority, the render slows the checks by a fraction d d through the memory, kernel and I/O they share,
and it keeps a share s s of its own speed. The bet therefore pays when the version passes with probability above
θ c = d / ( s ⁡ ( 1 + d ) ) \theta_{c}=d/\bigl(s(1+d)\bigr) ( Appendix S3 ). Idle priority keeps the bet cheap. The measured θ c \theta_{c} is
0.25 on 8 cores and 0.21 on 32. 4 takes the bet when p ^ > θ c \hat{p}>\theta_{c} , where
p ^ \hat{p} estimates that probability from the session’s last builds. A session’s first build, which rarely passes, thus
waits for its verdict, and later builds render early ( Fig. 1 c). The render starts early in
88.9% of all builds on 32 cores and in 87.6% on 8.

Across agents sharing a machine.
Under the capacity constraint, the builds of all agents on a machine draw cores and memory from one ledger sized from
measured footprints. Agent serving similarly shares servers among agents ( Yang et al., 2025 ) and meters resources per
tool call ( Zheng et al., 2026 ) . A render’s workers follow what the render is granted, and work ahead yields when blocking
work cannot fit. The ledger’s entries follow the memory admission below.
Memory admission.
A render asks a ledger, kept per memory budget, for the memory of its plan. This memory is estimated from
measurements on this machine: 0.4 GB plus 0.9 GB per capture worker at 1080p, 5 MB per second of film for the audio
chain alongside the frames, and 0.15 GB per warm page held by the execution service. The workers are first capped by
the cores the render may use and then sized by the memory granted. The audio runs alongside the frames only if it fits
in the grant. When the grant falls short of the plan, the render first drops the audio’s overlap and then workers.
Pages without the GPU.
Chromium gives every browser a GPU process. With the NVIDIA driver, these processes wait on a lock of the driver that
all of them share, whatever cores or GPU they use. On a 29 s film at 1080p, three renders at once each
took 1.49 × \times as long as one render alone. A film whose code never asks for WebGL is shown with the GPU
off ( --disable-gpu --disable-software-rasterizer ), so no process opens the driver. Its Canvas 2D is rasterized
on the CPU at full size either way, so the frames are the same (8,425 frames of four films).
No render then waits on the lock. A render takes 9.1 s instead of 15.5 s, and three
renders at once each take 1.03 × \times as long as one. Every system in Sec. 4 runs this
way, and the mode is part of every cache of pixels. A film counts as one that may use WebGL when its code mentions
WebGL anywhere. Such a film is drawn by SwiftShader, which runs the GPU interfaces on the CPU, with the Vulkan loader
shown only SwiftShader’s driver, so no process opens the graphics device either. Its 2D canvases are rasterized on the
CPU as in every other film, since on SwiftShader’s GPU path a canvas’s pixels depend on what the page drew before. Two
renders from scratch of one version then agree frame for frame. WebGL frames are never keyed and are always rendered
afresh. On the adjacent versions of a test session that draws with WebGL, every frame equals a render from scratch.

Co-location conditions.
All conditions run inside one scope that sets the machine’s cores, a CPU quota and a memory cap without swap. The
scope’s memory events, its kills, are kept. Uncoordinated execution has no priority classes and no ledger, and it runs
one executor per session. Niced renders add the priority classes of Sec. 3.3 and nothing else. One control
group per call runs like uncoordinated execution but puts every call in a control group of its own at equal weight.
Each session’s executor gets a control group of its own for its daemons. CodeReel has one ledger of the cores and memory,
the priority classes, and one executor for all sessions, which serves its callers in turn.
Sessions arrive at fixed offsets. Each session replays its calls closed-loop with a quarter of its recorded think time.
Each run takes eight cores of the upper hyperthread half of one socket, whose siblings our jobs leave unused.
Appendix S4 Registration and the machine
Frameworks and hardware.
Every system renders the same programs at 1080p and 30 frames per second. These are cv.js programs, written for our
Canvas 2D runtime and run in headless Chromium, and Remotion ( Remotion, 2026b ) programs, written in React. The machines
are 32, 8 or 4 of one server’s cores, with 2 GB of memory per core. 32 cores are abundant, since a render starts fewer
workers than there are cores. 8 cores, a laptop’s size, are constrained, since a render can use more workers than
cores. 4 cores are saturated, since frame capture alone fills them. Each session runs in its own control group on an
AMD EPYC 9755 machine. Every system renders on the CPU, for the reasons given under Pages without the GPU
( Appendix S3 ).
Registration.
We registered the protocol before any formal run. It fixes the split, the machines, the gate and every test. The
tests on 8 and 32 cores form the primary family under Holm’s procedure ( Holm, 1979 ) .
The registered decisions are these. Exactness holds if every pair, at least 1,800 random edits and the 32 narration
edits are exported and every frame of their incremental renders equals a render from scratch. For 8 and 32 cores, the
upper end of each ratio’s interval must lie below one, one-sided at 2.5% for the family under Holm’s correction. No
resample’s ratio reaches one. The largest of the 2,000 resampled ratios is 0.68 on 32
cores and 0.72 on 8. For real agents, the measure is the geometric mean over pairs of the ratio of
within-session median waits per build. It is taken on the 14 pairs whose topics development never touched, with all 26
pairs as a secondary analysis. The films’ quality is reported as paired differences. Per build, the agent’s wait under
CodeReel relative to its wait under Rebuild on the same build has a median of 0.56 × \times on 32 cores (95%
CI 0.53–0.59) and 0.52 × \times on 8 (CI 0.50–0.56). Table 2 gives the ratios of
total waits.
The machine.
The machine has 512 hardware threads on two sockets. Timed replays ran in lanes of disjoint cores on the upper
hyperthread half of one socket, whose siblings our jobs left unused. Both systems of a session ran back to back in one
lane. The scaling runs of Fig. S1 ran one replay at a time.

S5.3. Exactness and tightness of reuse
Over the 1,023,902 frames of the reuse study’s 355 pairs, CodeReel reuses no frame whose pixels
changed and renders close to the frames whose pixels are new. Every other scheme renders more or reuses stale frames
( Tab. 3 ). CodeReel renders 63.2% of the frames, which is 1.05 × \times the frames
whose pixels are new. Complete keys on whole scenes and on narration lines are exact as well. Complete keys on whole
scenes, which bound what per-call and per-scene caches ( The Manim Community Developers, 2026 ; Fourier, 2026 ) can reuse, render 80.2%
of the frames, and complete keys on narration lines render 71.1%. Of the frames an edit changes,
32.6% keep an SSIM above 0.99 to the frame they replace, and 8.1% keep an
SSIM above 0.999. The similarity rule of Tab. 3 therefore leaves 7.0% of all frames
stale. These frames miss the agent’s edit ( Fig. 2 , bottom) at a median SSIM of 0.999 to the
correct frame (see the similarity rule, below). No frame CodeReel reuses is stale, here or in 2,000 random
edits. A key audit checks every key against a lossless capture of its frame, over 2,164,167 frames, of which
98.6% are keyed. No key stands for two pictures, and every kept key audited equals its fresh
evaluation.

Evidence.
We compare incremental renders with renders from scratch, frame by frame, on 2,000 random edits of seven
kinds on four films (style 379, timeline 376, num 373, draw 257, neutral 255, color 180, text 180). Every edit rendered, and every frame of every edit equals the render from
scratch. The same holds over the adjacent versions of the test split ( Tab. 3 ).
Exports.
Every one of the 355 pairs and every random edit was exported and compared frame by frame. All
1,023,902 frames of the pairs, reused or rendered, equal a render from scratch.
The similarity rule.
At the threshold of Tab. 3 , the similarity rule leaves 7.0% of all frames stale. Its
stale frames look right to image metrics, at a median PSNR of 41.2 dB and a median SSIM of
0.999, because an agent often changes a few words. In one example, a caption was rewritten from “the weak
machine is about 4 × \times slower” to “the weak machine is about 4 × \times slower than the strong machine”
(translated from Chinese), and the frame the rule keeps has an SSIM of 0.993 to the correct frame.
Whatever the rule, many of the frames an edit changes stay near the frames they replace. Of the frames that differ
from the previous version’s frame at the same time, 32.6% have an SSIM above 0.99 to that frame and
8.1% have one above 0.999, and the median SSIM is 0.971. A rule that
reused every frame above 0.99 would leave 21.0% of all frames stale. The shares are measured on
thirty changed frames drawn from each pair of Tab. 3 , rendered in both versions and weighted by the pair’s
changed frames.
Table S10 gives the similarity rule at thresholds below that of Tab. 3 , on 23 pairs of
the test split drawn at random. The smallest mean difference that two different 32 × 18 32\times 18 thumbnails can have is
1 / 576 1/576 . At 0.001, below that value, the rule reuses a frame only when its thumbnail is identical to the
previous version’s. A stricter threshold makes the rule render more frames and reuse fewer stale ones. At the strictest
threshold, the rule renders 66.7% of the frames, more than the 57.2% whose pixels
changed, and still reuses 14 stale frames in 4 pairs. Matching each frame to
the nearest thumbnail of the previous version lets the rule reuse a frame moved in time. At the strictest threshold,
this matching reuses 1,804 stale frames in 17 pairs. Two frames with the same

Time-shifting edits.
CodeReel reuses the frames that a time-shifting edit moves. Such a move defeats reuse by time and by scene window. On
32 narration edits to four cv.js films ( Tab. 3 , right), CodeReel renders
43.9% of their frames, against 43.0% whose pixels are new, and reuses no stale
frame. Read sets render more and reuse 7,228 stale frames. On two Remotion films with eight such
edits each, 120 distinct pictures are new. CodeReel renders 128 frames there, and a cache
looked up by time renders 2,373.
Manim CE’s own cache.
On one scene of eight animation calls, Manim CE’s cache re-renders every frame of each call an edit reaches. This is
the granularity of Manim-style per-call caching in Tab. 3 . Manim CE re-renders from 16 of 106 frames after a
caption edit to every frame after a change to the text every call draws, and it shows no stale frame.
The stale frames of Manim-style per-call caching lie in scenes whose own files did not change but which call drawing
code from another scene’s changed file. A per-call key over a call’s own file, the shared scripts and its data cannot
see that code, which immediate-mode programs run every frame. Manim instead hashes the objects themselves.
The cost of each edit.
On 85.6% of the pairs, CodeReel renders within 5 percentage points of the frames whose pixels are
new, with a median excess of 0.1 points ( Fig. 6 b). Edit-time
methods ( Nitzan et al., 2024 ; Li et al., 2022 ) aim for such a cost, close to what the edit changes. Manim-style per-call caching
renders every frame of each call an edit reaches.
S5.4. Real agents in the loop
Real-agent runs.
Every session ran on 8 cores with cv.js programs and the scripted user of the registered protocol. The scripted user
asks for each round’s changes and accepts the film. Claude Code ran Claude Opus 5.5, and Codex CLI ran GPT-6.1. The
Wait and Film ratios of Tab. 4 are geometric means over pairs of per-session medians. The table’s Total column gives each pair’s ratio of total waits, the measure of the replays. Replayed under the
protocol of Sec. 4 , the sessions that Claude Code recorded live on topics never used in development
show the same gain. The agent waits 0.60 × \times as long as under Rebuild on 32 cores and
0.66 × \times on 8.
Film quality of the real-agent pairs.
Under the registered scoring protocol, Claude Opus judges the delivered films and lists the faults of each session’s
final film. We report the paired differences, CodeReel minus Rebuild. On the 14 pairs whose topics
development never touched, the final films’ faults change by − - 0.29 (95% CI
− - 1.64 to 0.69). For the 12 pairs through Codex CLI, the faults change by
− - 0.58. The judge sees each film’s contact sheets, last frame, narration text and audio levels under a
name drawn from a content hash, so the judge does not know which system built the film. Claude Code’s 26 pairs are ten
topics run twice and six topics of Code2Video’s benchmark ( Chen et al., 2026b ) run once. Codex CLI’s pairs are those six
topics run twice. The two sessions of each pair ran back to back on the same cores, in an order that alternates between
repetitions. Every interval resamples topics with all their pairs. Each final film that a build under CodeReel delivered
was rendered again from scratch with the session’s own code, and the two films decode to the same frames.
S5.5. Ablation study
The two parts shorten the wait in different ways. For the last block of Tab. 2 , we replay Rebuild with
one mechanism at a time on 32 and 8 cores over 70 topics, without think time. Reuse removes work. Added
alone, reuse renders 34.3% fewer frames with 0.81 × \times the CPU. The agent then
waits 0.94 × \times as long on 32 cores and 0.86 × \times on 8, where rendering fills the
machine. The verdict first, which runs the checks in parallel and the render alongside them, spends CPU to shorten the wait. With
the verdict first alone, the agent waits 0.69 × \times as long on 32 cores and 0.86 × \times on
8. On failing builds, it waits 0.49 × \times as long on 32 cores and 0.60 × \times on
8. The verdict first alone uses 1.12 × \times the CPU on 32 cores and 1.05 × \times on 8.
With every mechanism, the agent waits 0.64 × \times as long under CodeReel on 32 cores and
0.67 × \times on 8, and CodeReel uses 0.81 × \times the CPU on 32 cores and
0.76 × \times on 8. Reuse thus returns the CPU that the verdict first spends. With the fast checks alone,
the agent waits 0.82 × \times as long on 32 cores and 0.88 × \times on 8. Starting the render
early adds to the gain of the verdict first. When the render never starts early, the agent waits
1.07 × \times as long as under CodeReel on 32 cores (CI 1.03–1.10). Without static impact, CodeReel evaluates 1.22 × \times as many keys, and without values read, it evaluates
1.24 × \times as many (see the parts of reuse, below).
The parts of reuse.
We turn one part of reuse off at a time on 50 pairs of Tab. 3 . With static impact or values
read off, the same frames are rendered. The keys evaluated rise to 1.22 × \times with static impact
off and to 1.24 × \times with values read off. Text-baseline snapping saves 534
unchanged frames. Keys that hold a frame’s position in time cost 1.11 × \times the frames on
narration edits. We also time CodeReel with one part off at a time on four topics, with every film gated
(18/18). Relative to the full CodeReel, the agent waits 1.08 × \times as long with static impact off,
1.03 × \times with values read off and 1.04 × \times with text-baseline snapping off.
Appendix S6 Related work in full
Code-to-video agents and benchmarks.
Agents make explanatory videos by writing Manim, web or slide programs and refining them with a renderer in the
loop ( Chen et al., 2026b ; Ku et al., 2025 ; Li et al., 2026b ; Lin, 2026 ; Zhu et al., 2025 ) . Agents also drive physics simulators and
renderers through code ( Bai et al., 2026 ) , mix programs with generative models ( Liu et al., 2025b ) , and program slides and 3D
scenes in the same loop ( Ge et al., 2025 ; Huang et al., 2024 ; Gu et al., 2025 ) . VISTA ( Long et al., 2026 ) refines generated videos,
LottieGPT generates vector animations as tokens ( Chen et al., 2026a ) , and the Scene Language represents scenes as
programs ( Zhang et al., 2025 ) .
These works improve what the agent writes and how its output is judged, and some measure tokens and
time ( Chen et al., 2026b ; Li et al., 2026b ) . None goes beyond its framework’s per-call cache or targets the latency of a verdict.
Benchmarks grade the result, and some also grade cost or trajectories ( Gu et al., 2025 ; Chen et al., 2026c ; Gupta et al., 2026 ) .
Code2Video-Compass ( Chen et al., 2026c ) , on the same web and Remotion stack, generates a video in one call. Agent traces
record tool latencies ( Zhu et al., 2026 ) and are replayed to benchmark serving ( Pan et al., 2026 ; Lau et al., 2026 ) .
EditLoop’s replay instead executes the calls.
Reuse.
Training-free caches reuse or forecast features between denoising
steps ( Ma et al., 2024 ; Wimbauer et al., 2024 ; Zhao et al., 2025 ; Lyu et al., 2025 ; Liu et al., 2025c ; Kahatapitiya et al., 2025 ; Liu et al., 2025d ) . Edit-time methods compute on the edited
region ( Li et al., 2022 ; Nitzan et al., 2024 ; Yu et al., 2024 ; Liu et al., 2026a ) or reuse unchanged regions across editing turns ( Li et al., 2026a ) .
Serving, graphics and video models skip or reproject work for similar inputs, frames or
pixels ( Kodaira et al., 2025 ; Agarwal et al., 2024 ; Walter et al., 1999 ; Nehab et al., 2007 ; Habibian et al., 2021 ; Parger et al., 2022 ; Dutson et al., 2023 ) . All of these methods let
their output differ from the full computation’s.
Production tools and UI toolkits reuse operator outputs, frames and display lists ( Foundry, 2018 ; Adobe, 2026 ; The Chromium Authors, 2026 ; Flutter, 2026 ) .
Closest to us, Manim keys each animation call by its inputs ( The Manim Community Developers, 2026 ) . Kamishibai fingerprints each frame’s page and
reuses the previous run’s frame at the same index ( kamishibai, 2026 ) . HyperFrames repeats the frames that its timeline
predicts to be static within one render ( HyperFrames, 2026 ) . Fourier, a video framework built for agents, fingerprints
sources, assets and timing to reuse unchanged scenes, layers and speech, also after a layer moves in
time ( Fourier, 2026 ) .
CodeReel keys a frame by its evaluated drawing commands, normalized to the rasterizer, so frames of imperative code with
one global clock and no call or layer boundaries are found again in any version, at any time. Like build
systems ( Mokhov et al., 2018 ; Curtsinger and Barowy, 2022 ) and incremental computation ( Hammer et al., 2014 ; Hammer et al., 2015 ) , CodeReel keeps
its results consistent with a build from scratch. Its keys, however, come from what a program draws and not from the
files the program reads.
Scheduling around agents.
Test prioritization runs likely failures first ( Rothermel et al., 2001 ; Prado Lima and Vergilio, 2022 ) . Agent controllers weigh cheap
diagnostics against costly verification ( Papamarkou et al., 2026 ) . Agent serving places KV caches around tool
calls ( Xia et al., 2026 ; Liu et al., 2026b ) , shares GPU servers among agents ( Yang et al., 2025 ) , prewarms sandboxes ( Zhang et al., 2026 ) and
controls CPU and memory per tool call by declared intent ( Zheng et al., 2026 ) . Agent systems also run independent tool
calls in parallel ( Kim et al., 2024 ) and start a tool while the model is still decoding ( Xu et al., 2024 ) . Speculative
agent systems guess the agent’s next action and keep a guess only when the guess matches the action
taken ( Ye et al., 2026 ) . Build services schedule by a priority that users set ( BuildBuddy, 2026 ) .
CodeReel schedules the operations of a video build by what the agent is blocked on, within the build and across the agent’s
think time. It admits the work of agents sharing a machine against one ledger of the machine’s cores and memory. The
work ahead of CodeReel needs no rollback, since a frame stored under its key is exact for any later version that draws it.
